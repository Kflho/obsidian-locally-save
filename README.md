# Locally Save

把整个仓库（或只把自上次完整副本以来改动的那部分）打成一个 `.lsave` 文件，
用 U 盘、网盘、聊天软件搬到另一台电脑上应用。

不联网，不要账号，没有服务器，也不在后台同步。它只做一件事：离线地把单文件搬来搬去，
顺带留还原点。

- **换电脑 / 重装系统**：一份包搬过去，笔记和文件夹结构一起回来。
- **两台电脑轮流用**：日常只搬变了的那部分，通常几十 KB 到几 MB。
- **想留个还原点**：把当前仓库整份打成包，哪天改坏了，应用回去就回到那一刻。

想要“两台电脑通过一个共用目录（网盘 / NAS / U 盘）一直自动保持一致”，那不是这个插件要做的事。
那种连续同步交给 Remotely Save + WebDAV / 坚果云这类方案更合适。
这里管的是离线搬运和还原点：包能校验、能对账，搬过去应用完，两边文件一模一样。

## English overview

**Locally Save** is a desktop-only Obsidian plugin (its interface is in Chinese) that moves a vault
between machines **without network access**. Every `.lsave` file is either a full snapshot of the
vault or a diff computed from one of your full snapshots. You carry it on a USB drive, in a cloud
folder, or through a chat app, then apply it on the other machine.

- **Full copy**: the whole vault. It is both a baseline (changes bundles are always computed from one
  of your full copies) and a restore point. Applying it mirrors it: files the bundle does not contain
  go to a trash folder inside the vault, and locally modified files are replaced by the bundle's
  version (the old ones also go to trash). The vault then equals that bundle, and the full copy
  becomes your baseline.
- **Changes bundle**: a diff computed from one of your full snapshots. There are exactly two kinds:
  one full snapshot to another (to move the other machine onto your newer full copy without shipping
  the whole vault), and one full snapshot to your current vault (the everyday case). It carries only
  what changed since that full snapshot, so it **grows as you keep working**; exporting or applying a
  changes bundle does not move the baseline. The plugin reminds you when one has grown big enough to
  justify a fresh full copy. A changes bundle normally needs the receiving machine to stand on the
  same full snapshot. A bundle whose computed landing state matches the receiver's current content is
  also accepted, which is what makes a recovery bundle usable after the two baselines have drifted.
  Anything else is rejected with concrete next steps.
- **Applying is always a strict sync** (there is no mode to pick): files named in the bundle win (your
  version goes to trash), deletions named in the bundle are performed, and local files that the
  bundle's target state does not contain go to trash. In bidirectional use your own pending changes
  are packed into a changes bundle first; if that cannot be written, nothing is touched. In pull-only
  mode there is no "your half": edits on paths the bundle does not name are restored from the baseline
  full snapshot, so the resulting state id matches the sender's.
- Each bundle carries a payload checksum, a generation number, a baseline fingerprint, and a content
  **state id** ("are the two sides actually identical?"). A bundle corrupted in transit is rejected
  instead of being written into your vault. Opening a bundle is read-only: you get a full report
  (what will be added, overwritten, deleted) before anything is written.
- **Automatic modes** are off by default: keep a bundle on a schedule or after edits, and apply
  incoming bundles. The sync direction decides the policy: pull-only applies full copies and
  destructive updates, bidirectional asks first, and without git only non-destructive changes bundles
  are applied automatically.
- **Optional git transport** (off by default, desktop plus system `git`): the bundle folder itself can
  be a git worktree. New bundles are committed and pushed, the other machine's are pulled and applied,
  and each machine publishes a tiny status file (`.lsave-peers/`) with its state id, generation,
  baseline and host name. The status bar separates the git result (`已推送 / 已拉取 / 远程已是最新`)
  from per-machine content status (`一致 / 不同步 / 待上报`). Full copies are never pushed; you still
  carry the first one on a USB drive.
- **Install** from the Obsidian community plugin browser, or download `main.js`, `manifest.json` and
  `styles.css` from [Releases](https://github.com/Kflho/obsidian-locally-save/releases) and put them
  in `<vault>/.obsidian/plugins/locally-save/`. Requires Obsidian 1.7+ on desktop.

### Privacy and permissions

- **No network requests unless you turn on the optional git transport.** There is no telemetry, no
  account and no server. Git mode runs the `git` you installed against the remote you configured;
  credentials stay in your system git, the plugin never stores them. Everything else only touches your
  vault, the bundle folder you configured, and its own state file inside the plugin directory.
- **Filesystem access outside the vault** is the core feature. It copies files to and from the bundle
  folder you pick, and moves replaced or deleted files into a trash folder inside the vault.
- **Shell execution** happens only in optional features: associating `.lsave` with Obsidian (Windows
  only, runs `reg.exe`), the git transport (`git`), and the SSH setup (`ssh-keygen` / `ssh`, plus `gh`
  only if GitHub CLI is installed and logged in). None of them runs unless you click the
  corresponding button or turn git on.
- **Clipboard**: the copy-path and copy-fingerprint buttons write to the system clipboard. Nothing is
  ever read from it.

The rest of this document is in Chinese, the plugin's UI language.

## 安装

**从插件市场安装（推荐）**

1. Obsidian → **设置 → 第三方插件 → 浏览**；
2. 搜索 **Locally Save** → **安装** → **启用**。

**手动安装**

1. 到 [Releases](https://github.com/Kflho/obsidian-locally-save/releases) 下载最新一版的
   `main.js`、`manifest.json`、`styles.css`；
2. 放进 `<仓库>/.obsidian/plugins/locally-save/`，没有这个目录就新建；
3. 在 **设置 → 第三方插件 → 已安装插件** 里把它打开。

系统要求：桌面版 Obsidian 1.7 或更高（Windows / macOS / Linux）。手机端用不了：
包要写到仓库之外的文件夹，Obsidian 的手机端没有这个权限。

## 三步上手

1. **先填包目录**。设置 → Locally Save → **同步包** → 「同步包文件夹」填一个仓库之外的目录，
   比如 `D:\笔记同步包` 或 U 盘上的目录。这是必填项，没填时导出和应用按钮是灰的。
2. **A 机导出一份完整副本**。点「导出同步包…」→ 勾上「完整副本」→ 导出。
3. **B 机应用**。把那个 `.lsave` 拷过去（U 盘、网盘、聊天软件都行），拖到 Obsidian 窗口上，
   看一眼报告，点「应用」。

之后日常来回搬就用**更新包**，它只装自那份完整副本以来变了的部分，见下面「日常来回搬」。
第一次给别人机器搬家要用完整副本。对方应用完，两台机器就站在同一个基准点上，
从此互相发更新包才对得上号。

## 用 git 搬包（可选）

不想每次拷文件，可以把**同步包文件夹**接到一个**私有** git 仓库。GitHub、Gitee、自建都行：

1. 设置 → Git 远程 → 打开「启用 git 传输」→ 填远程地址（HTTPS 或 SSH）→「接入这个远程…」。
2. 平时点左侧栏第一个图标「立即同步」。它会先和远程对一遍，再发号、导出、推拉，
   最后按方向收包。导哪种包看自动留包开关；都没开时，有基准导更新包，没基准导完整副本。
3. 方向决定这台机器负责哪一半。这是硬边界，不只是一句提示：
   - **仅拉**（只收不发）：拉下来直接应用，连会删文件、删空文件夹、覆盖本地改动的包也照做，
     目标是变成对面那样。本机被覆盖或删掉的文件先进回收目录。它和对面严格相等：
     本机在包里没点名的文件上误改的，应用时从基准完整副本恢复，旧版本进回收目录，
     不会当成“我这一半”留着。应用完把新状态写进同步包文件夹。这台机器不导出任何包。
   - **双向**：收到包先弹一句确认，写清会写几个、删几个、覆盖几个，确认后才应用。
     应用完把本机这边的改动导成更新包回传，对面拉到就齐了。
   - **仅推**：只发不收，收件箱不看；对方的包要对方自己应用。
4. 想完全自动化：打开「定时同步」一个选项，到点会先推拉 git，再按「自动留包」开关留包；
   收包按上面的方向处理。
5. 完整副本不推，太大，仍用 U 盘搬一次。之后日常只有几十 KB 到几 MB 的更新包走 git。
6. 发号不撞车。导出前会看同步包文件夹里已知的最高代（对方的 peer 状态加上现有包），
   后发的那一份从它后面发号。A 先发第 101 代，B 同步时先拉到 101，再发就是第 102 代。

### 同步包文件夹可以就是某个仓库的子目录

不想为货架单独建一个仓库，就把**同步包文件夹**放进一个已有的私有仓库里
（比如个人数据仓的 `kf-personal-data/locally-save`），远程地址填那个仓库的地址：

- 插件**不会**在这个文件夹里 `git init`，也不会改那个仓库的远程地址；
- 提交只涉及这一段：仓库里你自己暂存 / 没管过的文件一个都不碰；
- `full/` 与回收站不提交，完整副本仍然只在本机（U 盘 / 网盘搬）；
- 拉取**只允许"限定范围的对齐"**（0.16.6）：能快进就快进；不能的话，只要本地没推的提交
  **全都只动货架这一段**、货架之外没有未提交改动，就自动 rebase 过去（两边同时留包不会再卡住）；
  一旦动了仓库别处、或者两边改了同一批文件，插件**停下报错并报出那个路径**，绝不 reset、不合并；
- 推的是那个仓库当前的**整个分支**（git 只能推分支），所以你自己没推的提交也会一起上去。

双向模式下两边改到同一个文件时，确认窗会写“N 处两边都改过”。应用时以包的版本为准，
你那一版留在冲突副本里（回收目录），捞得回来。想把方向定死、不要合并，
就用「让对面和我一致」/「让我和对面一致」这两个单向按钮，结果完全确定、两边状态编号一致。
它们也适合本来就是单向的机器：一台只发，一台只收。

每台机器还会往同步包文件夹里放一份很小的状态（`.lsave-peers/`，记着状态编号、
站在哪份完整副本上、主机名），同步完就能看到“对方在哪一步、两边一样了没有”。

多台电脑怎么对账：状态栏后半句会逐台计数（`对方：2 台一致 · 1 台不同步`）。
悬停能看到每台的状态编号、第几代、基准、最后上报时间；点状态栏或命令
「查看各台电脑同步状态…」开完整窗口。每台机器的「最后上报」时间是它最近一次和远程同步的时间。
超过一阵没报，先让它同步一次，再看是“待上报”还是真“不同步”。

## 两种同步包

| | 完整副本 | 更新包 |
|---|---|---|
| 里面装什么 | 整个仓库 | 只装自它基于的那份完整副本以来变过的文件（含一份删除清单） |
| 什么时候用 | 第一次给对方 / 想留还原点 / 攒大了换基准 | 日常来回搬 |
| 通常多大 | 跟仓库一样大 | 刚换过基准时几十 KB 到几 MB，之后随改动累积 |
| 应用后 | 本机变成那份包的样子，它也成为本机的基准 | 本机的内容变成包送到的状态，基准不动 |
| 放在哪 | `<同步包文件夹>/full` | `<同步包文件夹>/changes` |

导出的两个勾选各自独立，可以都要。两个都勾时先导完整副本、后导更新包：
完整副本刚把整个仓库装走，这时的更新包按它算必然是空的，所以不会生成空包，结果里会说明一句。
只想“传一个小文件过去”，就只勾更新包。

### 改名 / 移动文件夹不再重传内容（包版本 2）

以前把一个文件夹改个名，导出会把它当成“旧路径全删、新路径全是新文件”，每个文件的字节都重新装一遍。
1 MB 的文件夹改名，更新包就是 1 MB。现在包里写的是移动操作（`moves`），文件内容不进负载：

| 操作 | 包里装什么 | 接收方 |
|---|---|---|
| 整个文件夹改名 / 移动（内容都没变） | 一条 `dir` 操作 | 整棵子树 rename，0 字节内容 |
| 单个文件改名 / 移动 | 一条 `file` 操作 | rename，0 字节内容 |
| 移动后又改了某个文件 | 没改的走移动，改过的那一个才带内容 | 先 rename，再写改过的那一个 |
| 移动后又删了文件 | 旧路径和新路径各一条删除 | 两边谁有就删谁 |

- 普通包仍是版本 1，老插件照样读；带移动操作的包是版本 2，老插件会明确拒绝
  （不会把“移动”误当成删除或新增），所以两台机器都要用这一版插件；
- 移动只认“源文件还在、大小和修改时间没变”的机器。源被改过、目标真的占着，
  计划阶段就会拒绝并说清原因，不会做半套：包里没带内容，硬做只会落一个错误的状态；
- 累积更新包里重复出现的移动会跳过已经做过的：判据是“**这个源还是不是我上次记下的那一份**”，
  不是“目标在不在”。所以改名之后旧路径又被建了出来（改名时留下的空壳、你在旧名字下新建的
  文件夹 / 笔记）不会算冲突，照常应用；
- **目标文件夹已经存在时按文件并进去，不整棵替换**：目标里已经在该在的文件一个不碰，
  目标上没有的才搬过去，占着别的版本的按严格同步进回收目录的「冲突」。
  所以那台“旧版本没搬成”的机器可以放心收一份新的累积包：它已经搬过去的那批东西不会被扫掉；
- **你手工改过名 / 搬过文件也不要紧**：插件会在严格同步时按“这个包送到的那一点”核对 ——
  目标位置上的文件算在这一点里，不会被当成“本机多出来的”挪进回收目录
  （以前的版本会，症状就是“同步完那个文件夹里只剩一个文件”）；
- 连续改名（旧 → 中间 → 最终）会带链式移动，
  就算你漏掉了中间那份移动包，停在基准上的机器也能应用；
- 万一还是提示「包里要把 X 改名成 Y，但本地两个路径都不在」，那是本机真的没有这个路径了
  （本地删过或挪走了）。更新包只带改名、不带内容，补不了缺的文件：先把本机恢复到基准，
  重新应用「第 N 代」那份完整副本，再应用这个包；或者让对方导一份完整副本。
  插件不会静默落一个错乱的状态；
- 改名没做成（目标被占、文件被锁）时，状态里记的还是旧路径 —— 下一份累积包不会把它当成
  “本地多出来的”删掉，处理好之后重新应用一次就行；
- 改动历史在「同步包更新记录…」里，每次导出或应用都有一行（世代、状态编号、文件数、移动处数）。
  `changes/` 里同一台机器、同一基准的旧累积更新包会被最新那份取代，内容已经被它包含了；
  别的机器导的、别的基准的包会保留。

### 基准点：只有完整副本才算

- 一个基准点就是一份完整副本，它同时是你的还原点。更新包不产生基准点。
- 更新包只有两种形态，都是自某一份完整副本算出来的差量：
  - **完整副本 → 最新状态**：日常那种，只装自那份完整副本以来你改过的东西；
  - **完整副本 → 另一份完整副本**（差量包）：把对方从一份完整副本带到另一份，
    不用重传整个仓库。
- 导出和应用更新包都不换基准。你还是站在同一份完整副本上，所以更新包是累积的，改得越久它越大。
  攒大了插件会提醒你导一份新的完整副本换基准，之后的更新包从它重新算起，又变小了。
  想多留一个还原点，也随时在「导出同步包…」里勾「完整副本」。
  唯一的例外：对方换了新基准、却按它那份新完整副本给你导了更新包。你收下之后会跟着站到它那份完整副本上
  （你的内容本来就是它加这个包），这样两边才在同一份上，你下次发回去的包它直接收得下。
- 更新包必须发到正站在它那份完整副本上的机器，否则缺的那部分它根本带不了。
- 号永远往前走，同一个号底下不会再出现两份不同内容。比如这条线走到第 54 代，
  你应用一份老完整副本回退到第 39 代、又改了东西，这时导出的是 `39 → 55`，
  起点是你站的那份完整副本，号从用过的最大值往后发，不是历史上早用过的 `39 → 40`。
- 两份完整副本对不上（对方漏发了中间那份），插件明确拒绝并说清从哪一份重来，绝不猜着合。

## 日常来回搬（两台电脑）

假设笔记本 A 和台式机 B 要轮流用同一份笔记。

### 第一次：A → B（完整副本）

1. **A 机**：`导出同步包…` → 勾「完整副本」→ 导出；
2. 把生成的 `.lsave` 拷到 B 机；
3. **B 机**：把文件拖到 Obsidian 窗口上（或在 `打开同步包并应用…` 里选它）→ 看报告 → 点「应用」。

B 机第一次装机时仓库通常是空的，没什么可动。已经有内容时，先看一眼报告里
「删除 N 个」那一行：完整副本是镜像，B 机里包里没有的文件会挪进回收目录。

### 之后：日常来回搬（更新包）

1. **A 机**：`导出同步包…`，只勾「更新包」；或者点左侧栏第一个图标「立即同步」
   （导出、推拉、收包一起做）。
2. 拷到 B 机，打开并应用。B 机没动过的话，报告会显示同步程度 100%。
3. B 机把自己这半也导出来发回给 A，A 应用。这样 A 才拿得到 B 那边的改动。

### 为什么要来回两趟

每台机器手上只有自己这半：A 那份更新包里没有 B 改过的东西，反之亦然。
两边各导一次、互相应用一次，两个仓库才收敛。

两边的基准始终是同一份完整副本。B 应用完，基准没变，它再导出的更新包还是“从这份完整副本到最新”，
A 站在同一份上直接收得下。B 那一趟不用手动准备：应用完插件只是记一笔“你这边还有 N 个改动没发出去”，
下次导出更新包时自然一起带上，不会一应用就自动生成一个包，和对方来回套娃。

报告里那句「你这边还有 N 个改动是对方没有的」，就是要回传的东西。

### 两台都改过了怎么办

最常见的一轮是顺序做：两台都站在第 55 代那份完整副本上，A 改完导出发给 B（`55 → 56`），
B 收到后接着改，再导出发回给 A（`55 → 57`）。两趟之后两台都停在 57 上，内容一致、状态编号一样。
两份包的起点都是那份完整副本，更新包就是这么累积的。

如果 B 在收到 A 的包之前就已经改了自己的东西，应用 A 的包时，B 那边的改动会被严格同步挪进回收目录。
不过插件在动手之前已经把它们存成了一个包，也就是包列表里那份 `第 56 → 57 代`：
起点正是 A 的包送到的状态，内容只有 B 自己动过的文件。

- B 自己应用它，仓库就变成“A 的改动 ＋ B 的改动”；
- 把它发给 A 应用，A 那边同样凑齐，两台回到一致。

一个边界要说清：两台改到了同一个文件时，以你应用的那一版为准，另一版在回收目录里
（`<仓库>/.trash/locally-save/`），不会自动合。需要的话自己捞出来看一眼。

### 怎么确认两边内容一模一样：状态编号

每个包都带一个状态编号，也就是整个仓库内容的短指纹，空文件夹也算在里面。

- 每导出一个包，“导出完那一刻”的编号会写进包里，也记在更新记录里；
- 应用别人的包之后，本机会重新算一个自己的跟它比。一样就是「跟对方完全一致」，
  不一样会写明还差什么，多半是你这边还没发出去的改动。

打开命令「同步包更新记录…」，顶部一行是你现在的编号，下面每条记录也带着当时的编号。
两台机器记录里最后一条编号相同，就说明文件内容一致。

编号是“上次导出或应用那一刻”算的，之后又改了文件，要等下一次导出或应用才刷新，
所以那一行也写着它是什么时候算的。单个超过 64MB 或读不出内容的文件会如实标出
「其中 N 个没能校验内容」。

**编号对不上时会直接说差在哪**（0.16.2 起）：应用完整副本之后如果编号还差一点，
通知里会写「本机多 X 个文件 / 缺 Y 个 / Z 个内容不同 / 多、缺几个文件夹」，带上几个例子；
如果缺的那些里有被**本机排除规则**挡住的，还会单独点出来 ——
两台机器的排除规则（设置里的“不同步的文件”）不一致时，编号会永远对不上，
而文件其实都在，这种就得把两边的规则改成一样。细节记在 `debug.log` 里。

### 包被拒收时怎么办

更新包要求“起点正好是本机站的那份完整副本”。对不上时插件不猜着合，
猜着合的代价是本机一大批文件会被当成“对方删过它们”。它给出三条出路：

1. **让对方从你这份完整副本重导**。应用对话框里有个「复制指纹发给对方」按钮，
   把你这边的基准指纹发过去，对方导出时把设置里「更新包」→「从哪个状态开始」选成那一项；
2. **让对方导一份完整副本**。完整清单自带基准，随时能接，但它会镜像覆盖本机内容；
3. **让对方导一份“从你那份完整副本到他那份完整副本”的差量包**，中间缺的那一段一次带过来。

有一种情况是白跑一趟：对方那份包要送到的地方正好就是你现在站的基准点，
说明包里没有你缺的内容，应用它一个文件都不会改。这时按第 1 条让对方重导就行。

**包的起点比你站的更新时，不算“拒收”**（0.16.1 起）：

> 用户的原话：“对面有 320 代的，112 代只是之前遗留，明显可以同步。”

包里写着“从第 320 代出发”，而你记的基准还是第 112 代 —— 这不是对不上，是**你落后了一段**，
而第 320 代那份完整包往往就躺在包目录的 `full/` 里。插件会：

- **能接上**（那份完整包在本机、且确实比你站的更靠后）→ 按它做三方合并：中间那一段补上、
  包里点名的改动落下，**你自己相对本机基准的改动留着**（不镜像、不进回收目录）。
  应用对话框会写一句“接上后续基准：……你自己相对本机基准的 N 处改动会留着”；
- **接不上**（包起点不比你的靠后 / 状态文件太老没有可比对的清单 / 「仅拉」方向）→
  拒收消息照旧，但多一个按钮 **「按第 N 代镜像对齐再应用」**：先把仓库整到那份完整副本上，
  再应用这个包（本机多出来的进回收目录，能捞回来）。

找不到那份完整包时才真的没法同步 —— 这时按上面三条出路办。

## 会不会弄丢东西

### 应用 = 严格同步（没有可选项）

包里点名的文件一律用包里的版本，包里点名删掉的照删，本地多出来的也挪进回收目录。
应用完仓库就是包送到的样子，两边的状态编号当场可比。

| 情况 | 会怎么处理 |
|---|---|
| 本地没动过、包里有 | 按包写入 |
| 两边都改过 | 用包里那一版覆盖，你改过的那份挪进回收目录 |
| 包里点名删掉的 | 照删（本地那份进回收目录） |
| 本地有、但包送到的状态里没有它 | 挪进回收目录（自己新建的、对方删过的都一样） |
| 包里有、本地这份只是旧版本 | 覆盖，不算冲突 |
| 对方改名 / 挪了位置 | 跟着改名，不重传内容 |
| 空文件夹 | 包里记着的补建出来；包送到的状态里没有的本地空目录清掉 |
| 本地是文件夹、包里是同名文件 | 挪进回收目录腾位置 |

为什么只有这一种方式？合并会有无穷多种结果：本机改的算谁的、独有的留不留、删除传不传播。
每一种都能配出一个“既不等于包、又不等于本机”的仓库，之后互发更新包时基准就对不上了。
严格同步保证“应用完两边一样”，也保证下一次的更新包一定接得上。

### 对不上时的兜底：强制回退到基准再应用

本机被改乱过（改名做了一半、被移动的文件删了、目标位置被占……）时，应用可能没法按原样算出来。
这时插件不再逐条猜“这一处改动该怎么合”，而是走一条确定的路：

1. 找到你站着的那份**完整副本**（按指纹认，不看文件名）；
2. 把它按严格同步应用一遍，仓库回到那个基准点；
3. 再把这份更新包重新算、重新应用一遍。

**基准包 + 更新包信息是全的，所以这条路一定落得下去。** 本机多出来的、改过的、被删掉的，
都进回收目录（`.trash/locally-save/`），随时能捞回来。应用完会核对结果，
对不上就自动走这一步；「仅拉」那台本来就更严格 —— 编号不一致也会走。
如果本机没有那份完整副本，插件会明确告诉你把它放回包目录（或让对方发一份），绝不硬合。

### 东西去哪儿了：回收目录

被覆盖、被删掉、被挪走的本地版本一律进 `<仓库>/.trash/locally-save/`，
那是仓库自带的回收站，带时间戳的子目录，随时能手动捞回来。没有“直接消失”这回事。

### 应用之前，先把你这一半存成一个包

严格同步会覆盖或挪走本地东西，所以动手之前插件会先把你这边“对方还没有的改动”存成一个更新包。
存不下就不动手，宁可这次不应用。那个包的起点是“这份包送到的状态”，所以：

- 你自己应用它，就等于在那个状态上把你的改动加回来；
- 发给对方应用（他也停在同一状态上），你的改动就叠到他的新版本上。

### 传输过程弄坏了？

包尾部记着整段内容的校验和。传输中弄坏的包会在应用前被拒绝，而不是写进仓库。
「应用前校验完整性」这个开关默认打开，大包会多花几秒。

## 自动功能

### 自动留包（默认关）

- 留哪种包在「自动留包」页：`留更新包`（推荐，几乎不额外花时间）或 `留完整包`
  （每次都把整个仓库重写一遍，大库会明显变慢）。两个开关各自独立。
- 什么时候留在同一页：启动后一次、定时同步（每 5 分钟到 3 小时；到点先推拉 git，再按开关留包）、
  保存后停顿若干秒。
- 自上次留包以来没有任何变化时，一个包都不写，只如实说一句。
- 第一次必须先导一次完整副本，更新包要有起点才算得出来。

### 收包与自动应用（按方向）

git 方向决定收到包怎么处理；没开 git 时由「自动应用收到的更新包」这个开关决定：

- **仅拉**：收到就应用，完整副本也收。连会删文件、删空文件夹、覆盖本地改动的也照做，
  目标是对面那一点，本机被覆盖或删掉的文件先进回收目录。这个方向不导出任何包；
- **双向**：收到先弹一句确认，确认后才应用；应用完把本机这边的改动导成更新包回传；
- **仅推**：不看收件箱，只发不收。

没开 git 时保持老边界：只自动应用“不会删东西、也不会覆盖你改过的内容”的更新包。
完整副本、要删东西的、两边都改过的一律只提示一句。

两种情况下都按基准收：起点正好是本机站的那份完整副本，同一份基准上每个来源只取最新那一份。
同一个包只处理一次，不会每 30 秒弹一遍。手动点「立即同步」时，上次停在“要你确认 / 失败了”
的包会再试一次，所以不会出现“两边代数差一截、点同步却只说已经最新”的情况。

### 状态栏

- 前半句是 git 推拉本身：`已推送 12:31`、`已拉取 12:31`、`已推拉 12:31`、
  `远程已是最新 12:31`、`同步失败 12:31`。这里不写“已同步”，因为推上去只说明远程有我的包，
  对方没拉、没应用之前，内容并不一定一样；
- 后半句是内容状态：`对方：一致`、`对方：不同步`、`对方：待上报`（我刚应用完，它还没报新状态）、
  `对方：还没上报`。多台时逐台计数，比如 `对方：2 台一致 · 1 台不同步`；
- 悬停看每台电脑的状态编号、第几代、基准、最后上报时间；点一下打开「各台电脑同步状态」窗口
  （命令面板里也有「查看各台电脑同步状态…」）；
- 跑长活时有进度：导出和应用是 `导出中 3/10`、`应用中 2/5`，git 推拉是 `同步中：拉取远程…` 这类阶段；
- 不想要这一格就在「通用」页关掉。

### 三个左侧栏图标

每个都能在设置里单独关掉。

| 图标 | 点一下 |
|---|---|
| 包裹加号 | 立即同步（导出包加 git 推拉；git 没开时只留包） |
| 包裹 | 导出同步包（打开导出对话框） |
| 开箱 | 打开同步包并应用（选包 → 看报告 → 再应用） |

### 拖放与双击

- 把 `.lsave` 拖到 Obsidian 窗口上，直接打开应用对话框并填好路径。只拦 `.lsave`，
  往笔记里拖图片、拖别的附件照旧。不想要这个行为可以在设置里关掉。
- 双击 `.lsave` 直接用 Obsidian 打开（仅 Windows，需要点一次「设置关联」）：
  设置 → 同步包 → 「用 Obsidian 直接打开」→ 设置关联。它会写一条当前用户的文件关联
  （`HKCU\Software\Classes`，不需要管理员权限，会覆盖你现有的 `.lsave` 关联；不想要了点「解除关联」）。
  关联是每台电脑各自设置的，换机器后要在那台机器上重新点一次；换过仓库文件夹名也要重设。

### `.lsave` 不是 Obsidian 能直接打开的格式

除非你按上面设过关联，否则不要用「用 Obsidian 打开」去双击它，那只会被当成一个未知文件塞进仓库。
正确用法是把它拖到 Obsidian 窗口上，或者用插件里的对话框选它。
万一包进了仓库也没关系：默认排除规则里有 `*.lsave`，它不会被打进下一个包。

## 命令

命令面板（`Ctrl+P`）里搜命令名。给命令设了快捷键的话，快捷键会一直有效，插件不会给命令改名。

| 命令 | 干什么 |
|---|---|
| 立即同步 | 导出包（有基准导更新包、没基准导完整副本），和 git 远程推拉，再应用拉到的包 |
| 预览这次会导出什么 | 列出会装进包里的文件、点名要删的清单、约多大。只算不写 |
| 导出同步包… | 打开导出对话框（完整副本与更新包两个独立勾选） |
| 打开同步包并应用… | 选包 → 先看报告 → 再点应用 |
| 管理同步包… | 列出所有包：应用、打开文件夹、复制路径、挪进回收站、彻底删除、清空回收站 |
| 同步包更新记录… | 像 git log 一样列出每次导出和应用 |
| 让对面和我一致（推上去） | 把本机改动导成更新包推上去；对面拉下来应用后和我一致 |
| 让我和对面一致（拉下来） | 把对方最新的包拉下来，严格对齐过去；本机改动先进回收目录 |
| 与 git 远程同步一次 | 只做推拉，不导出也不应用 |
| 查看各台电脑同步状态… | 每台的状态编号、第几代、基准、最后上报时间，标出一致、不同步、待上报 |
| 启用 / 停用插件 | 总开关（关掉后上面的入口都不干活，设置面板还能打开） |

## 管理已有的包

导出对话框、打开包对话框、命令 `管理同步包…` 都会列出同步包文件夹里的所有包，
按类型分组（更新包一组、完整副本一组、读不出内容的一组），组内从新到老。
每行写着认包要用的信息（第几代 → 第几代 · 状态编号 · 大小 · 时间），鼠标停在行上是完整路径。

选中一行可以：

- **应用… / 检查**：打开应用对话框，先出报告；
- **文件夹 / 复制路径**；
- **挪进回收站**：只是挪走，落在 `<同步包文件夹>/.lsave/bundles-trash/时间戳/`，能手动捞回来；
- **彻底删除**：真删，单独确认一次，删完捞不回来。

列表上方那一行是回收站汇总（还剩几个包、占多大、完整路径），点「清空回收站」把攒下的一起清掉。

`changes` 目录里的更新包默认都留着。删错一份，还站在它那份完整副本上的机器、或者另一台机器那一半改动就没了。
只有“同一份起点、同一种形态、也是这台机器导的”才会用新的那份取代旧的；
别的起点、别的形态、别的机器导的一律留着。

### 合并相邻的更新包

如果你在两份完整副本之间分段搬过（先导一份「F0 → F1」的差量包，再导一份「F1 → F2」），
`changes` 里就会串成一串。「管理同步包…」里的「合并相邻的更新包…」会把这样的一串并成一份「F0 → F2」：
起点还是段首那份完整副本，落点还是段末那一份，中间那几份不再单独留着。

- 正好停在中间那一份上的机器照样收得下合并后的这一份；
- 合并后装的是整段路上所有变过的文件，一份都不少；
- 原来那几份挪进回收站，不是真删，捞得回来；
- 同一个起点往外分过岔（有好几份不同落点的包）时不动。哪条是正路只有你清楚，插件不猜。

### 更新包可以指定「从哪个状态开始、到哪个状态为止」

两个下拉里列的都是你手里那几份完整副本。「从哪个状态开始」默认是你现在站的那一份，
「到哪个状态为止」默认是最新，也就是你现在的仓库。

- 对方还停在一份更老的完整副本上时，把「从哪个状态开始」选成对方报给你的那一份，
  他收到就是确定的更新，不必先要一份完整副本，也不必一段一段补；
- 反过来，把「到哪个状态为止」选成另一份完整副本，导出的就是一份“把对方从起点送到那一份”的差量包。
  内容取自那份包，不是你现在的仓库，所以这一趟不会改变你自己的状态。

认基准指纹，别只看“第几代”。世代号是每台机器各数各的节奏号，两边的“第 32 代”完全可能是两份不同的完整副本。
让对方打开「同步包更新记录…」，把顶上那行「基准：第 N 代 · 指纹 xxxx」念给你，照着那个指纹选。

## 设置说明

设置按“你要干什么”分成五页：

| 页 | 里面有什么 |
|---|---|
| 通用 | 启用插件、日志级别、左侧栏三个图标、状态栏 |
| 同步包 | 同步包文件夹、立即同步、手动导出、管理同步包、应用同步包、关联 / 说明 |
| Git 远程 | 启用 git 传输、远程地址、方向、状态与接入（检查 / 接入 / 连通性 / SSH）、同步动作 |
| 自动留包 | 触发时机（启动后一次 / 定时同步 / 保存后）、留哪种包（更新包 / 完整包） |
| 高级 | 不进包的文件、更新包起点 / 终点、攒大了提醒、自动应用、拖入即打开、应用前校验、git 分支 / 路径 |

几个容易忽略的：

- **同步包文件夹**：必填。留空时导出和应用按钮是灰的，并提示去填；
- **不进包的文件**：写法同 `.gitignore`（`目录/`、`*.tmp`、`a/**/*.md`），
  默认已排除配置目录、回收目录、`*.lsave` 与系统垃圾文件。想连插件与快捷键一起搬，把默认那行删掉即可；
- **应用前校验完整性**：读一遍整个包算校验和，确认传输没把文件弄坏，大包会多花几秒。

## 常见问题

**它会自动帮我同步吗？**
不会。留包（写文件）与应用（改仓库）默认都是关的，要你自己打开或点一下。

**包有多大？**
完整副本跟仓库差不多大。更新包只装“自它那份完整副本以来”变的那部分，刚换过基准时通常
几十 KB 到几 MB，之后随改动累积。攒大了插件会提醒你导一份新的完整副本换基准，
换完之后的更新包又从小的重新算起。想长期搬来搬去，日常只导更新包就行。

**手机上能用吗？**
不能，插件是桌面端专用，包要写到仓库之外。

**“删除同步包”是真删吗？**
默认是挪进回收站（`<同步包文件夹>/.lsave/bundles-trash/`），能手动捞回来。
真删只有两条路：行内的「彻底删除」（单独确认一次）与「清空回收站」。

**双击 `.lsave` 没反应？**
关联是每台电脑各自设置的，换机器后要在那台机器上重新点一次「设置关联」；
不想设关联就直接把包拖到 Obsidian 窗口上。

**应用完报告说“还差一点”？**
先看是不是“你这边还有 N 个改动”——那是你自己那一半，下次导出更新包会带上，不算错。
如果是包该送到的东西没到位（比如移动的源缺了），插件会**自动强制回退到基准再应用一遍**，
把该有的内容从基准完整副本补齐，应用完与包里那一点严格对齐；本机原来的版本都进了回收目录。
连回退都没成功时，报告里会写清原因（最常见：那份完整副本不在包目录里，把它放回来即可）。

**回退到某一份老完整副本之后，为什么又冒出一个包？**
「仅拉」那台已经拦死了：这个方向一个包都不写（连“应用前先存我这一半”都不做）。
其他方向回退时如果本机还有对方没有的东西，应用前的存包是有意为之 —— 那是你这一半的去处。

**应用了完整副本，但世代和编号还是没变到那一代？**
说明这一趟没落准，有文件没写成，或者有文件夹删不掉。插件不会把基准换过去，
报告里会写「没落到这份基准」，并列出失败的文件和删不掉的文件夹。
最常见的是文件夹里只有 `desktop.ini`、`Thumbs.db`、`*.lsave` 这种不参与同步的东西。
这种目录现在不算内容，重新应用一次就好。如果报告里列了失败的文件，先处理它（占用、权限、路径太长），再应用一次。

**只拉那台误改了文件，会怎样？**
只拉不推的规则是“和对面严格相等”。应用更新包时，包里没点名的本地改动会从基准完整副本恢复，
旧版本进回收目录，不会被当成“我这一半”留着。前提是那台机器还留着基准完整副本；
没有就先让它应用一份完整副本。若它自己导过完整副本、基准已经错位，
让对方从你这份基准重导一份更新包，或者直接导一份完整副本；应用完两边就回到同一份基准上。

**能只应用包里的某几个文件吗？**
不能。应用是整包语义（严格同步），为的是保证应用完两边内容一致、下一次的更新包接得上。
只想看某个文件在不在包里，可以展开报告里的文件清单。

**状态文件和插件配置在哪？**
插件的配置在插件目录里（通常是 `<仓库>/.obsidian/plugins/locally-save/`）。
`data.json` 是设置，`sync-state.json` 是基准、世代、更新记录与状态编号。
删掉 `sync-state.json` 等于“当作第一次”，不会动仓库里的文件，
但下次导更新包会要求先立基准（导一份，或应用别人一份完整副本）。

**同步失败看不出原因？**（0.15.9 起）
插件目录里会有 `debug.log`（JSONL，一行一条，到 512KB 轮转成 `debug.log.1`）。
平时只在出错/关键步骤才写，重点是这几条：

- `plugin.loaded` / `commands.registered`：插件起来并注册完命令；
- `command.run` / `command.error`：命令到底跑没跑、抛了什么；
- `sync.start` / `sync.skip`：同步开始与早退原因（`inactive` / `no-bundle-dir` / `busy`，busy 带三个忙标记）；
- `incoming.failed`：收包失败，带包头部坐标（基准 / 落点 / 状态编号）和 stack；
- `incoming.confirm.deferred`：窗口不在前台，确认框没弹（记 `needs-review`，手动同步会再问）；
- `apply.restore-needed`：严格镜像要恢复本机改动但找不到基准完整副本，带涉及路径。

收包失败的原因同时写进 `sync-state.json` 的 `incoming[].error`（截断 500 字）；
跟别人对表时，最近一次失败也会写进货架 `.lsave-peers/<copyId>.json` 的 `lastError`，
对面拉一次就能看到，不用手动发日志。

日志写不出来时不会再静默：控制台里会有一行 `[locally-save] debug.log 写入失败`。
设置里可以关掉「调试日志」（默认开）。

## 已知限制

- 只支持桌面端：读写仓库之外的文件必须走文件系统；
- 判据是「大小 + 修改时间」，修改时间带 2 秒容差（FAT/exFAT 只精确到 2 秒）。
  同一个文件在 2 秒内被改成同样长度，这一轮可能看不出来。想确认“两边内容一不一样”，看状态编号，
  那是按内容指纹算的；
- 排除规则挡住的东西不进包：默认是配置目录、`.trash/`、`*.lsave` 与系统垃圾文件；
- 包带来的改名是文件系统层面的，仓库里指向它的链接不会跟着更新（Obsidian 只跟踪应用内的改名）；
- 只装着被排除文件的目录不算内容：里面没有一个可见文件或子目录（只有 `*.lsave`、`desktop.ini` 这类），
  但又不是真正空的时候，它不参与“两边一不一样”的判断，插件也不会去动它，`rmdir` 本来也删不掉。
  真正空的目录（一个文件都没有）仍然算内容，照常同步；
- 打开同步包文件夹依赖系统文件管理器，拿不到时会弹一条含路径的通知让你手动复制；
- 打开同步包对话框时只会把 Obsidian 叫到前台，不会动你的窗口大小与位置；
- 接收端默认要手动点一下：开 git 时按方向走（仅拉直接收、双向确认后收）；
  没开 git 时打开「自动应用收到的更新包」（见上面那节）。

## 隐私

不开 git 传输时，这个插件不发起任何网络请求。没有遥测，没有账号，不上传任何东西。
开了 git 也只是跑你装的 `git` 跟你的远程通信，凭据留在系统 git 里。

它碰的东西只有三处：

- **仓库之外的文件**：这正是它的功能。包要写到仓库外，被替换的文件要挪进回收目录，
  所以它用 Node 的文件系统读写。它只会碰你指定的同步包文件夹、仓库本身，
  以及仓库里的 `.trash/locally-save` 回收目录；
- **系统命令**：只有可选项才用。「把 .lsave 关联到 Obsidian」按钮（仅 Windows，跑 `reg.exe`
  写当前用户的文件关联，不要管理员权限）、git 传输（跑你装的 `git`）、SSH 设置（跑
  `ssh-keygen` / `ssh`，装了 GitHub CLI 才会用 `gh`）。不点对应按钮或不开 git 就不会执行；
- **剪贴板**：只有「复制路径」「复制指纹发给对方」会往里写一句话，从不读剪贴板。

所有会改文件的功能默认都是关的。只有你明确选了「仅拉」方向时，收到包才会不弹窗直接应用
（本机被覆盖或删掉的文件进回收目录，捞得回来）。
