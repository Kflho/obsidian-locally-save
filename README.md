# Locally Save

> Obsidian desktop plugin (interface in Chinese): packs your vault — or the changes since the last
> full copy — into a **single transferable file** (`.lsave`) to carry on a USB drive or cloud folder,
> and applies it on the other machine. No network calls at all.

把仓库（或自上次完整副本以来的改动）打包成**单个 `.lsave` 文件**，用 U 盘 / 网盘 / 聊天软件
搬到另一台机器上应用。**完全不联网**：没有账号、没有服务器、不做连续同步。

**它就干一件事：离线单文件搬运**（外加一个还原点）。想要"两台机器通过一个共用目录
（网盘 / NAS / U 盘）一直自动同步"，那不是这个插件要做的事 —— 用 Remotely Save +
WebDAV / 坚果云这类走云的方案，它们在连续同步这件事上更成熟。

## English overview

**Locally Save** is a desktop-only Obsidian plugin (the interface is in Chinese) that moves a vault
between machines **without any network access**: it packs the vault — or just the changes since the
last full copy — into a single `.lsave` file that you carry on a USB drive, a cloud folder, or a chat
app, and applies it on the other machine.

- **Full copy**: the whole vault. It is the anchor for every later incremental bundle, and your
  restore point. Applying it is a **mirror** — no merging: files the bundle does not contain are
  moved to the trash folder, locally modified files are replaced by the bundle's version (the old
  ones also go to the trash). After applying, the vault *is* that bundle.
- **Changes bundle**: **one link in the anchor chain** — it carries only what changed since the
  previous anchor point, and applying it lands a new anchor point on the receiving side. It is only
  accepted when the receiving machine stands on the **exact same baseline** (equal baseline
  fingerprint); otherwise it is rejected with concrete next steps (re-export against your
  fingerprint, send the missing links in order, or send a full copy instead). Merging across
  different baselines would delete a large part of the receiving vault, so this check is hard,
  not a warning.
- **Applying is always a strict sync** (no mode to choose): files listed in the bundle win
  (your version goes to the trash), deletions listed in the bundle are performed, and local files
  the bundle's target state does not contain are moved to the trash too — after applying, the vault
  equals the bundle's state and both sides report the same content state id. Your own pending
  changes are packed into a changes bundle first (if that cannot be written, nothing is touched).
- Each bundle carries a checksum of its payload, a lineage/generation number, a baseline
  fingerprint ("are we continuing from the same full copy?") and a content **state id**
  ("are the two sides actually identical?"). A bundle that got corrupted in transit is rejected
  instead of being written into your vault.
- **Open is read-only**: selecting a bundle first computes a full report (what will be added,
  overwritten, skipped, deleted); nothing is written until you press Apply.
- **A restore point in one click**: tick *full copy* in the export dialog and the whole vault is
  written as a single bundle; your baseline point moves onto it, and the vault itself is untouched.
  Any machine that fell behind can jump straight onto it (the full copy doubles as a backup).
- **Automatic modes** (both off by default): auto-keep a changes bundle on a schedule / after edits,
  and auto-apply an incoming changes bundle — the latter only when it would not delete or overwrite
  anything you already have.
- **Not** a continuous sync tool. If you want two machines to stay in sync through a shared folder
  (WebDAV, NAS, cloud drive), use a cloud-based plugin such as Remotely Save; this plugin
  deliberately dropped that mode in 0.8.0 (see the section below).

### Install

1. Download `main.js`, `manifest.json` and `styles.css` from
   [Releases](https://github.com/Kflho/obsidian-locally-save/releases).
2. Put them into `<vault>/.obsidian/plugins/locally-save/`.
3. Enable the plugin under **Settings → Community plugins**.

Requires Obsidian 1.7+ on desktop (`isDesktopOnly: true`) — bundles live outside the vault, and
Obsidian's vault API cannot reach outside it, so the plugin uses Node's filesystem.

### Typical use

1. Machine A: **Settings → Locally Save → 同步包** → *Export bundle…* → tick **full copy**.
2. Carry the `.lsave` file to machine B and **drop it onto the Obsidian window**; check the report,
   then apply. This *mirrors* A's vault onto B (B's own files go to B's trash folder).
3. From then on, only export/apply **changes bundles** — small files, newest one is always enough.
4. Set a **bundle folder** first (required): that is where bundles are written, and where the
   incoming-bundle watcher looks.

### Privacy and permissions

- **No network requests at all.** No telemetry, no account, no server. The only things it reads and
  writes are your vault, the bundle folder you configure, and its own state file inside the plugin
  directory.
- **Filesystem access outside the vault** is the core feature (that is what `isDesktopOnly` is for):
  it copies files to/from the bundle folder you pick, and moves deleted files into a trash folder.
- **Shell execution**: only one feature uses it — the optional *"associate `.lsave` with Obsidian"*
  button (Windows only), which writes a per-user file association under `HKCU\Software\Classes` by
  running `reg.exe`. It never runs unless you click that button.
- **Clipboard**: the *"copy path"* button writes a file path to the system clipboard; nothing is
  ever read from it.
- All file-modifying actions default to **off** and are confirmed in a dialog before they run.

The rest of this document is in Chinese (the plugin's UI language).

## 安装

**手动安装**（当前没上架社区插件市场）：

1. 到 [Releases](https://github.com/Kflho/obsidian-locally-save/releases) 下载最新一版的
   `main.js`、`manifest.json`、`styles.css`
2. 放进 `<仓库>/.obsidian/plugins/locally-save/`（没有这个目录就新建）
3. 在 Obsidian 里 **设置 → 第三方插件 → 已安装插件** 里把它打开

插件是**桌面端专用**（`isDesktopOnly: true`）—— 包要写到仓库之外的文件夹，
Obsidian 的 vault API 出不了库，只能用 Node 的文件系统。

从源码装也可以：`npm install && npm run build`，`deploy.mjs` 会顺手把产物同步到
`OBSIDIAN_PLUGIN_DIR`（默认取环境变量，没设就跳过）。

## 为什么

**定位：不联网的单文件搬运 + 还原点。** 它解决的是"这台机器的仓库怎么整份或增量地搬到
另一台机器"，不是"两台机器怎么一直保持一致"。两种包分工明确：

- **完整副本**：整个仓库。第一次给对方时用它；它同时是一个**基准点**与**还原点**；
- **更新包**：只装自上一个基准点以来变过的文件，也就是**基准链条上的一环**。日常来回搬只用它，
  通常几十 KB 到几 MB；对方站在那一点上就能直接收下。

> **基准链条（0.11 起）**：一个**基准点**就是"一份确定的内容"——完整副本是一个点，
> **每份被应用的更新包**也落出一个新点。点与点之间是严格镜像（包里点名什么就是什么），
> 所以链条上每个节点的内容都是确定的：**不必猜着合，也就不会冲突**。
> 基准点**自己往前走**（导出 / 应用都会前进），所以没有"手动换基准"这回事（那个按钮 0.11 删了）；
> 链条中间断了会**明确拒绝**并说清从哪个基准点重来，绝不硬合。

包这一条线自带一套对账的家伙：整段负载的**校验和**（传输弄坏了会被拒绝，而不是写进仓库）、
**基准指纹**（两边是不是接着同一份完整副本）、**世代号**，以及"两边内容一不一样"的
**状态编号**。这几样在"两个文件夹互相同步"的做法里很难做扎实 —— 那边只能靠
"大小 + 修改时间"猜，出了分歧也说不清是谁改的。

**为什么不做"共用目录自动同步"**：那是另一类问题（谁先写、谁后写、断了怎么办、
目录被别的程序动过怎么办），走云插件（Remotely Save + WebDAV / 坚果云）比这里合适得多。
0.8.0 之前本插件确实还有第二条通道（把仓库同步到一个本地文件夹），已经连同它的引擎
一起删掉 —— 见下一节。

## 0.8.0：砍掉了「同步到本地副本」

那条通道（把仓库同步到一个本地文件夹）整个删掉了，插件只剩**同步包**一条线。
删掉的东西：`src/sync/runner.ts`（同步调度）、`src/sync/execute.ts`、`src/ui/sync-modal.ts`
（同步预览窗口）、设置里的 **`targetDir`（目标文件夹）** 与 **`syncDirection`（同步方向）**，
以及状态文件里那份"每个目标的基准"。

**老用户升级后会发生什么**：

| 原来 | 现在 |
|---|---|
| 「目标文件夹」+「同步方向」两个设置项 | 没了。旧 `data.json` 里的值留着不读，不影响别的设置 |
| 包放在 `<目标文件夹>/.lsave/bundles`（那时「同步包文件夹」留空就跟着目标文件夹走） | **自动迁到同一个路径**：升级后「同步包文件夹」＝ `<旧目标文件夹>/.lsave/bundles`，包还在原处，不用重新找。自己填过包目录的照旧 |
| 「同步包文件夹」可以留空 | **必填**：留空时导出 / 应用按钮是灰的，并提示去填。包放哪儿由你说了算，插件不替你藏一个默认值 |
| 「同步删除」（本地删的副本也删） | 收窄成应用包时的一条：**包里点名的删除照删**（0.11 起应用只剩严格同步，"删不删多余文件"那个开关也一起没了） |
| 「删除前先备份」「两边都改了怎么办」 | **0.11 起都删了**：应用只剩严格同步 —— 本地被覆盖/挪走的一律进回收目录（必然备份），"两边都改了"等于"用包里那一版覆盖" |
| 「自动同步」的三个设置项（启动后一次 / 定时 / 保存后） | **字段名一个都没变**，语义变成"**自动留包的时机**"（启动后留包一次 / 定时留包 / 保存后留包） |
| 命令 `sync-now`（立即同步） | 还在，改叫 **「立即留包」**：按两个「自动留包」开关立即留一次；都没开时提示去设置里选一种 |
| 命令 `sync-preview`（预览同步） | 还在，改叫 **「预览：这次会留什么包」**：打开导出预览（只算不写） |
| 命令 `upload-to-copy` / `download-from-copy` | **ID 还注册着**，但只弹一句指路通知（告诉你去用「导出同步包…」/「打开同步包并应用…」）。直接删掉的话快捷键会静默失效，所以留一版，**下一版删** |
| 应用对话框里的「应用后顺便同步到本地副本」 | 没了 —— 包是唯一的搬运格式，没有"顺便同步"这回事 |

**想要连续同步该用什么**：Remotely Save + WebDAV / 坚果云这类走云的方案（或者系统自带的
文件夹同步工具）。本插件守住的是**离线搬运 + 还原点**：包能校验、能对账、能当还原点，
"一直保持一致"不是它要解决的问题。

> 为什么砍：两条通道各自实现了一遍"基准 / 冲突 / 回收 / 删除传播"，行为已经分叉 ——
> 文件夹副本那边只认"大小 + 修改时间"、没有状态编号、也不知道副本是不是被别的机器或
> 别的程序写过；而共用目录那种用法交给走云插件更合适。分析与实测留在 `docs/` 里。

## 功能

### 同步包（`.lsave`）

把仓库打包成**单个文件**，拷到另一台机器上用插件打开：

- **完整副本**：整个仓库，到哪台机器都能整份恢复；也是更新包的**基准**
- **更新包**：**基准链条上的一环** —— 只装自上一个基准点以来变过的文件（含一份删除清单），
  应用它就在这边落出一个新基准点。链条上的每一环都从上一环的落点往外长，
  所以"我该收哪一环"是确定的（起点要跟本机站的基准点完全相等，见下面「起点对不上会被拒收」）
- **导出预览**：命令「预览：这次会留什么包」先算一遍给你看 —— 这次会装进包里的文件、
  点名要删的清单、估算大小。**只算不写**，与真正导出共用同一套挑选逻辑，
  不会出现"预览说一套、实际导另一套"；没有基准（还没导过完整副本）时不报错，只说明原因
- **打开即报告**：选包之后先算一遍再让你决定 —— 同步程度百分之多少、
  会新增/覆盖/跳过/删除各几个、会不会动东西、有没有漏包。**打开包这一步不写任何文件**
- **应用完整副本 ＝ 镜像**（不合并）：包里没有的本地文件（连你自己新建的）挪进回收目录，
  本机改过的被包里那一版覆盖 —— 应用完这个仓库**就是那个包**。镜像让两边的基准成为同一份东西，
  之后互发更新包才不会"基准对不上"
- **更新包必须与本机同一份基准**，否则**拒收**并说清两条出路（让对方按你的指纹重导 /
  让对方导一份完整副本）。没有共同基准硬合 = 一大片本机文件会被当成"对方删过它"删掉，
  所以这条是硬的，不是警告
- **应用方式没得选**：包里点名的文件一律用包里的版本（你改的那份挪进回收目录）、
  点名的删除照删、**本地多出来的也挪进回收目录** —— 应用完这个仓库就是包送到的状态，
  两边的状态编号当场可比。动手前还会先把你这边的改动存成一个更新包（存不下就不动手）
- **想留一个还原点**：`导出同步包…` 勾上「完整副本」—— 整个仓库写成一份包放进 `full/`，
  你也会站到它上面（仓库文件一个都不动）。平时不用管基准点（它自己前进）；
  落后很多的机器直接应用这份完整副本就能一步跳上来，不必一环一环补
- **文件与文件夹都报**：包里几个文件夹、本地几个、两边都有几个、要补建/删掉/留着各几个 ——
  只报文件的话，你永远不知道目录这边差多少
- **校验**：包尾部记着整段负载的 sha256，传输过程弄坏了会被拒绝（而不是写进仓库）
- **`changes` 里的环默认一个都不删**：更新包是链条上的一环，删了它，还站在那一环起点的机器
  就接不上来了。只有**完整副本**能取代它们（它是完整清单，站在老环上的机器直接应用它就行），
  以及"同一环重导了一遍"那种。
  留着没删的会说明原因（别的机器导的包 / 世代不比新包小 / 链条上的另一环）：
  提示里会写清楚，不需要就去「管理同步包…」里手动挪走
- **两种一起勾时，先导完整副本、后导更新包**：完整副本一写完，它自己就是最新的**基准点**，
  这时的更新包按它算**必然是空的** —— 那就不写空包，只在结果里说一句
  （"更新包是空的：刚留的完整副本已含全部内容"）。
  想要一个"小文件传出去"就**只勾更新包**，别同时勾完整副本
- **更新记录（像 git log）**：命令面板里的 `同步包更新记录…`（「管理同步包…」里也有按钮）
  按时间倒序列出每次 **导出 / 应用**：方向、类型、包里几个文件（含几个删除）、世代
  （`第 N → M 代`，完整副本标"立基准"）、包名、以及**来自哪个仓库**。
  顶部先写清"我现在站在哪儿"：基准是第几代、指纹、**具体是哪份完整副本**，
  以及这之后收发过几个更新包 —— 两台机器来回搬时，一眼看得出谁还欠谁一个包
- **包文件名一眼看得懂**：仓库名 + **完整 / 更新** + **第几代到第几代** + **目标状态**：

  ```
  我的笔记-完整-36代-状态3f9a2c1d4e5f6a7b-e34cc7.lsave
  我的笔记-更新-32代到37代-状态3f9a2c1d4e5f6a7b-5f4807.lsave
  ```

  完整包写的是它**立的那一代**；更新包写「起点代到终点代」（终点＝对方应用完到达的世代）；
  那个**状态编号就是"对方应用完应该落在哪个状态"**（跟「更新记录」里那条对得上）。
  末尾 6 位是包 ID：同一秒里连导两个也不会互相覆盖；不带时间戳 —— 什么时候导的，
  列表里每行都有修改时间（名字只用来一眼认出"这是哪一份"）。
  老包的名字还是 `-full-` / `-changes-`：**两种写法都认**，照旧分组显示
- **包管理**：导出弹窗、导入弹窗、以及命令面板里的 `管理同步包…` 都会列出包文件夹里的所有包，
  而且**按类型分组**：更新包一组、完整副本一组、读不出头部的一组 —— **组内从新到老**，
  组标题吸顶，滚动时也知道自己在看哪一类。每行只写**认包要用的判据**
  （第几代 → 第几代 · 状态编号 · 大小 · 时间；鼠标停在这行上是完整路径），
  选中一行可以 **应用…** / **打开所在文件夹** / **复制路径** / **挪进回收站** / **彻底删除**：
  - 「挪进回收站」只是挪走 —— 落脚在**同步包文件夹**下的 `.lsave/bundles-trash/时间戳/`
    （跟 `bundles` 平级，不会再套一层 `.lsave`），想反悔可以手动捞回来；
  - 「彻底删除」是**真删**，单独确认一次，删完捞不回来（只想扔掉某一个没用的包时用它，
    不必为它清空整个回收站）。
  列表**上方**那一行是回收站汇总：还剩几个包、占多大，还会把完整路径写出来 ——
  点「清空回收站」把攒下的一起清掉。
  读不出头部的 `.lsave` 也会列出来、单列一组 —— 看得见才删得掉
- **想留一个还原点**：`导出同步包…` 勾上「完整副本」—— 整个仓库写成一份包，你也会站到它上面
  （仓库文件一个都不动）。0.11 起**基准点自己往前走**，所以没有"手动换基准"这回事：
  「管理同步包」里原来那个「立新基准…」按钮、「更新包超过多大就提醒换基准」那个设置，
  都跟着链条模型删掉了（每份更新包只装自上一个基准点以来的新改动，不存在"越攒越大"）
- **包放在哪**：「同步包文件夹」是必填项，完整包与更新包分别放在它的 `full` 与 `changes`
  子目录里。这个目录不参与任何扫描 —— 包不是笔记，不会被打进另一个包

### 自动留包

「自动留包」页只管**时机**（启动后一次 / 定时 / 保存后静置若干秒，默认全关），
留哪种包看「同步包」页里两个**各自独立**的开关（默认也都关）：

- **留更新包** —— 每次自动留包把"自上一个基准点以来的新改动"导成一环放进 `changes/`，几乎不额外花时间
- **留完整包** —— 每次都把整个仓库重写一遍放进 `full/`，几百 MB 的库会明显变慢，
  只在"随时要给别人一份完整副本"时打开
- 两个都开时**先留完整包、后留更新包**：完整包刚把整个仓库装走，更新包按它算必然是空的 ——
  那就不写空包，只说一句
- **自上次留包以来没有任何变化时，一个包都不写**（完整包一写就是整库重写），只如实说一句
- **第一次必须先导一次完整副本** —— 更新包要有**起点**才导得出来；没有基准点时预览与导出
  都会说明原因，而不是导出一个半成品
- 两个开关都关着时，「立即留包」与三个自动触发**什么都不做**（不弹错）；
  手动点「立即留包」会提示先去设置里选一种
- 更新包**不会越攒越大**了：每同步一轮就落出一个新基准点，下一环只装这之后的新改动

整库只扫一次、两个包共用同一份清单 —— 所以自动留包几乎不额外花时间，
唯一可能慢的是"留完整包"本身（它每次都要把整个仓库写进一个文件）。

### 自动应用收到的包

有人把包放进「同步包文件夹」之后，不用再手点那一下：打开「同步包」页里的
**「自动应用收到的更新包」**（默认关），插件每 30 秒看一眼那个文件夹。
安全边界是硬的：

- **更新包只在完全不会动到本地已有的东西时才自己应用** —— 不删文件、不删空文件夹、
  不覆盖你改过的内容、不产生冲突副本。要删东西或两边都改过时，只提示一句
  （"收到更新包 xxx，但它会删 3 个文件 —— 没有自动应用"），让你用「打开同步包并应用…」自己看；
- **完整副本从来不自动应用**（它可能删掉你本机独有的文件），也只提示一句；
- **按链条顺序接**：从本机站的那一点往后，找"起点正好是它"的那一环应用，应用完再看下一环 ——
  缺环就停在那儿等它到齐（那一环**不记账、不动它**，缺的到了自动接上，同一份只提示一次）；
- 我自己的导出、已经处理过的包、读不出头部的文件一律跳过；
- 每个包只处理一次（状态文件里记着），不会每 30 秒弹一遍；
- 应用完这一拍**不会紧接着留包** —— 那等于立刻生成"回礼包"，两边容易来回搬运。
  你这边确实还有对方没有的改动时，它会在通知里写着"还有 N 个改动没发出去"，
  等你下次留包时一起带上。

### 状态栏

- 平时显示**更新记录里最后一条**：`上次留包 <时间> · 更新包 N 个文件（含 M 个删除）`
  （上次是应用包就写"上次应用"）；还没有任何记录时写「尚未留包」。
  重启 Obsidian 之后从状态文件读回来，不会丢

## 怎么用同步包（跨机器搬运）

假设要把 A 机（笔记本）的仓库搬到 B 机（台式机），或者让两台机器来回搬。

### 第一次：A → B，用**完整副本**

1. **A 机**：设置 → Locally Save → **同步包** → 滚到「手动导出」→ 点 **导出同步包…**
   （或者 `Ctrl+P` 输入 `导出同步包`）
   - 勾上 **导出完整副本**（第一次必须导完整副本：更新包要以它为基准）
   - 「导出更新包」与「导出完整副本」是**两个独立勾选**，可以都要。
     两个都勾时**先导完整副本、后导更新包** —— 完整副本刚把整个仓库装走，这时的更新包
     必然是空的，所以**不会生成空包**，结果里会写一句为什么
     （想要"一个小文件传出去"，就只勾更新包）
   - 对话框里会写明 **会写到：** 哪个目录（完整副本 → `<同步包文件夹>/full`，
     更新包 → `<同步包文件夹>/changes`）；在这里改路径只影响这一次导出，
     可以填个方便拷走的地方（比如 U 盘）
   - **导出完这个窗口不会自动关掉**：底下那行就是结果（几个文件、多大、从第几代到第几代），
     刚生成的那个包已经在列表里选中了 —— 接着就能 **文件夹 / 复制路径 / 挪进回收站 /
     彻底删除**，或者改改参数再导一份
   - 底下还列着这个文件夹里**已有的包**（更新包一组、完整副本一组，组内从新到老）：
     选中一行就能 **应用… / 文件夹 / 复制路径 / 挪进回收站 / 彻底删除**
2. 把生成的 `.lsave` 文件拷到 B 机（U 盘、网盘、聊天软件，怎么拷都行）
3. **B 机**：**把那个 `.lsave` 直接拖到 Obsidian 窗口上**（会自动打开对话框并填好路径），
   或者 设置 → Locally Save → **同步包** →「应用同步包」→ 点 **打开同步包并应用…**
   - 从列表里选（按类型分组，更新包与完整副本各一组、组内从新到老），也可以直接粘完整路径
   - **先看报告**：同步程度、新增/覆盖/删除各几个、走哪条通道、有没有漏包
   - 确认无误，再点 **应用**
   - ⚠ **应用完整副本是"镜像"**：B 机里包里没有的文件会挪进回收目录（`仓库/.trash/locally-save`），
     B 机改过的会被包里那一版覆盖（旧的也进回收目录）。**B 机第一次装机时它通常是空的**，
     所以没什么可动的；已经有内容时先看一眼报告里"删除 N 个"那一行

> 拖放只拦 `.lsave`，别的文件一概放行 —— 往笔记里拖图片、拖别的附件照旧。
> 不想要这个行为可以在设置里关掉（「拖入 .lsave 即打开应用对话框」）。

### 之后：日常来回搬，用**更新包**

1. A 机留一次包 —— 开了「留更新包」（外加「自动留包」页里的某个时机）的话，包已经躺在
   `changes/` 目录里了；没开就手动导一次（选「导出更新包」），或者点一下左侧栏第一个图标
2. 拷到 B 机 → 打开并应用。B 机没动过的话，报告会显示同步程度 100%
   - 更新包**必须站在同一个基准点上**才收：B 机没走到那一环的起点时会被**拒收**，
     报告里会写清本机站在哪一点、要怎么办（让对方从本机这一点重导 / 把中间缺的几环补上 / 导完整副本）。
     这是有意的 —— 起点对不上就硬合，会删掉一大批 B 机的文件
3. **B 机把自己这半也导出来发回去**：应用完**不会**立刻自动生成一个包（那样两边会互相套娃），
   只在通知、报告和更新记录里记一笔"你这边还有 N 个改动没发出去"。
   等你下次导出更新包（手动，或开了「留更新包」就自动）时，它自然一起带上 ——
   那一环是"从 B 刚落到的那一点往外延伸"的，所以 A 正站在它的起点上，收得下。
   把它拷回 A 机应用 —— 这时 A 才拿得到 B 那边的改动

> **为什么要来回两趟**：**每台机器手上只有自己这半**（A 那一环里没有 B 改过的东西，反之亦然）。
> 两边各导一次、互相应用一次，两个仓库才收敛。好在**基准点会跟着一起往前走**：
> B 应用完就站到 A 那一点上，它导出的那一环正好接在那儿，A 收得下。
> 不用怕漏发：报告里会一直写着「你这边还有 N 个改动（M 个删除）是对方没有的」，
> 那个数就是要回传的东西，下次导出更新包时一起走。
>
> 前提是这台机器**站在一个基准点上**（更新包要有起点才导得出来）。

#### 两边是不是站在**同一个基准点**上，工具会替你对账

每份完整副本自带一个**基准指纹**（把它的清单排序后取短哈希），更新包会带上
"我从哪一点来"（`baselineHash`）与"我落到哪一点"（`targetBaselineHash`）—— 链条就是靠这两个字段
首尾相接认出来的。应用时一比，报告里直接写清楚：

- **一致** → 「✓ 基准一致」：接着应用是**确定的**；
- **不一致** → **接不上，不合并**：报告与通知里写明包从哪一点来、本机站在哪一点，
  并给出三条出路 —— 让对方从本机这一点重导 / 把中间缺的几环一起发过来按顺序应用 /
  让对方导一份完整副本（完整清单自带基准，随时能接）；
- **说不清**（包是旧版本导的、没记指纹）→ 同样拒收，理由同上；
- **完整副本** → 永远收（它自带完整清单，就是一份新基准），应用方式是镜像。

为什么不能只看世代号：两台机器各自 +1，**会碰号**；内容对不上时也看不出来 ——
"不确定更新状态"就是这么来的。指纹是内容的直接证据。

包列表里每行也会写明世代与状态编号（完整副本「第 N 代」、更新包「第 N → M 代」），
这样两台机器的 `full/`、`changes/` 目录一眼能对上号。

#### 两边**内容**到底一不一样，看「状态」编号

世代号只说明"接着谁往后数"，基准指纹只说明"祖先是同一份"—— **都不回答"现在是不是一样"**。
所以要看的是一行**状态编号**（整个仓库的内容指纹，跟基准指纹一样是短的十六进制）：

- 每导出一个包，**导出方导完那一刻**的编号会写进包里，也记在更新记录那一条上；
- 应用别人的包之后，这边**重新扫一遍仓库**算一个自己的，跟包里那个比：
  - **一样** → 通知与报告里写「✓ 跟对方完全一致（状态 3f9a2c1d）」；
  - **不一样** → 「状态 3f9a2c1d，跟对方导出时的 7b21a4e0 不一样」—— 差的就是你这边还没发出去的改动；
- 打开**更新记录**（命令「同步包更新记录…」）：顶部一行是你现在的编号，下面每条记录也带着当时的编号。
  **两台机器日志里最后一条编号相同 ＝ 文件内容一致**（空文件夹也算在里面）。

> 编号记的是"上次导出 / 应用那一刻"；之后又改了文件，要等下一次导出 / 应用才刷新 ——
> 所以那一行同时写着它是什么时候算的。读不到内容的文件（单个超过 64MB、读失败）会如实标出
> "其中 N 个没能校验内容" —— 那种情况下编号不是完全的内容指纹，界面会说明白。

### 应用时按什么规则处理：**只有一种 —— 严格同步**

包里点名的文件一律用包里的版本（你本地改过的那份先挪进回收目录）、包里点名删掉的照删、
**本地多出来的文件也挪进回收目录**。应用完**仓库 == 包送到的状态**，两边的状态编号当场可比。

| 情况 | 会怎么处理 |
|---|---|
| 本地没动过、包里有 | 按包写入 |
| 两边都改过 | 用包里那一版覆盖，你改过的那份挪进回收目录 |
| 包里点名删掉的 | 照删（本地那份进回收目录） |
| 本地有、但**包送到的状态**里没有它 | 挪进回收目录（严格同步下不留：自己新建的、对方删过的、那边压根没有的） |
| 包里有、本地这份只是旧副本 | 覆盖（不算冲突） |
| 对方改名 / 挪了位置 | 跟着改名，不重传内容 |
| 空文件夹 | 包里记着的补建出来；包里没有的本地空目录清掉 |
| 本地是文件夹、包里是同名文件 | 挪进回收目录腾位置 |

三条要紧的语义（每条都踩过坑，都写进测试了）：

- **完整副本与更新包走的是同一套**。完整副本代表"另一台机器此刻的完整样子"，包里没有的
  本地文件（连你自己新建的）一律挪进回收目录。合并会有无穷多种结果（本机改的算谁的、
  独有的留不留、删除传不传播），每一种都能配出一个"既不等于包、又不等于本机"的仓库 ——
  之后导出的更新包 `base` 就对不上，两台机器开始互相报"基准对不上"
- **更新包也敢镜像，是因为起点被卡死了**：它的起点必须与本机站的基准点**完全相等**
  （`checkAncestor`，见下一节），所以"包送到的状态"是确定的 ＝ 本机站的这一点 ＋ 条目 − 点名删除。
  "本地有、包里没有"在更新包里**什么也不代表**（它只装变过的文件），删除只认包里点名的清单
- **动手前先把你这一半存成一个更新包**（你有对方没有的改动时才存；存不下就**不动手**），
  被覆盖 / 挪走的本地版本再一律进回收目录（`仓库/.trash/locally-save/`，捞得回来）

> **0.11 起应用只有这一种语义。**「应用方式」那个下拉框没了：更新包以前那几档
> （按设置 / 以包为准 / 两边都留 / 以我为准）、对话框里「这次不执行包里的删除」那个勾、
> 以及「两边都改了怎么办」「包里删掉的文件，这边也删」「删除前先备份」三个设置项，
> 全部删掉 —— 那些档位合出来的状态既不等于包、又不等于本机，下一次导出的更新包 `base` 就对不上。
> 合并那条路（`strictness: 'normal'`）现在只有**自动收包**与**接链**在用：它们的边界是
> "只应用不会动到本地已有东西的包"，合并语义正好对上。想读旧档位长什么样，看 `git log`。

### 起点对不上的包会被拒收（接不上就不合）

三方比对全靠"共同祖先"：没有它，"本机改没改过"整个判不出来 —— 更新包只有变过的那部分，
起点不是本机站的这一点时，本机一大批文件会被当成"对方删过它"删掉。所以规矩定死，宁可拒收也不猜：

| 本机状态 | 完整副本 | 更新包 |
|---|---|---|
| 还没有基准点（第一次用） | ✓ 收下，应用完它就是你的基准点 | ✗ 拒收：没有起点，算都算不出来 |
| 站在同一个点上（指纹相等） | ✓ 收下（换基准点） | ✓ 收下 |
| 不是同一个点 | ✓ 收下（它自带完整清单，就是一个新基准点） | ✗ 拒收，并说清从哪个点重来 |
| 对不上、但**这个包要送到的正是我站的这一点** | — | ✓ 收下（应用它一个文件都不会改，报告会写明"白跑一趟"） |

拒收时给的**三条出路**：① **让对方从本机这个基准点重导**（报告里会写本机的指纹与第几代，
导出时把「更新包：从哪个状态」选成它）；② 让对方把**中间缺的那几环**一起发过来，按顺序应用；
③ 让对方导一份**完整副本**（完整清单自带基准，随时能接）。
旧版本导的包没记指纹，同样按"说不清"拒收。

### 想多留一个还原点：立一份新的完整副本

**基准点平时自己往前走**（导出 / 应用都会前进），所以"攒大了要清零"这件事已经不存在了 ——
每份更新包只装自上一个基准点以来的新改动。想**多留一个还原点**时：

1. **把本机现状写一份完整副本**：`导出同步包…` → 勾「**完整副本**」→ 导出。
   它按**现在的仓库**写一份新完整副本、并把你站的点换成它，这份包同时是一份备份。
   **仓库文件一个都不动**。（`管理同步包` 顶上那行写着"自基准点以来改了 N 个文件、删了 M 个"，
   那就是"下次更新包会装多少"。）
2. **拿别人的完整副本当自己的基准点**：在「打开同步包并应用…」里选那份包 ——
   走的是应用那条路（先出报告、再动手），也就是上面那条**镜像**规则

> **导一份"内容没动过"的完整副本不会让世代号虚增一代**（0.10.1 修的）：语义是"把已经掌握的内容固化成基准点"，
> 内容一代都没往前走，那这份完整副本就**还是当前这一代**，之后的更新包也从这一代往后数。
> 只有仓库**真有新改动**时，它才占一个新世代号。
>
> 这条很要紧：本机第 39 代、收到并应用了别人「39 → 46」的更新包之后，本机内容**就是第 46 代**。
> 这时再导一份完整副本若自称"第 47 代"，你导出的更新包会变成「46 → 47」——对面看着像凭空多一代，
> 应用完也停在 47 上，两边的"第几代"跟内容再也对不上。


### 双击 `.lsave` 直接用 Obsidian 打开

设置 → Locally Save → **同步包** →「用 Obsidian 直接打开」→ **设置关联**。
之后双击 `.lsave` 就会用 Obsidian 打开并**直接弹出应用对话框**。

为什么不能简单"用 Obsidian 打开"：把 `.lsave` 关联到 `Obsidian.exe "%1"` 是**通不了**的 ——
Obsidian 收到一个陌生路径只会当成未知文件，压根到不了插件。能到插件的通路只有 **URI 协议**，
所以关联要指向 `obsidian://locally-save?vault=<仓库名>&bundle=%1`（`%1` 由系统换成被双击的路径）。

两个坑（都踩过，写在代码注释里了）：

- **`vault=` 不能省**：插件属于某个 vault，Obsidian 得知道把 URI 交给哪个。
  少了它会直接弹 **`Vault not found. Unable to find a vault for the URL`**，压根到不了插件。
  链接里的仓库名就是**当前打开的仓库**，换 vault 或改过文件夹名后重新点一次「设置关联」即可
- **参数名不能叫 `path`**：Obsidian 对 URI 里的 `path` 有特殊处理（[官方文档](https://obsidian.md/help/uri)：
  "path 会覆盖 vault 与 file，并让应用去搜索哪个 vault 包含这个路径"）。
  我们的包在仓库外、不属于任何 vault —— 于是它找不到 vault，报同一个错。所以用的是自定义参数名 `bundle`

- 只写**当前用户**注册表（`HKCU\Software\Classes`），**不需要管理员权限**；
  点"设置关联"前会把要跑的命令**逐条列出来**
- 会覆盖你现有的 `.lsave` 关联；不想用了在同一处点 **解除关联**
- 链接形式也可以手工用（路径要 URL 编码）：
  `obsidian://locally-save?vault=我的仓库&bundle=D%3A%5C%E4%BC%A0%E8%BE%93%5Ca.lsave`
- 不带路径也行：`obsidian://locally-save?vault=我的仓库` 就是"打开应用对话框，让我自己选"
- **这台机器上双击没用？** 关联是**每台机器各自设置**的（注册表在本机），
  换机器后要在那台机器上重新点一次「设置关联」；在此之前用拖放或对话框选文件一样能用

### `.lsave` 不是 Obsidian 能打开的格式

同步包是插件自己的容器格式。**不要**用"用 Obsidian 打开"去双击它（除非你按上面设过关联）——
那样只会被当成一个未知文件塞进仓库。正确用法是**把包拖到 Obsidian 窗口上**，
或者用插件里的对话框选它。

- 插件读包**只看绝对路径**，跟你系统里 `.lsave` 关联到哪个程序**完全无关**
- 默认排除规则里有 `*.lsave`：万一包被拖进了仓库，它也不会被打进下一个包
  （确实想让包进包，把设置里「不进包的文件」中那行删掉即可）

### 几个要点

- **打开包那一步是只读的**：随便点、随便看，不会动你的文件；只有点「应用」才写盘
- **包里要求删、本地改过的文件不删**（删除必须过基准检查，没有例外）
- 提示「**基准接不上**」不用慌：**插件不会猜着合**，一手都不动。按报告里给的三条出路走 ——
  让对方从本机这个基准点重导 / 把中间缺的几环一起发过来 / 让对方导一份完整副本
- 自动留包的两个开关**各自独立**：只开「留更新包」最省（几十 KB 到几 MB）；
  「留完整包」每次都要重写整个仓库，几百 MB 的库会明显变慢
- 包丢了、传坏了都不影响仓库：**导出是只读的**，包损坏会在应用前被校验拦下
- **接收端要手动点一下**：包落地后得在 Obsidian 里打开并应用（拖进去、双击、或对话框选）——
  还没有"监听文件夹自动应用"这回事

设置面板里也有一个 **「看说明」** 按钮，写的就是上面这套流程。

## 设置面板

按"用户要干什么"分成四页（1.13+ 是可折叠的分页，旧版本平铺成小节）：

| 页 | 里面有什么 |
|---|---|
| **通用** | 启用插件 · 日志级别 |
| **同步包** | **包放在哪**（同步包文件夹 · 不进包的文件）· **自动留包**（留更新包 / 留完整包）· **更新包从哪个状态到哪个状态**（从哪个状态开始 / 到哪个状态为止）· **手动导出** · **管理** · **应用同步包**（自动应用收到的更新包 · 拖入 .lsave 即打开 · 应用前校验完整性）· **用 Obsidian 直接打开** |
| **自动留包** | 触发时机：启动后留包一次 · 定时留包 · 保存后留包 |
| **界面与交互** | 左侧栏三个图标 · 状态栏 |

几个容易忽略但很有用的：

- **同步包文件夹**：必填。留空时导出 / 应用按钮是灰的，并提示去填
- **不进包的文件**：写法同 `.gitignore`（`目录/`、`*.tmp`、`a/**/*.md`），
  默认排除配置目录、回收目录、`*.lsave` 与系统垃圾文件
- **应用前校验完整性**：把整个包读一遍算校验和，确认传输没把文件弄坏（大包会多花几秒）

> **0.11.0 删掉了「应用同步包时的默认处理」那一组三项**（两边都改了怎么办 /
> 包里删掉的文件这边也删 / 删除前先备份）：应用只剩"严格同步"一种语义 ——
> 包里的版本一律覆盖本地、点名的删除照删、被换掉的都进回收目录（必然备份），没有可配的地方。
> 旧 `data.json` 里的这几个值留着不读即可。

> **0.11.0 删掉了「更新包超过多大就提醒换基准」**：链条模型下每份更新包只装自上一个基准点
> 以来的新改动，不存在"越攒越大"，那个提醒也就没意义了（旧 `data.json` 里的值留着不读即可）。
>
> **0.8.0 删掉了两个设置项**（随那条被砍掉的通道一起删的，见前面那一节）：
> 迁移规则也写在那儿 —— 没填过包目录的会自动迁到老位置，包还在原处，不用重新找。

> **0.7.0 精简掉了 6 个设置项**：「加载时弹提示 + 提示文案」（没有信息量）、
> 「状态栏显示上次同步」（跟「显示同步状态」重复）、「打开包时最大化窗口」
> （插件不再动你的窗口，只把它叫到前台）、「导出后清掉被取代的旧更新包」
> （现在一律清理）、「记住内容指纹」（现在一律记住 —— 状态编号要用它）。
> 另外「保存后同步」的开关与秒数合成了一个下拉（这个下拉在 0.8.0 里改叫
> 「保存后留包」，语义也从"同步"收成"留包"，见前面那一节）。这些在 `data.json` 里的旧值会被忽略，
> 不影响其他设置；旧配置里"保存后同步"是关掉的话，升级后仍然是关的。

## 包是传输格式，不是工作目录

为什么不把 `.lsave` 当"另一个仓库"直接在上面编辑、也不让它当连续同步的落点：
容器头部记的是每个文件在负载里的**绝对偏移**，任何一个文件大小一变，后面的偏移全要挪 ——
除非把格式改成"只能往后追加 + 索引放尾部"，否则**每次写都得整包重写**，那是另一套格式与压实逻辑。

所以这里的分工是：**包当传输格式**（单文件、带校验、带世代，适合拷来拷去），
**仓库本身是工作目录**（想连续同步就用走云的插件，见「为什么」）。

## 它是怎么判断的

> 这一节讲的是**合并那条路**（`strictness: 'normal'`）：自动收包（`incoming.ts`）与接链
> （`chain.ts`）在用它 —— 那两处的边界是"只应用不会动到本地已有东西的包"，合并语义正好对上。
> **界面上的手动应用一律严格同步**（见「应用时按什么规则处理」那一节）：不比对、直接镜像，
> 因为链条保证了两边站在同一个点上、包送到的状态是确定的。

应用一个包时的核心是**三方比对**：基准 vs 本地现在的样子 vs 包里的清单。

```
   基准（我上次应用 / 导出的样子；缺的地方用包里自带的 base 补）
        ↙                              ↘
  本地现在的样子                    包里的清单
```

- 基准是 `state.bundle.files`：上次应用 / 导出时**两边都见过、而且真的写成了一致**的路径。
  把包发给一台**新机器**时，每个条目自带的 `base`（"我以为你原来是这样"）会把基准补上
- **只有跟基准不一样的那一侧才算"改过"**；一边没了、另一边没动 → 那就是删除
  （删除必须过基准检查，本地改过的不删）
- 两边都动过 → 按冲突策略处理，默认留两份，绝不静默覆盖
- 两种"看着像冲突其实不是"的会直接覆盖：本地停在对方**发过的中间版本**上（包里的 `history`
  认得出来）、或者包里没给基准而本地那份比包还旧
- **移动会单独认**：对方改名 / 挪了位置时，本地直接跟着改名，不重传内容、也不留成
  "删一个 + 加一个"。识别条件是「新路径确实是新出现的 ＋ 旧路径在基准里 ＋
  对方那份自基准以来没动过 ＋ 大小与修改时间完全一致」，四条缺一不可
- 「以包为准 / 完全镜像」两档**不走三方比对**：目标是"仓库 == 包"，直接两侧比
  （手动应用走的就是镜像这一支）

## 基准点链条与世代

0.11 起，更新包不再是"自完整副本累积的一大坨"，而是**基准链条上的一环**：

```
完整副本 F0 ──► 更新包 C1 ──► 更新包 C2 ──► …（每一环都从上一环的落点往外长）
   点 P0           点 P1           点 P2
```

- 每个包头部都写着**我从哪一点来**（`baselineHash`）与**我落到哪一点**（`targetBaselineHash`），
  链条就是靠这两个字段首尾相接认出来的（`bundle/chain.ts`）；
- **点与点之间是严格镜像**：包里点名什么就是什么，所以链条上每个节点内容都是确定的 ——
  不必猜着合，也就不会冲突；
- **基准点自己往前走**：导出任何包 → 前进到"这次导到的那一点"；应用任何包 → 前进到"
  包送到的那一点"。自己导出的那一点只算**可能**（对方应用了才算数）；
- 链条中间断了（起点对不上）→ **拒绝**并说清从哪个点重来（见上一节），绝不降级合并；
- `changes/` 里的环默认**一个都不删**：删了它，还站在那一环起点的机器就接不上来了。
  只有完整副本（完整清单，谁都能取代）或"同一环重导了一遍"才会清掉旧的。

**漏了几环怎么办**：「自动接链」（`bundle/chain.ts` 的 `planChain` / `runChain`）能认出本机这一点
后面的整条链、按顺序接上去，并**保住本机自己的改动**（接完再放回）。界面入口还在做。

**世代号什么时候往前走**（0.10.1 起）：

| 动作 | 世代号 |
|---|---|
| 导更新包 | +1（内容确实变了一版） |
| 导完整副本，仓库**自上次导出以来有改动** | +1 |
| 导完整副本，仓库**没动过** | **不动** —— 它装的内容就是当前这一代 |
| 应用别人的包 | 采纳包里记的那一代（往回走也是对的：内容退回去了） |

"没动过就不占新世代"是为了让**内容与世代号始终对得上**：本机第 39 代、应用了别人
「39 → 46」的更新包之后，内容就是第 46 代；这时再导一份完整副本若自称第 47 代，
你导出的更新包会变成「46 → 47」，对面看着像凭空多一代。

每个文件除了新内容，还带两样东西，用来判断"本地那份能不能直接覆盖"：

| 字段 | 含义 | 什么时候对上 |
|---|---|---|
| `base` | 我**上次导出**时这个文件的样子 | 对方每次都跟着应用（最常见） |
| `history` | 自上一个完整副本以来它经历过的中间版本 | 对方停在中间某一环上 |

两个都不对 → 那才是**真的本地改动** → 留冲突副本，两份都在。

删除一视同仁：包里要求删、但本地改过的文件**不删**（只登记为"保留"）。
只有当本地仍停在 base 或某个中间版本上时才真删 —— 这是唯一不可逆的动作，宁可留着。
（引擎里的 `listed-wins` 档是例外：包里点名的照删，本地那份先进回收目录；手动应用走的是严格档，
照删的点名清单一律执行。）

对方世代**低于**包的基准世代（= 没应用过那个完整副本）时会明确提示：
"你还没应用这个包所基于的完整副本，请先要一份完整副本" —— 而不是默默应用一半。

### 更新包可以指定「从哪个状态到哪个状态」

上面那条"要彻底对齐就得互导一次完整副本"有个更省事的出口：**本地有几份完整包，
就有几个状态**，更新包可以从其中任一份出发。

**能当起点 / 终点的不只是完整副本**：链条上的**每一个点**都能选（完整副本是一个点，
每份更新包也落出一个新点，见前面「基准点链条」那节）。那些点没有自己的包文件 ——
它们的清单与内容由 `bundle/points.ts` 沿链条叠加算出来：清单 ＝ 起点清单 ＋ 各环的条目 −
各环点名的删除；内容逐文件看"哪一环点名了它"，没动过的仍从起点那份包里取。

于是"对方站在中间某一环上、我这边已经往前走了几环"这种情况可以**直接导一份从它那一环
到最新（或到另一环）的包**，它收到一个包就追上来了 —— 不必先要一份完整副本，也不必一环一环补。
（链条上已经有一份两端一样的包时不重复生成，会直接说清是哪一份。）

设置 → Locally Save → 同步包 →「更新包从哪个状态到哪个状态」两个下拉：

| 下拉 | 默认 | 选一个状态时 |
|---|---|---|
| **从哪个状态开始** | 我站的这个基准点 | 接着**那一点**往后算 —— 对方正站在它上面时，收到就是**确定**的更新（指纹对得上、一环都不缺） |
| **到哪个状态为止** | 最新（当前仓库，现在这一刻） | 导一份"从起点到**那一刻**"的**差量包**：内容逐文件沿链条取（改过的在那一环的负载里、没动过的还在起点那份包里），对方应用完正好落在那一刻，**状态编号当场对得上** |

#### 认指纹，别只看"第几代"

两个下拉的选项按**基准指纹**排：**完整副本 ＋ 链条上的每一个点**（同一份只列一次）：

```
从哪个状态开始
  我站的这个基准点（第 36 代 · 基准 4c03ccb8956d9122）
  第 35 代 · 基准 9f1c0a77b23e4d11
  第 32 代 · 基准 7a22d790635332a0
  第 24 代 · 基准 1b9f0c77aa3e4d21
```

**为什么不能按"第几代"选**：世代号是每台机器各数各的节奏号（导出一个包 +1）——
两边的"第 32 代"完全可能是**两份不同的完整副本**（一份是你导的、一份是对方自己导的）。
实际踩过的例子：按"第 32 代"选起点导了个更新包，对方回「⚠ 基准对不上」——
它报的指纹其实是你**最新**那份的，说明它早就站在你的新基准上了，这一趟是白跑。
（也可能反过来：它手里那份"32"根本不在你的包目录里，那就得先把它那份完整副本要过来。）

所以流程是：**让对方打开「更新记录」**（命令 `同步包更新记录…`），把顶上那行念给你：

```
基准：第 36 代 · 指纹 4c03ccb8956d9122 · obsidian-full-20261005-185551-e34cc7.lsave
```

照着那个**指纹**在「从哪个状态开始」里选。列表里每一行也写着「第 N 代 · 基准 xxxx」，
对得上就是同一份东西。对不上时应用对话框里有个 **「复制指纹发给对方」** 按钮，
把你这边的指纹原样发过去最省事。

#### 收到的包"送到的地方正好是我的基准"

如果对方把一份 `32 → 36` 的差量包发给你，而你**已经站在第 36 代**上（基准就是那份 36），
应用对话框会直接告诉你：

> ✓ 这个包要送到的那份完整副本（第 36 代 · 基准 4c03ccb8…）**就是你这边的基准**：
> 里面没有你缺的内容，应用它不会改动任何文件。

（包头部带着目的地那份完整副本的指纹 `targetBaselineHash`，接收方一比就知道。）
这时你不用应用它，直接让对方按**你的基准指纹**重导一份更新包即可。

几条硬规矩：

- 指定的那一份**找不到就明确报错**，并列出"现在有哪些状态"—— 绝不悄悄换一份
  （包头部记的基准决定接收方怎么比对，偷偷换一份等于骗它）
- 差量包（终点是某份完整副本）导的时候**本机什么都不推进**：世代、基准、状态编号、
  "欠回传"那笔账都不动 —— 它代表的不是"我现在的仓库"
- 同一份差量包**不会重复生成**（内容由两份完整包决定）：已经躺在那儿就直说，
  删掉那个包才能重导
- `changes/` 里的环**默认一个都不删**（删了它，还站在那一环起点的机器就接不上来了）；
  只有"完整副本"（完整清单，谁都能取代）与"同一环重导了一遍"会清掉旧的，
  其余留着并说明为什么（别的血脉 / 世代不比新包小 / 链条上的另一环）

于是那个经典场景（两台都在第 32 代 → 我这边重立基准到了第 36 代 → 对方还在 32 代）
就有了第三条路：

```
对方：第 32 代  ──应用「32 → 最新」的更新包──►  内容与我对齐（状态编号一致）
                （不必先要那份第 36 代的完整副本；我这边在「从哪个状态」里选它那个指纹）
```

顺带一句：**同步包界面（导出 / 应用 / 管理）都会显示"本机：第 N 代 · 站在哪个基准点
（已确认 / 待对方合并）· 状态 xxxx"**，列表里每一行也写着那个包自己的世代与状态编号 ——
一边一个编号，对得上就是同一份东西。

## 已知边界

- **只支持桌面端**（`isDesktopOnly: true`）：读写仓库之外的文件必须走文件系统，
  Obsidian 的 vault API 出不了库
- 判据是「大小 + 修改时间」，修改时间带 2 秒容差（FAT/exFAT 只精确到 2 秒）。
  **导出挑成员与应用比对都用它**，代价是：同一个文件在 2 秒内被改成同样长度，
  这一轮可能看不出来（换长度、或者把时间拉开，就会认出来）。
  想确定"两边内容一不一样"，看**状态编号** —— 那个是按内容指纹算的
- 排除规则挡住的东西**不进包**：默认是配置目录（`.obsidian/`）、`.trash/`、`*.lsave`
  与系统垃圾文件。想连插件与快捷键一起搬，把「不进包的文件」里那行删掉即可
- 应用包里带来的改名是**文件系统层面**的改名：仓库里指向它的链接不会跟着更新
  （Obsidian 只跟踪应用内的改名）
- **删不掉的空目录**：目录里只有被排除规则挡住的东西时（`*.lsave`、`desktop.ini`、`.DS_Store`…），
  插件看不见它们、`rmdir` 也就删不动。这时会**明确报出来**（"里面还有东西，只删空的"），
  而不是反复尝试
- **打开更新包文件夹**依赖系统文件管理器：优先走 Electron 的 `shell.openPath`，
  拿不到就退回 Obsidian 自带的"用默认程序打开"，都不行时弹一条含路径的通知让你手动复制
- 打开同步包对话框时只做一件事：**把 Obsidian 叫到前台**（双击 `.lsave` 进来时你可能没看见它）。
  插件**不会动你的窗口大小与位置** —— 以前那个"最大化窗口"的开关已经删掉了
- **接收端默认要手动应用**：想省这一步就打开「自动应用收到的更新包」（见上面那节）——
  它只在完全不会动到本地已有东西时才自己动手；完整包永远要你亲自看
- 状态文件在 `.obsidian/plugins/locally-save/sync-state.json`，记着基准、世代、目录基准、
  内容指纹缓存、更新记录与状态编号。删掉它等于"当作第一次"，不会动仓库里的文件 ——
  但下次导更新包会要求先立基准（导一份、或者应用别人一份完整副本）

## 隐私

**这个插件不发起任何网络请求。** 没有遥测，没有账号，不上传任何东西。

它碰的东西只有三处，都在你眼皮底下：

- **仓库之外的文件**：这正是它的功能（包要写到仓库外、删掉的文件要挪进回收目录），
  所以它用 Node 的文件系统读写——`isDesktopOnly: true` 就是这么来的。
  它只会碰你指定的**同步包文件夹**、仓库本身、以及仓库里的 `.trash/locally-save` 回收目录；
- **系统命令**：只有一处 —— 设置里那个「把 .lsave 关联到 Obsidian」按钮（仅 Windows）。
  它跑 `reg.exe` 往 `HKCU\Software\Classes` 写一条当前用户的文件关联，**不点这个按钮就不会执行**，
  也不需要管理员权限；不想要了就点「解除关联」，不会留下别的东西；
- **剪贴板**：只有「复制路径」按钮会往里写一条路径，从不读剪贴板。

另外，所有**会改文件**的动作默认都是关的（自动留包、自动应用都如此），
真正动手之前还有确认框；删除一律进回收目录（手动应用的严格档**强制先备份**）。

## 开发

```bash
npm install
npm run dev      # 监听改动，打包完自动同步到 vault 的插件目录
npm run build    # 类型检查 + 生产打包
npm test         # 663 项检查（比对矩阵 / 排除规则 / 同步包 / 自动留包 / 自动应用 / 设置面板 / 装配）
npm run lint
```

测试文件在 `test/` 下：`manifest / exclude / diff / bundle / auto-export / auto-apply / drop /
protocol / settings / commands`。其中 `auto-export.test.ts` 是"留包整条链路"的端到端、
`auto-apply.test.ts` 是"收包 → 安全边界 → 自动应用"的端到端（都用插件装配 + 真实临时目录），
改自动留包 / 自动应用 / 状态栏 / 通知文案时要一起看它们。

改完在 Obsidian 里 **设置 → 第三方插件** 重新加载即可。

### 发版

```bash
npm version 0.8.0        # 同步 manifest.json 与 versions.json，打好同名 tag（不带 v 前缀），
                         # 并顺带跑一次 npm run build —— 重新打包、部署到 vault 的插件目录
git push origin main --follow-tags
```

`postversion` 里那次 build 不是多余的：不然"先 build、后改版本号"会让 vault 里那份
`manifest.json` 停在旧版本号（代码是新的、版本号是旧的），你从插件目录拷到另一台机器，
装出来就是旧版本。

CI（`.github/workflows/release.yml`）会在 tag 推上去之后跑测试与构建，
校验 **tag 与 `manifest.json` 的 version 一致**，然后创建 Release 并附上
`main.js` / `manifest.json` / `styles.css`。版本号忘了改就打 tag 会被直接拦下。
