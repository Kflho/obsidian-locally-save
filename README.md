# Locally Save

把 Obsidian 仓库同步到**本地磁盘上的一个文件夹副本**，几秒完事；再提供一个"同步包"，
把改动或整份副本装进单个文件，用 U 盘 / 网盘搬来搬去，在另一台机器上打开即可应用。

对标 Remotely Save 的用法，但走的是本地文件系统而不是网络 —— **完全不联网**。

## 为什么

走网络的同步插件，几百 MB 的仓库来回传一次要等很久；而同一台机器上两个文件夹之间
复制 500MB 只需要几秒。日常备份、异地机器之间搬运，本地路径快得不是一个量级。

## 功能

### 本地同步

把仓库同步到任意本地文件夹（可以指向移动硬盘、网盘的同步目录、另一块盘）：

- **双向**：两边改动互相补齐；也可以选**仅上传**（副本只作备份）或**仅下载**
- **同步删除**：本地删的副本也删，反之亦然；可以关掉；关掉后之前删掉的文件会从另一边取回
- **删除前先备份**：删掉的文件挪进回收目录，而不是直接消失
  （副本那边在 `目标文件夹/.lsave/trash`，本地这边在 `仓库/.trash/locally-save`）
- **两边都改了怎么办**：默认留两份 —— 新的那份占原名，旧的那份存成
  `xxx (冲突副本 20261004-153000).md`；也可以选"以本地为准"或"以副本为准"
- **排除规则**：写法同 `.gitignore`（`目录/`、`*.tmp`、`a/**/*.md`），
  默认排除配置目录（各台机器的插件与快捷键往往不同）
- **自动同步**：启动后一次 / 定时 / 保存后静置若干秒，三个开关默认都关着
- **预览**：`预览同步（不执行）` 先摊开"这次会干什么"，确认了再动手

### 同步包（`.lsave`）

把仓库打包成**单个文件**，拷到另一台机器上用插件打开：

- **完整副本**：整个仓库，到哪台机器都能整份恢复；也是更新包的**基准**
- **更新包**：自上次完整副本以来**累积**的全部改动（含一份删除清单）。
  对方永远只需要应用**最新那一个** —— 跳过中间几个也不会少内容，也不会留下冲突副本
  （它认得出"这是你以前发过的版本，不是我自己改的"）
- **打开即报告**：选包之后先算一遍再让你决定 —— 同步程度百分之多少、
  会新增/覆盖/跳过/冲突各几个、会不会删东西、走的是快速通道还是逐文件合并、
  中间有没有漏包。**打开包这一步不写任何文件**
- **校验**：包尾部记着整段负载的 sha256，传输过程弄坏了会被拒绝（而不是写进仓库）
- **自动留包**：两个开关**各自独立**（默认都关）
  - **留更新包** —— 每次同步成功后把累积改动导成一个包。用的是同步刚扫完的结果，
    **几乎不额外花时间**；没有改动就不导。适合天天来回搬
  - **留完整包** —— 每次同步成功后导一份整个仓库。**每次都要把整个仓库重写一遍**，
    几百 MB 的库会明显变慢，只在"随时要给别人一份完整副本"时打开
  - 更新包会随改动越攒越大（笔记型仓库通常几 MB 就到顶）；**导一次完整副本，累积就清零**
  - 第一次必须先导一次完整副本 —— 更新包要有基准才谈得上"累积"
- **包放在哪**：默认在**同步目标文件夹**的 `.lsave/bundles` 下 ——
  这个目录不参与同步，所以包不会被当成"副本新增的文件"传回仓库。
  完整包与改动包分别放在它的 `full` 与 `changes` 子目录里；
  设置里填了「同步包文件夹」就改用你指定的路径（同样会分这两个子目录）

### 三个左侧栏图标

插件在左侧栏放三个图标（**每一个都能在设置里单独关掉**，见「界面与交互」页）：

| 图标 | 点一下 |
|---|---|
| ⟳ 刷新类图标 | **立即同步到本地副本** |
| 📦 包裹类图标 | **导出同步包**（打开导出对话框） |
| 📂 开箱类图标 | **打开同步包并应用**（选中包 → 先看报告 → 再应用） |

跟命令面板里的 `立即同步` / `导出同步包…` / `打开同步包并应用…` 是同一套动作，
喜欢哪种入口用哪种。图标名是**运行时**从 Obsidian 的图标清单里挑的
（`IconName` 在类型上就是 `string`，写错了只会静默显示成空白方块，所以不能猜）。

设置面板的「本地同步」页里也有对应的按钮，找不到命令面板时从那儿点。

同步包相关的设置都在设置面板的**「本地同步」页**里（它本来就是本地同步的搬运方式）。

## 怎么用同步包（跨机器搬运）

假设要把 A 机（笔记本）的仓库搬到 B 机（台式机），或者让两台机器来回同步。

### 第一次：A → B，用**完整副本**

1. **A 机**：设置 → Locally Save → 本地同步 → 滚到「同步包：手动导出」→ 点 **导出同步包…**
   （或者 `Ctrl+P` 输入 `导出同步包`）
   - 「导出内容」选 **完整副本**
   - 「同步包文件夹」默认是 `你的目标文件夹/.lsave/bundles`，也可以改成一个方便拷走的地方（比如 U 盘）
   - 点「导出」；对话框里会写明 **会写到：** 哪个目录
2. 把生成的 `.lsave` 文件拷到 B 机（U 盘、网盘、聊天软件，怎么拷都行）
3. **B 机**：设置 → Locally Save → 本地同步 →「同步包：应用」→ 点 **打开同步包并应用…**
   - 从列表里选（`full` 与 `changes` 两个子目录的包都会列出来），也可以直接粘完整路径
   - **先看报告**：同步程度、新增/覆盖/冲突/删除各几个、走哪条通道、有没有漏包
   - 确认无误，再点 **应用**

### 之后：日常来回搬，用**仅改动**

1. A 机同步一次 —— 如果开了「同步后自动留改动包」，包已经躺在 `changes` 目录里了；没开就手动导一次（选「仅改动」）
2. 拷到 B 机 → 打开并应用。B 机没动过的话，报告会显示同步程度 100%

### 三种应用方式（在应用对话框里当场选）

| 模式 | 本地也改过的文件 | 本地多出来的文件 | 包里要求删的 |
|---|---|---|---|
| **所有都保留**（默认） | 留冲突副本，两份都在 | 保留 | 过基准检查才删 |
| **清老的** | 同上 | 只删比包旧的 | 同上 |
| **强制应用** | 直接覆盖 | 全删，不管新旧 | 直接删 |

**后两种只对完整副本开放**：改动包里只装了变过的文件，对着它清理等于把仓库其余文件全删光。
所以选中改动包时那两个选项会灰掉，并自动切回「所有都保留」——这是防呆的第一层。

第二层：真要删文件或覆盖本地改动之前，会再弹一次确认框，把"删哪几个、覆盖了几个本地改动、
东西去哪儿了"摊开给你看。纯新增的包不会被打断。

被覆盖 / 被删掉的本地版本会**先进回收目录**（`仓库/.trash/locally-save/时间戳/`），
所以"强制一致"之后仍然捞得回来 —— 那个目录不参与同步，不影响一致性。

### 应用完，本地副本要不要跟上

对话框里有一项 **「应用后顺便同步到本地副本」**（填了目标文件夹时默认开着）：
应用完再跑一次正常同步，把这次的改动推到副本。不这么做的话，备份会在应用完包之后
悄悄落后一截 —— 你以为它是新的，其实不是。

顺序上有个讲究：**包里删掉的文件，会先从副本里也清掉、再把基准划掉，然后才同步**。
否则常规同步会把它们当成"本地缺了、该从副本取回"，刚删掉的文件又长回仓库
（「同步删除」关着时必然如此）。

### 几个要点

- **打开包那一步是只读的**：随便点、随便看，不会动你的文件；只有点「应用」才写盘
- **包里要求删、本地改过的文件不删**（删除必须过基准检查，没有例外）
- 提示「**漏了包**」不用慌：插件会降级成逐文件合并 —— 能安全写的照写，本地也改过的留冲突副本。
  想彻底对齐，让对方导一份完整副本
- 自动留包的两个开关**各自独立**：只开「改动包」最省（几十 KB 到几 MB）；
  「完整包」每次都要重写整个仓库，几百 MB 的库会明显变慢
- 包丢了、传坏了都不影响仓库：**导出是只读的**，包损坏会在应用前被校验拦下

设置面板里也有一个 **「看说明」** 按钮，写的就是上面这套流程。

## 为什么不让"包"直接当同步目标

看上去更统一（本地就一个文件），但性能上不划算。`.lsave` 的头部记的是每个文件在负载里的
**绝对偏移**，任何一个文件大小一变，后面的偏移全要挪 —— 除非把格式改成"只能往后追加 + 索引放尾部"，
否则**每次同步都得整包重写**：

| 场景（500MB 库 / 1 万文件 / SSD） | 文件夹副本 | 单包（整体重写） | 单包（追加式改造后） |
|---|---|---|---|
| 改一个 10KB 笔记后同步 | 只复制 10KB **≈0.2 秒** | 重写 500MB **≈2–5 秒** | 追加 10KB + 重写索引 **≈0.3 秒** |
| 比对扫描 | 两侧各 1 万次 stat | 索引直接给出（更快） | 同左 |
| 磁盘占用 | 1× | 1× | 1× + 垃圾，需定期压实 |
| 谁能打开 | 任何程序都能直接读 | 只有本插件 | 只有本插件 |
| 损坏的后果 | 坏一个文件 | 整包校验失败 | 整包/索引损坏 |

文件夹副本的增量是**内核级**的（`copyFile` 只搬改动的那几个字节），包格式的增量得我们
自己在 JS 里维护索引与偏移。所以这里的分工是：**文件夹副本当同步目标**（快、透明、坏只坏一个），
**包当传输格式**（单文件、带校验、带世代）。

## 它是怎么判断的

同步的核心是**三方对比**：以上次同步后的样子为基准，分别看本地和副本现在什么样。

```
   上次同步记下的状态（基准）
        ↙            ↘
  本地现在的样子    副本现在的样子
```

- 只有跟基准不一样的那一侧才算"改过"；一边没了、另一边没动 → 那就是删除
- 两边都动过 → 按冲突策略处理，默认留两份，绝不静默覆盖
- **移动会单独认**：改名/挪目录本质是"删一个 + 加一个"，真按两步做的话，
  关了删除传播时旧文件会被拉回来、两边各留一份。所以比对阶段会按
  「大小 + 修改时间完全一致」把「新增」与「对侧删除」配对，配对成功就在对侧直接改名，内容不重传
- 复制之后会把修改时间对齐到源文件 —— 不对齐的话每轮都会误判成"改过"，反复重传

## 同步包的累积与世代

更新包是**以完整副本为基准累积**的，这是整套设计里最关键的一条：

```
完整副本 F0  ──►  更新包 C1（自 F0 以来）──►  更新包 C2（自 F0 以来，含 C1 的内容）──► …
                      │                                    │
                   对方应用 F0 之后，应用 C1 就是最新的；直接应用 C2 也是最新的
```

所以：**永远只需要应用最新的那一个**，不用担心顺序、不用担心漏包。代价是包会越滚越大，
**导一次完整副本就清零** —— 这不是可选项，而是这套方案的节制阀。

每个文件除了新内容，还带两样东西，用来判断"本地那份能不能直接覆盖"：

| 字段 | 含义 | 什么时候对上 |
|---|---|---|
| `base` | 我**上次导出**时这个文件的样子 | 对方每次都跟着应用（最常见） |
| `history` | 自完整副本以来它经历过的中间版本 | 对方跳过了一两个包 |

两个都不对 → 那才是**真的本地改动** → 留冲突副本，两份都在。

删除一视同仁：包里要求删、但本地改过的文件**不删**（只登记为"保留"）。
只有当本地仍停在 base 或某个中间版本上时才真删 —— 这是唯一不可逆的动作，宁可留着。

对方世代**低于**包的基准世代（= 没应用过那个完整副本）时会明确提示：
"你还没应用这个包所基于的完整副本，请先要一份完整副本" —— 而不是默默应用一半。

## 已知边界

- **只支持桌面端**（`isDesktopOnly: true`）：同步目标是仓库之外的文件夹，
  Obsidian 的 vault API 出不了库，只能用 Node 的文件系统
- 比对用「大小 + 修改时间」，修改时间带 2 秒容差（FAT/exFAT 只精确到 2 秒）。
  代价是：**同一个文件在 2 秒内被改成同样长度**，这一轮可能看不出来，下一轮才会发现
- 在**副本**里改名，不会更新仓库笔记里指向它的链接（Obsidian 只跟踪应用内的改名）。
  在仓库里改名（正常用法）不受影响
- 状态文件在 `.obsidian/plugins/locally-save/sync-state.json`，记录每个目标的基准、
  世代与内容指纹缓存。删掉它等于"当作第一次同步"，不会动仓库里的文件

## 隐私

**这个插件不发起任何网络请求。** 没有遥测，没有账号，不上传任何东西。
它只做两件事：读你指定的本地文件夹、按上面的规则复制或删除文件。

## 开发

```bash
npm install
npm run dev      # 监听改动，打包完自动同步到 vault 的插件目录
npm run build    # 类型检查 + 生产打包
npm test         # 210 项检查（比对矩阵 / 排除规则 / 端到端同步 / 同步包 / 设置面板）
npm run lint
```

改完在 Obsidian 里 **设置 → 第三方插件** 重新加载即可。

## 源码结构

```
src/
  main.ts          入口：生命周期与装配（同步引擎通过 SyncHost 接口拿它要的东西）
  sync/
    diff.ts        三方比对 + 移动识别（纯逻辑，可测）
    exclude.ts     排除规则（纯逻辑，可测）
    disk.ts        磁盘访问层（唯一碰 node:fs 的地方）
    execute.ts     执行同步计划
    runner.ts      总调度：扫描 → 比对 → 执行 → 重建基准
    state.ts       状态：血脉、世代、per-target 基准、指纹缓存
    hash-cache.ts  内容指纹的懒算与缓存
  bundle/
    format.ts      .lsave 容器格式
    export.ts      导出（完整 / 仅改动）
    apply.ts       先算后做：报告 → 应用（快速通道 / 降级合并）
  ui/              预览窗口、同步包界面、状态栏
  settings/        设置模型 + 字段表（面板的单一数据源）
test/              测试（Node 直跑，无测试框架）
```
