# 「同步到本地副本」到底在干什么 —— 分析与优化清单

> **后续（0.8.0）：这条通道已经整条砍掉了。** 结论是"共用目录那种连续同步交给走云的插件
> （Remotely Save + WebDAV / 坚果云），本插件只做不联网的单文件搬运"——
> 实施记录见 `docs/砍掉副本通道-实施计划.md`。
> 所以下面 P0~P3 那些优化项里，**只在副本通道上成立的那几条（P0-1 大删除护栏、
> P0-2 原子写入、P0-3 副本同步后重算编号、P1-*、P2-*）已经不适用了**；
> 保留这份文档是因为它记录了"为什么砍"的实测证据 —— 下次有人想加第二条通道时先看这里。

分析对象：0.7.0（`8269cc5`）的 `src/sync/` 那一整条通道，以及它跟 `src/bundle/` 的分工。
结论都有代码位置或实测输出撑着；实测是拿**真实引擎**跑临时目录得到的（见 §3 与 §7）。

---

## 0. 一句话结论

**这个功能有用，但有用的不是它花力气最多的那部分。**

| 你的感觉 | 实际情况 |
|---|---|
| 「副本和本地文档不是完全一样的东西吗」 | **功能上**确实一样，它要的就是一样；但**判据**不一样 —— 副本通道只靠「大小 + 修改时间」判断"变没变"，而这条判据在被别的程序碰过的副本上会骗人（§2.1、场景 2） |
| 「只是盲目模仿远程同步中的远程端」 | **说对了一半**：方向 / 冲突 / 上传下载 / 每台机器各自一份基准，都是照"网络远端"的模型搬来的；而本地副本的两条优势（两侧都能读、能算哈希；副本是一个可能被别人写的真实文件夹）恰好没用上 |
| 「根本没有用」 | **不对**。有三件事它是真在干，其中"从副本给另一台机器铺库/恢复"是同步包替代不了的（§1） |

真正的问题不是"没用"，而是：**它在"副本只是被动备份"时留下了没必要的复杂度，在"副本真被别人写"时又没有任何防线。**

## 1. 它现在实际提供的三件事

| # | 用途 | 谁在用 | 靠什么实现 |
|---|---|---|---|
| 1 | **增量镜像备份**（单机最常见） | 立即同步 / 定时 / 保存后自动同步 | `fs.copyFile` 内核级复制（只搬改动的那几个字节）+ 基准三方比对 + 删除传播 + 移动识别（改名不重传）+ 回收目录 |
| 2 | **给另一台机器铺库 / 灾备恢复** | `仅从本地副本拉取` | 空基准时所有文件都是"副本新增" → 直接全量拉下来。**比导包快**：不打包、可中断续跑、不用等一个 500MB 的文件写完 |
| 3 | **同步包的中转站** | 「同步后自动留包」/ 导出弹窗 /「应用后顺便同步到副本」 | 默认包目录就是 `<副本>/.lsave/bundles`（`bundle/paths.ts:27-32`）；应用完包再跑一轮同步，副本才不落后（README「应用完，本地副本要不要跟上」） |

第 2 条值得单独强调：**"另一台机器上什么都没有 → 指着副本拉一遍"是这条通道最硬的用途，而且比包更好**
（包要先把整个仓库写成一个文件，再读出来；副本是现成的树，还能只补缺的那部分）。

顺带清点一下"为了像远程同步"而存在、但日常用不到的东西：
双向方向、三档冲突策略（`keep-both` / `local-wins` / `remote-wins`）、`upload` / `download` 的动作命名与命令
（`upload-to-copy` / `download-from-copy`）、移动识别（`detectMoves`）。
它们在"单机 + 副本只写不读"的用法里基本不会触发；在"副本真的被别人写"的用法里又不够用（§2.2）。

## 2. 三条"远程假设"，在本地副本上的代价

### 2.1 判据只能是「大小 + 修改时间」

网络那一侧，为了判断"改没改"把两边的文件都读一遍算哈希是不划算的，所以只能拿 size+mtime 当代理。
**本地副本两侧都在盘上，这个妥协没必要原样继承。**

- 代码：`sync/diff.ts:26-30`（`sameRecord`，2 秒容差）、`diff.ts:197-198`（`localChanged` / `remoteChanged` 全靠它）。
- README「已知边界」自己承认了一半：同一秒内改成同样长度可能看不出来。

代价分两档，实测都在场景 2：

1. **整库被回写**：网盘客户端 / U 盘拷贝工具 / 某些备份软件会**重写副本的修改时间**（内容一字不改）。
   下一轮同步：本地没动、副本"动了" → 每个文件都判成 `download` → **把整个仓库重写一遍**，
   连仓库里笔记的 mtime 也一起被改成副本那套时间。Obsidian 与别的同步工具会看到"全库刚被改过"。
2. **用户的真改动可能输给旧内容**：同一轮里用户真的改了内容，同时副本时间被外部改新 →
   判成冲突 → **谁赢按 mtime 定**（`diff.ts:230`）→ 时间戳更新的那份**旧内容**赢，用户刚写的被挪进回收目录。

对照一下：**同步包那条通道没这个毛病** —— `bundle/apply.ts` 靠 `base` / `history` 指纹判断"这是本地改的还是我发过的中间版本"，
`sync/hash-cache.ts:12` 的注释写得就是这件事：「因为修改时间会被复制、被外部工具改，靠它认文件在某些场景下会出错」。
**同一条理由，副本通道还没落实。**

### 2.2 假设两侧是对等的写入者

方向、冲突、上传/下载都是"两个平等的副本互相补齐"的模型。但：

- 副本多数时候是**只写不读**的备份 —— 那些冲突逻辑不会被触发；
- 副本真的被写时（另一台机器、网盘客户端、用户手动改），插件**没有任何记录能说出"副本是谁写的、什么时候写的"**。

根源是基准只存在**本机插件目录**里（`sync/state.ts:17-19` 明说了这个设计：
「同一个副本（比如一块 U 盘）可能被两台机器用，各自的基准必须分开记，否则会互相覆盖」）。
这个理由本身没错（两台机器不能互相覆盖对方的账本），但它顺带把**副本自己的真相**也扔了：

- 副本里 `.lsave` 只有 `bundles/`、`bundles-trash/`、`trash/`，没有一份"这个副本现在长什么样、上一笔是谁写的"的清单；
- 换一台机器，第一轮只能靠 size+mtime 猜（内容恰好一致时侥幸无事，见场景 1）；
- 设置面板里还**明确建议**把目标指向"移动硬盘或网盘的同步目录"（`settings/fields/sync.ts:39`）——
  这正是"副本会被别人写"的场景，而插件对这件事零感知。

### 2.3 「两边一致」这句话，副本通道没人回答

状态编号（`sync/state-id.ts`）是用户点名要的东西："需要一个编号让用户能确定当前文件状态，如哈希值，打开日志看到就能确定两边文件到底是否一致"。
它现在只在**同步包**的导出（`bundle/export.ts:290`）与应用（`bundle/apply.ts:952`）里算。

- 副本同步从头到尾**不算、不存**编号 → 预览窗口里只有一句"一致 N 个"（`ui/sync-modal.ts:43-44`），
  而那个 N **还不准**：被方向过滤掉的动作被计进了 `unchanged`（`diff.ts:153-159` 的 `push()`），
  于是"仅下载"时仓库独有的文件会被报成"一致"（场景 5）。
- 更硬的问题（场景 3）：**仅下载把副本内容写进仓库之后**，仓库内容已经变了，
  `state.stateId` 还是上一回导出/应用时的旧值。日志顶部那句"我现在：状态 …"（`bundle/log.ts:78-79`）
  以及之后跟包头部编号的比较（`compareStateId`）全都建立在一个**过期编号**上。
  应用同步包那条路会重算（`apply.ts:952-960`），副本同步这条路不会。

## 3. 实测：五个场景（真实引擎跑临时目录）

探针脚本用 `runSync` 直接跑临时目录（造法见 §7），下面是要点原样摘录。

### 场景 1：两台机器共用同一个副本文件夹（U 盘 / 网盘目录）

```
A 首次同步 → upload:a.md / upload:b.md
B 首次同步（B 自己没有任何基准）→ （没有动作，一致 2）
A 改了 a.md 后同步 → upload:a.md
B 改了自己的 b.md 后同步 → download:a.md / upload:b.md
B 删掉 a.md 后同步 → delete-remote:a.md
  副本里还有 a.md 吗： false
A 再同步 → delete-local:a.md / download:b.md
  A 的仓库里还有 a.md 吗： false     ← A 的文件被 B 的删除带走了
```

内容最后是收敛的（这一步设计得不错：内容一致时"没有基准"不会乱判），但：
**A 那边只看到"副本已删除 → 删除本地"，完全不知道这是另一台机器干的**；界面上也没有任何地方能回答
"这个副本现在代表哪台机器"。删除进的是 `仓库/.trash/locally-save/<时间戳>/`（可捞回），所以不算数据丢失，但过程对用户是黑箱。

### 场景 2：副本的修改时间被"网盘 / U 盘 / 拷贝工具"重写过（内容没变）

```
首次同步 → upload:x.md / upload:y.md
（模拟：网盘重写副本里所有文件的修改时间，内容一字未改）
再同步 → download:x.md / download:y.md
  仓库里 x.md 的修改时间被改成了： 2026-01-08T00:00:00.000Z （原来： 2026-01-01T00:00:00.000Z ）

再同步（用户在仓库改了 x.md，同时副本时间又被动过）→ conflict:x.md / download:y.md
  副本里 x.md = "XXXX"            ← 旧内容赢了，占了原名
```

第二段是这次分析里**最该修的一条**：一个"内容完全没变"的副本，能让插件把整个仓库重写一遍。
第三段更严重：用户刚写的内容输给了时间戳更新的旧版本（那份进了 `仓库/.trash/locally-save/冲突/`，能捞回来，但用户看到的是"我的改动没了"）。

### 场景 3：从副本往仓库里写（仅下载）之后，状态编号不更新

```
同步前 state.stateId = aaaaaaaaaaaaaaaa
仅下载同步 → download:n.md
  仓库里 n.md = "N2-副本里的新内容"
  同步后 state.stateId = aaaaaaaaaaaaaaaa （仓库内容已经变了）
```

编号的含义是"我这台机器现在的内容指纹"（`sync/state.ts:188-195`）。写到仓库之后它就不成立了 —— 这是明确的 bug，
不必等大改，收尾时重算一次即可。

### 场景 4：目标文件夹"看着是空的"（指错目录 / 网盘还没同步下来 / 只拷了一半）

```
首次同步 → upload:1.md / upload:2.md / upload:3.md
再同步（副本空了）→ delete-local:1.md / delete-local:2.md / delete-local:3.md
  仓库里还剩几个文件： 0
  仓库回收目录： [ '20261005-180036/1.md', '20261005-180036/2.md', '20261005-180036/3.md' ]
```

一轮里把整个仓库搬进回收目录。**默认设置下可恢复**（`deletedToTrash` 默认开），但：
用户看到的是"我的仓库空了"；而且如果关掉「删除前先备份」就是不可逆的。
现在**没有任何护栏**：同步包通道有「这次不执行包里的删除」（`skipDeletions`）与强制档的单独确认，副本通道什么都没有。

反方向同样值得防：如果**仓库**被外部事故清空，下一轮同步会跟着把**副本**也清空 —— 备份被同一个事故一起带走。
（副本是**镜像**，不是**历史**；历史是完整包 `.lsave` 的职责。这条区别值得在界面上说清。）

### 场景 5：「一致 N 个」这个数字是怎么算的

```
仅下载 → （没有动作，一致 2）
  但副本里其实并没有 only-local.md： false
```

`plan.unchanged` 把"因为方向而被跳过"的动作也算成了一致（`diff.ts:153-159`），
于是预览窗口会说"一致 2 个"，而其中一个文件在副本里根本不存在。

## 4. 优化清单

按"性价比 × 风险"排。P0 是可以立刻做、单独发一版的；P2 是真正改变这条通道定位的。

### P0 —— 先堵漏（都是小改动）

| 编号 | 要改什么 | 落点 | 验收 |
|---|---|---|---|
| **P0-1** | **大删除护栏**：一轮里某一侧的删除数越线（建议：`> 50 个`，或 `> 5 个且 > 基准的 25%`）时不直接执行 —— 走一次预览确认。**自动同步（定时 / 保存后 / 启动）不许自动确认，直接跳过这一轮并通知** | `sync/runner.ts` 出计划之后、`executePlan` 之前；确认弹窗复用 `ui/sync-modal.ts`；引擎只出标志位（不 import obsidian），由 `ui/actions.ts` 决定问不问 | 新测试：造一个"副本空、基准满"的场景 → 断言没有 `allowMassDeletion` 时不动文件、有计划待确认 |
| **P0-2** | 写进**仓库**的复制改成「同目录临时文件 + `rename`」原子替换，别让 Obsidian 读到半截笔记（写进副本的可以不变，那边坏了下一轮会重传） | `sync/disk.ts` 的 `copyFilePreservingMtime` 加一个"原子"分支，`sync/execute.ts` 的 `download` / `conflict(winner=remote)` / `rename-local` 回退分支用它 | 测试：复制过程中断（用只读目标目录模拟失败）→ 目标文件要么不存在、要么是完整的旧版本 |
| **P0-3** | **写到仓库之后重算状态编号**并落盘：这一轮只要动过本地（`download` / `delete-local` / `conflict` 里本地那份 / `rename-local`），收尾就 `computeStateId` 一次，写进 `state.stateId` | `sync/runner.ts` 收尾（`saveState` 之前）；直接复用 `sync/state-id.ts` | 测试：仅下载一轮之后 `state.stateId` 与"重算一遍"一致；没动过本地时不必重算（省时间） |
| **P0-4** | 「一致 N 个」口径修正：被方向跳过的动作单独计数（如 `skipped`），预览里写成「这次不处理 N 个（方向限制）」，别再混进"一致" | `sync/diff.ts`（`push` 里分账）、`sync/types.ts`（`SyncPlan` 加字段）、`ui/sync-modal.ts`、`sync/summary.ts` | `test/diff.test.ts`：仅上传 / 仅下载两个方向的矩阵，断言 `unchanged` 只数真正一致的 |

### P1 —— 判据从"时间"升级到"内容"

| 编号 | 要改什么 | 说明 |
|---|---|---|
| **P1-1** | **有差异时先核对内容再动手**：只在"两侧 size/mtime 对不上、且要判断谁改过"的那些文件上算一次 sha256（本地盘，成本可控）。内容一致 → 只把 mtime 对齐（或记进基准）后当无事发生；不一致 → 才走原来的上传/下载/冲突 | 这一条直接消灭场景 2 的两档：整库回写、以及"旧内容靠时间戳赢了用户改动"。实现上复用 `hash-cache.ts` 的 `fingerprint`（有缓存、按 size+mtime 失效） |
| **P1-2** | **副本侧也有状态编号**：同步结束后分别算"仓库编号 / 副本编号"，两个一样才说"两边一致"；预览、通知、状态栏、更新记录里都显示（例如 `状态 副本 3f2a… = 仓库 3f2a…`） | 这才是用户当初要的那句话，对副本通道现在完全没有。**注意**：`state.hashes` 的键现在只有路径（`state.ts:325-335`），仓库与副本里"同路径 + 同大小 + 同时间"的文件会共用一条缓存 —— 要给缓存键加上根（vault / copy），否则这一步会自欺欺人 |
| **P1-3** | 给核对加预算：单文件上限（沿用 `fingerprint` 的 64MB）、每轮最多核对 N MB / N 个文件，超出的部分退回"按时间判断"并在报告里说明 | 一万个文件的大库里，第一轮"差异文件极多"时别把同步拖成慢动作 |

### P2 —— 给副本一份"自述"（把"远程端"这件事做实，或者明确不做）

| 编号 | 要改什么 | 说明 |
|---|---|---|
| **P2-1** | 在副本里写一份 `.lsave/copy.json`：**上次写入者**（copyId / 机器名 / 仓库名）、时间、**清单**（`path → size + mtime + 内容指纹`）、**当时的状态编号**、世代 | 三个直接收益：① 另一台机器可以直接**认领基准**，不再"没有基准、全靠 mtime 猜"（场景 1 的黑箱消失）；② 界面能说"这个副本是机器 B 在 2 小时前写的"；③ 清单与磁盘一比就能认出**半拷贝 / 被别的程序改过**，这时只补不删（场景 4 的护栏再加一层）。注意 `.lsave` 已经整个不参与扫描，放这里不会污染同步 |
| **P2-2** | 把两种用法显式化：**镜像**（默认；副本只听仓库的，副本侧的改动默认不回流）/ **共享**（承认副本有别的写入者，走 P2-1 的清单 + P1 的内容核对） | 现在这两件事被压在同一组"双向 / 冲突策略"设置里，用户只能自己猜该选哪档 |
| **P2-3** | 文案去掉网络味：`上传 / 下载` → `写入副本 / 从副本取回`；`仅从本地副本拉取` → `从副本恢复`（**命令 ID 不许改**，只改显示名）；预览里同时显示两侧文件数与大小 | 便宜、直接对症"盲目模仿远程"。`DIRECTION_OPTIONS`（`settings/model.ts:25-29`）与 `ACTION_LABELS`（`sync/types.ts:124-132`）就是全部落点 |

### P3 —— 收敛两条通道

| 编号 | 要改什么 | 说明 |
|---|---|---|
| **P3-1** | 副本同步与应用同步包共用一套"先算后做 + 冲突裁决 + 回收目录"的核心 | 现在两条通道各写了一遍，行为已经分叉：包通道用指纹判断、有 `skipDeletions`、有强制档单独确认；副本通道用 mtime、什么都没有。这类分叉以后还会再长出来 |
| **P3-2** | 统计口径只定义一处（`一致 / 这次不处理 / 要建 / 要删 / 留着`），预览、通知、状态栏、包报告都从它取 | 顺带解决 P0-4 那类"同一个数字两种含义" |
| **P3-3** | （可选）副本同步也进「更新记录」，标成"副本"这一类 | 用户现在只能在状态栏看到一句"上次同步 …"，看不出"副本这条线走过的路" |

---

## 5. 不建议做的

- **不要砍掉副本通道**：铺库 / 恢复（§1 第 2 条）是包替代不了的，而且它是包唯一的落脚点。
- **不要给副本同步加"每次全量 sha256 校验"**：那是每轮把整个仓库读两遍。要"更硬的判据"就按 P1-1 只核对有差异的那些。
- **不要为了统一把包当同步目标**：README「为什么不让包直接当同步目标」已经把性能账算清了（偏移量回写 → 每次整包重写）。
- **不要为了"看起来对称"而把包通道的指纹/history 机制塞进副本通道**：副本通道不需要 history（它没有"漏了几个包"的概念），它需要的是 P1-1 的"内容核对"与 P2-1 的"副本自述"。

---

## 6. 建议的落地顺序

1. **第一批（P0-1 ~ P0-4）**：都是小改动、纯收益，能单独发一版 0.8.0。大删除护栏是最该先有的。
2. **第二批（P1-1 ~ P1-3）**：判据升级 + 副本编号。这一批做完，"副本和本地到底一样不一样"才有确定的答案。
3. **第三批（P2-*）**：`.lsave/copy.json` 与两种模式。这一批做完，"副本是一个可能被别人写的真实文件夹"这件事才算被正视。
4. **第四批（P3-*）**：收敛两条通道；等前三批稳定之后再动，避免大搬家。

## 7. 这次分析的实测是怎么跑的

探针没有留在仓库里（它只是在演示现状，断言现状会把问题一起钉死）。要复现，建个临时 TS 文件：

```ts
import { runSync } from '../src/sync/runner';   // 传 SyncHost：vaultRoot / stateFile / configDir
```

用仓库里的 esbuild 打包后直接跑：

```bash
npx esbuild tmp-probe/probe.ts --bundle --platform=node --format=esm \
  --target=node18 --outfile=tmp-probe/probe.mjs
node tmp-probe/probe.mjs
```

`SyncHost` 的 `settings` 直接 `{ ...DEFAULT_SETTINGS, targetDir }`，`log` 用 `createLogger(() => 'silent')`，
就不需要 obsidian（引擎本来就不 import 它）。

**实现 P0 / P1 时，建议把这五个场景改写成断言**（放进 `test/sync.test.ts` 的新分组），
但断言的是**修好之后的行为**：

- 场景 2 → 断言"副本只被改了时间"时 `plan.actions.length === 0`；
- 场景 3 → 断言仅下载之后 `state.stateId` 变过、且等于重算值；
- 场景 4 → 断言越线时没有 `allowMassDeletion` 就一个文件都不动；
- 场景 5 → 断言仅下载时 `unchanged` 不含仓库独有的文件；
- 场景 1 → 断言第二台机器能读到副本的 `.lsave/copy.json` 并认领基准。
