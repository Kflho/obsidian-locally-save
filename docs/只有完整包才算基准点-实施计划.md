# 只有完整包才算基准点 —— 实施计划

> 用户拍板（2026-10-07）：**"目前导出更新包的自由度太高了，用户容易出错，而且要管理一堆包。
> 更新包只留从完整包到完整包，或从完整包到最新状态的，防止出错。"**
> 追问确认的两条：① **只有完整包才算点，更新包不再产生新点**；
> ② 累积变大**认了**，配一个「该立新完整包了」的提醒。

## 为什么要改

0.11 起用的**基准点链条**模型里，「点」有两种来路：完整包（有文件）、
**更新包落出的点**（没有文件，清单得沿链叠加算）。于是：

- 导出更新包会**顺手落一个新点**，下一份包默认从那个点往外接 —— 链条一环一环长，
  每来回一次就多一个包、多一个点；
- 两个下拉（从哪个状态 / 到哪个状态）把**完整副本 + 链条上每一个中间点**都列出来，
  用户得自己认「第 N 代 · 基准 xxxx」才不会选错（实测踩过：按代选锚，对面报「基准对不上」）；
- 「管理一堆包」：`changes/` 里躺着 39→54、54→55、55→56… 一串小包，少一环就"接不上"。

**新模型把「点」收回到一种东西上：完整包。** 一句话对照 git 更直白了 ——
**完整包 ＝ commit，更新包 ＝ commit → commit（或 commit → 工作区）的 diff**，
而"导出顺手替你 commit 一个"这件事没有了。

## 新模型（三条）

### 1. 点 ＝ 完整包

`state.bundle.fullFiles / fullGeneration / fullHash / fullFile` 的含义回到
**"我站的那一份完整包"**（这份东西真实存在，别人手里也能有）。

### 2. 更新包只有两种形态

| 形态 | 起点 | 终点 | 内容取自 |
|---|---|---|---|
| **差量包** | 一份完整包 | **另一份完整包** | 终点那份包的负载（不是我现在的仓库） |
| **更新包** | 一份完整包 | **最新状态** | 当前仓库 |

两者都是"相对**那份完整包的清单**算差量"：自它以来变过的文件进包、
没了的进 `deleted`。**没有第三种形态**，"从链条上某个中间点往外导"不存在了。

### 3. 更新包不产生新点

| 动作 | 点动不动 |
|---|---|
| 导出**完整包** | **前进**到这份新完整包 |
| 导出差量包（完整包→完整包） | 不动（内容是终点那份的，不是我现在的仓库） |
| 导出更新包（完整包→最新） | **不动**（我还是站在起点那份完整包上） |
| 应用**完整包** | **前进**到这份完整包 |
| 应用差量包 | **前进**到它终点那份完整包 |
| 应用更新包（完整包→最新） | **不动** |
| 应用"应用前存下的那一份"（`parkLocalChangesFor`） | 不动（`frozen`） |

内容记录（`bundle.files`）、世代号（`generation`）、中间版本（`history`）、
目录清单（`dirs`）照旧每次都前进 —— **只有"点"这三件（含 `fullFile`）不再跟着更新包走**。

## 为什么回传照样成立（这是新模型的关键一格）

```
A、B 都站在完整包 F0 上
  A 改东西 → 导出「F0 → 最新」(P1)     A 的点仍是 F0，内容 P1
  B 应用它                             B 的点仍是 F0，内容 P1
  B 改东西 → 导出「F0 → 最新」(P2)     P2 ＝ P1 ＋ B 的改动
  A 应用它：起点 F0 ＝ 本机基准点 ✓ → 收下，落到 P2
```
两边的点**始终是 F0**，所以谁都能接着发、接着收 —— 不必先"重导一份几百 MB 的完整副本"。
累积变大由**用户导一份新完整包**来收口（见下面的提醒），这正是"从完整包到完整包"那一格的用处：
对方还站在 F0 时，用**差量包**把 F0 → F1 一次带过去，不必镜像整库。

## 连带决定

1. **`base` 一律取起点那份完整包的清单**（`ExportOptions.baseFrom` 删掉）——
   接收方就站在那份完整包上，它手里是这个文件的哪一版只有那份清单知道。
2. **`history` 改记「我发出去过的版本」**（`previous[file]`），不再是 `base`。
   为什么要改：默认那条路的 `base` 从"我上次导出的样子"变成"起点完整包里的样子"之后，
   如果 `history` 还记 `base`，它就退化成"起点的版本"，起不到作用了。
   它的用处有两处，都要保住：
   - `apply.ts` 的 `normal` 档：本地停在"对方发过的中间版本" → 不算本地改动，直接覆盖；
   - **严格档**：判断"本地是不是动过"（决定要不要先备份一份进回收目录）时也认它 ——
     新模型下接收方停在 F0 与最新之间某一版是**常态**（他应用过上一份更新包），
     拿"跟 F0 不一样"当"本地改过"会满屏多余的备份与"覆盖本地改动"的报数。
3. **起点下拉只列完整副本**；`points.ts`（链条上的点）整个删除。
   `BundleHeader.viaHashes` **只读不写**：老包还认它，新包不再生成
   （新模型下"我这一点在不在包的覆盖范围里"由 `checkAncestor` 里
   "算一遍落点"那条按**内容**判，比按来路认更准）。
4. **`state.bundle.pointConfirmed` 删除**：它的语义是"这条链上的点是我导的还是我应用的"，
   点变成完整包之后不存在这个问题（完整包自己就是权威，指纹可以现算）。
5. **同一份起点只留最新那一份更新包**（`removeSupersededChanges` 重写）：

   | 新包 | 旧包 | 处置 |
   |---|---|---|
   | 完整包 | 更新包（世代不比它新） | 删（完整清单取代得了它）—— 不变 |
   | 完整包 | 完整包 | **一律不碰**（那是你的还原点）—— 不变 |
   | 更新包 | 同一份起点、同为"到最新"、**也是我导的** | **删旧的**（新的是累积的、内容更新） |
   | 更新包 | 同一份起点、同为"到最新"、**别的机器导的** | **留着**（那是对方那一半改动，删了就丢） |
   | 更新包 | 别的起点 | 留着（站在那一点上的机器要用它） |
   | 任何 | 回退环（落点号 ≤ 起点号） | 留着（正向导出生不出来）—— 不变 |
   | 任何 | 别的血脉 / 读不出头部 / 世代比新包新 | 留着 —— 不变 |

6. **自动收包（`incoming.ts`）按基准收，同一基准只应用最新那一份**：
   新模型下应用完"基准 → 最新"的包之后**基准点不前进**，
   老循环会拿同一个基准再匹配一次 —— 那可能把**更旧的**那一份又应用一遍（内容回退）。
   规则改成：同一基准的候选里取**终点世代最大**的那一份应用；应用完就换下一个基准
   （其余同基准的旧包记一笔"已被更新的取代"，不再动手）。

## 提醒：「该立新完整包了」

新模型下"更新包自起点那份完整包累积"，攒大了就该换基准（这也是包变大的唯一节制阀）。
- 设置项 `bundleSizeWarnLimit`（MB，`0` ＝ 不提醒）：0.11 删掉过它，现在它又有前提了，
  按老名字回到设置里（旧 `data.json` 里那个字段正好接着用）；
- 判断时机：**包写完之后**看这一份的 `payloadBytes`（＝ 自起点以来要搬的字节数）；
- 落点：导出结果对话框里说一句（"自第 N 代那份完整包以来已经攒了 X MB，
  建议导一份新的完整副本当基准"）＋ 通知一句；导出**预览**里也提前说一句。

## 已知后果（写清楚，别当成 bug）

1. **回传包里会带上对方刚发来的那些路径**（"回声"）：基准不再前进，那些路径相对那份完整包
   仍然算"变过"，所以 B 的回传包会把 A 那一半原样带回去。代价是包大一点；
   **数据不会错**（A 应用它时那些文件通常一模一样，一个动作都不会发生），
   而且**换一次基准就自然收口**。老链条模型靠"点一起往前走"躲开了这个，
   新模型用「提醒立新基准」换掉了那套复杂度 —— 这是有意的取舍。
2. **本地改动不会被回声盖掉**：手动应用前会先把本机改动存成一个包（`parkLocalChangesFor`），
   自动应用那条路只收"不会覆盖本地改动"的包（`isDestructivePlan`）。
   所以最坏情况是"你那一半被存进了一个包"，不是丢东西。
3. **取代规则必须带"同一台机器导的"这个条件**（`header.source.copyId`）：
   两份"同一份起点 → 最新"的包，如果来自不同机器，装的是**各自那一半改动** ——
   删掉任何一份就是丢数据。自动收包同理：同一基准上**按源头分组**，每组取最新那一份，
   不同源头的都要应用。
4. **`history` 有上限（每文件 8 条）**：超出的最老版本认不出来时，严格档会当成本地改动
   备份一份（进回收目录）—— 不是丢数据，只是多一次备份与一行报数。

## 新旧兼容

- **旧状态文件**：`fullHash` 可能仍是一个"链条上的点"（不是完整包）。
  默认起点就是"状态里那一份清单"，所以**照旧能导**（包头部记那个指纹，
  站在同一个点上的对方照样收）；从此以后点只在完整包上动，下一次导/应用完整包就自然归位。
  `pointConfirmed` / `viaHashes` 留着不读（或不写）即可。
- **旧包**：`checkAncestor` 的三条例外一条都不动，链条时代发的包照旧收得下。
