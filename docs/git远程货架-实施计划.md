# Git 远程货架 —— 功能更新方案（0.15）

> 用户的想法：**"之前 Remotely Save 的问题很大程度上就是因为 Obsidian 库太大；
> 现在我们已经改成更新包的形式，可以尝试用 git 同步了。"**
>
> 这份方案回答三件事：git 该搬什么、该放在哪一层、怎么把这套东西接进现有的一条通道里。
> 核心机制已经在本机用临时裸仓库验证过（见文末「验证结果」与「已核实的事实」）。

## 一句话结论

**git 只当"货车"，不当"裁判"。**

仓库里**只有 `.lsave` 包文件**，git 负责把它们在几台机器之间搬来搬去；
"谁站在哪一份基准上、这个包能不能收、收下会不会删东西"仍然由包头部
（基准指纹 `baselineHash` ＋ 状态编号 `stateId`）说了算，一行代码都不交给 git。

整库永远不进 git。**包文件夹就是那个 git 仓库的工作区**（下称"货架"）。

## 为什么"现在"才成立（四条性质）

1. **日常要搬的量已经被更新包压小了**。库多大只影响"导完整副本"（偶尔、手动），
   日常一次只有几十 KB 到几 MB —— 这正是 git 擅长的量级。
   Remotely Save 的痛点是"每次同步都要对整库做一遍网络往返"，不是"库大"本身。
2. **包文件写下就不再改，名字还带随机 6 位**（`<仓库名>-<完整|更新>-<世代区间>-状态<16位>-<6位>.lsave`）。
   于是 git 眼里的合并只有"新增一个整文件 / 删掉一个整文件"两种，
   两个操作的对象永远不同名 —— **合并天生无冲突**。
3. **同一份起点上，我的新包是累积的**（0.14 的"点＝完整包"模型），
   旧的那份被我这份全说了；而清理只撤下**我自己导的**包（`removeSupersededChanges` 按 `source.copyId` 认人），
   别的机器那半份改动永远不碰 —— 所以"删除会随 git 传播"这件事是安全的。
4. **有"点"可对**。0.14 之前是链条模型（少一环就接不上），那种东西放进 git 会天天打架；
   现在一份更新包自带"起点指纹 ＋ 落点"，对端站错点直接拒收并指路，
   git 只要把文件送到，剩下的是确定性计算。

> 一句话对照：**完整包 ＝ commit，更新包 ＝ commit → 工作区的 diff，差量包 ＝ commit → commit 的 diff。**
> 既然我们本来就在搬 git 形状的东西，那就让 git 搬。

## 为什么不是"把库放进 git"（另一条路，否决）

| | 整库进 git | 包进 git（本方案） |
|---|---|---|
| 每次搬多少 | 所有变过的文件（含 `.obsidian/`、附件） | 一个 `.lsave`（几十 KB 到几 MB） |
| 谁来合 | git 的三方合并 → Markdown 里出现冲突标记、二进制直接没救 | 不需要合：包是确定的状态，只认基准对不对 |
| 仓库体积 | `.git` 里躺着整库历史（图片/PDF 各存一份），很快上 GB | 只有包的历史，可随时换仓库 |
| 与插件现有模型 | **两套基准**（git 的 HEAD ＋ 插件的基准点）互相打架 | 一套：包头部就是唯一真相 |
| 和 0.8.0 的决定 | 重新造一条通道，基准/冲突/删除各实现一遍 | 同一个通道，只换运输工具 |

0.8.0 砍掉「同步到本地副本」时留下的那句话仍然有效：
**两条通道各自实现一遍基准 / 冲突 / 回收 / 删除传播，分叉出的行为差异已经交过一次学费。**
所以这次**不加通道，只给现有的包加一个运输方式**。

## 0.15.0（内建 git 传输）

### 概念

```
        ┌──────────── 私有 git 远程（GitHub / Gitee / 自建 / NAS 裸仓库）────────────┐
        │   full/…lsave   changes/…lsave   （只有包，没有笔记）                    │
        └───────────────▲───────────────────────────────▲──────────────────────────┘
                        │ push                          │ push
              ┌─────────┴─────────┐         ┌───────────┴─────────┐
              │ A 机的货架（包文件夹）│         │ B 机的货架（包文件夹）│
              └─────────┬─────────┘         └───────────┬─────────┘
                        │ pull（每 N 分钟）              │ pull
                  留包 / 应用（现有引擎，一个字都不改）      自动应用（现有 sweepIncoming）
```

- 货架 ＝ 设置里那个「同步包文件夹」，它本身就是一个 git 工作区；
- 远程里**只有一个分支**（默认 `main`），所有人往同一份上推；
- 一台机器 = 一个提交作者，但"谁站在哪"**不看 git**，看包头部。

### 一次同步（唯一的写入口，`src/git/sync.ts`）

1. **自检**：`git rev-parse --show-toplevel` 必须等于货架路径。
   不等 → 说明这个文件夹属于另一个仓库（比如库本身是个 git 仓库）→ 报错、什么都不动。
2. **收拾残局**：`.git/rebase-merge` / `MERGE_HEAD` 还在（上次卡住）→ 先 `--abort`。
3. **暂存 + 提交**：`git add -A`（`.git/info/exclude` 保证它只碰得到包：完整包与回收站都被挡住），
   没有变化就跳过。提交信息写这一轮有几个文件。
4. **拉取**：`git fetch origin <branch>` →
   能快进就快进；两边都有提交 → `rebase`（**没有共同祖先也能直接接上**，实测）；
   rebase 真失败才退回 `merge --allow-unrelated-histories`，再失败就收拾干净并报错。
5. **推送**：`git push origin HEAD:<branch>`。被拒（另一台刚推过）→ 回到第 4 步再试一次，最多两轮。
6. **报账**：这一趟新增了哪些包（给自动应用用）、推上去没有、现在领先/落后几个。

**为什么用"每 30 秒看货架脏不脏"的节拍，而不是在导出/应用里埋钩子**：
货架有三类写入者 —— 导出（含"应用前先把本机改动存成包"）、合并相邻更新包、用户手动删包。
一个"脏了就提交"的节拍能一次覆盖全部，也天然处理"上次推送失败"的重试；
引擎（`bundle/`、`sync/`）因此**一行都不用知道 git 存在**（继续保持它们不 import obsidian 的规矩）。

### 设置项（新页面「Git 远程」）

| 键 | 默认 | 界面上那一行说明 |
|---|---|---|
| `gitEnabled` | 关 | 把包文件夹接到一个 git 仓库：一台机器推上去，另一台拉下来 |
| `gitRemote` | 空 | 远程地址（HTTPS 或 SSH）。仓库里只放包，别放笔记 |
| `gitBranch` | `main` | 分支名 |
| `gitPullMinutes` | `5` | 每隔多久拉一次（`0` ＝ 只手动）。拉下来之后，自动应用那条路照旧在 30 秒内处理 |
| `gitAutoPush` | 开 | 货架里有新包就推上去（留包、应用前存包、合并包之后都算） |
| `gitMaxFileMb` | `50` | 单个包超过这个大小就不推，只在本机留着（`0` ＝ 不限） |
| `gitPath` | 空 | `git` 程序的路径；留空＝从 PATH 里找 |
| `exportDiffOnRebaseline` | 开（**只在 git 开着时生效**） | 换基准时顺手导一份「旧基准 → 新基准」的差量包（很小），放进货架 |

`gitRemote` / `gitBranch` 的校验：留空时其余项灰掉并提示去填；`gitRemote` 只在"接入"动作里写进
`.git/config`，**不自动改**已有的 remote（写进去 = 以后往那儿推，等于把笔记内容发出去，必须用户明确点）。

**完整包一律不推**（用户拍板：太大）：`.git/info/exclude` 里常驻 `/full/`，`git add` 永远碰不到它，
也没有开关 —— 完整包继续用 U 盘 / 网盘手动搬。第一次接入也一样，只把更新包提交上去，
并如实报一句"有 2 个完整包没推，共 1.2 GB"。
唯一的例外：用户自己手动 `git push` 过一份完整包 —— 它在远程就是 tracked 文件，
拉下来照常收、撤下也照常同步（测试里守着，见文末用例 12）。

### 入口

- **设置 → Git 远程**：
  - **页首一行「当前状态」**（动态文案，见 `describeGitConnection`）：`还没填…` / `还没接入…` /
    `已接上 … · 12:31 同步过` / `上次同步失败：…`。点「看详情」看完整信息；
  - `接入这个远程…`（首次）：空文件夹 → `git clone`；已有包 → `init + remote + fetch + merge`；
    然后报"提交了 N 个包 / 共 X MB / 推上去没有"。
    **只提交更新包**（完整包永远不进 git，留在本机），并如实报一句
    "有 2 个完整包没推，共 1.2 GB，用 U 盘搬"—— 别让第一次点"接入"就往上怼几个 GB；
  - `测试连通性`：**不依赖本地仓库**，直接对设置里的地址跑 `git ls-remote` ——
    git 装没装、远程通不通、SSH / 凭据行不行一次说清（失败给下一步）；
  - `SSH 接入…`：找 / 生成 `~/.ssh/id_ed25519`、复制公钥、用 `gh ssh-key add` 一键添加（登录过 gh 时）、
    `ssh -T git@<host>` 测登录。**私钥不出插件**，只读 `.pub`；
  - `现在同步一次` / `让对面和我一致` / `让我和对面一致` / `打开货架文件夹`。
  - **按钮不变灰**：没填全时点了直接说差什么、下一步做什么（变灰只会让人问"为什么点不了"）。
- **命令**：`sync-now`「**立即同步**」是用户面前的主入口（左侧栏第一个图标同一个动作）：
  导出包（自动留包开关开了按它；都没开时有基准导更新包、没基准导完整包）→
  写 peer 状态 + 提交 + 拉 + 推 → 应用拉下来的安全更新 → 一句总结。
  `git-sync` 仍是"只推拉不导出"；`upload-to-copy` / `download-from-copy` 两个老 ID
  接到"推 / 拉"上（见下面「双向信息与方向」）。
- **状态栏**：在现有那句后面补一小段 —— `· git 12:31 同步过` / `· 2 个没推上去` /
  `· 对方：一致` / `· 对方：不同步`。失败只说一句，不刷屏。
- **通知**：拉下来 N 个包时说一句；自动应用的结果照旧由 `reportIncomingSweep` 报。

### 三条流程

1. **留包之后**：不用做任何事。下一个 30 秒节拍看到货架脏了 → 提交 + 推送。
2. **定时**：`main.tick()` 里在"收包"之前先跑一次 git（到了 `gitPullMinutes` 才走网络），
   拉下来就紧接着 `checkIncomingBundles` —— 新包在同一拍里被看见，不必等下一个周期。
3. **应用之后**：应用前存下的那份包（`parkLocalChangesFor`）同样在节拍里被推走；
   它是"给对方的那半份改动"，本来就该发出去。

### 换基准这条路必须补平（`exportDiffOnRebaseline`）

新模型下换基准 = 导一份新完整包。完整包**太大、默认不推**，于是对端手里没有新基准的包，
下一次更新包会被 `checkAncestor` 拒收 —— 这条路不补，git 货架在第一次换基准时就断了。

补法很小：**导完整包时，顺手再导一份「旧基准 → 新完整包」的差量包**（内容取自新包的负载，
通常只有几 MB），推进货架。对端收下、应用完就站到新基准上了（**不需要手里有完整包**：
`apply.ts` 的 `landedOnBaseline` 只认清单与指纹）。这一条一条链就闭合了：

```
A: 改东西 → 导完整包 F1（本地，几百 MB）+ 差量包 F0→F1（几 MB）→ 推
B: 拉 → 应用 F0→F1 → 两边都在 F1 上，状态编号一致
```

注意：应用那一步如果会动到本机改动，**自动应用会停下来让人点**（安全边界不变），
点"应用"时现有流程会先把本机改动存成包 —— 那份包随后也会被推上去。

### 删除跟着同步（用户拍的板：两边要一致）

**撤下一个包就是一笔提交**：本机把包挪进回收站 / 引擎自动清理，下一次同步把删除推上去，
对面拉下来也删掉。除了不跟踪的 `full/`（完整包本来就不在 git 里），两边的包集合最后**收敛到同一份** ——
端到端测试的收尾那两条就是比这个（跟踪列表 + 状态编号）。

- **自动清理**只删"我自己导的、被同一份起点的新包取代的"更新包，以及"被我自己的完整包取代的"，
  别人的半份改动永远不删（现有 `removeSupersededChanges` 已经按 `source.copyId` 认人）；
- 撤下的包在**本机回收站**还留一份，远程历史里也永远在（`git log` 能翻出来）；
- **用户手动"挪进回收站 / 彻底删除"**要弹一句确认：「其他机器也会看不到这个包（历史里还在）」，
  并在 0.15.x 给一个「从远程历史取回…」的入口；
- 万一远程里有一份**被手动推上来的完整包**（tracked），删它同样会传到对面 —— 跟踪文件不受 `/full/` 排除影响；
- 不做 force push：历史只往前走。

## 双向信息与方向（0.15.0 已落地）

包本身是**单向广播**：对方不应用，你永远不知道它到了哪一步。git 货架是共享的，
所以每台机器再往货架里放一份**很小的状态**（不是包、不带文件内容）：

```
<货架>/.lsave-peers/<copyId>.json
  { stateId, generation, baselineHash, baselineGeneration,
    lastExport: {bundleId, file, target, at}, lastApply: {...}, pending, at }
```

拉一下就能回答三件事：**两边内容一样吗**（`stateId` 相同就是一样）、**我的包对方应用了没有**
（它的 `lastApply` / `stateId` 会变）、**谁还站在旧基准上**。状态栏那半句 `对方：一致 / 不同步`、
「检查环境」里那一行、以及"撞车了没有"都读它。`.git/info/exclude` 因此多放行
`/.lsave-peers/` 与 `/.lsave-peers/*.json`；它仍然**不是第二条内容通道**。

### `syncDirection`（0.8.0 之前那一项，原样请回来）

| 值 | 行为 |
|---|---|
| `both`（默认） | 互相应用：自动拉、自动应用**安全**的更新包；两边都改过时停下来，让你选方向 |
| `upload` | 只推：让对面变成我这样；不应用对方的包 |
| `download` | 只拉：让我变成对面那样；撞车/删除也要点一下方向按钮 |

命令 ID 一个没改：`upload-to-copy` →「让对面和我一致（推上去）」，
`download-from-copy` →「让我和对面一致（拉下来）」。设置页里也有同名按钮。

### 「让我和对面一致」＝ 严格对齐（`ApplyOptions.alignToPeer`）

普通应用的目标是"**我的内容 ＋ 对方的改动**"（互相应用，两边各留一半）。
单向对齐的目标是"**基准 ＋ 包里的条目 − 包点名的删除**"—— 正好是对方那一点：
本机改过的、多出来的文件进回收目录（备份），做完两边 `stateId` 必须相同。
引擎里就一行开关（`contentBefore` 换成 `state.bundle.fullFiles`），
不是第二套合并逻辑；测试 `git-flow.test.ts` 第 5 段守着"对齐后编号一致"。

### 撞车为什么不自动合

两边的更新包都相对同一份基准；自动把两份都应用上去，冲突文件会各留各的版本，
状态编号永远对不上，下一轮还会来回换 —— 正是 Remotely Save 那类"逐文件各改一半"的隐患。
所以 `both` 只自动应用**不会覆盖 / 删除本机东西**的包，撞车时状态栏写 `对方：不同步`，
由用户点一次方向（以谁为准），结果**完全确定**、编号一致。自动"先合再回礼"那套
（park → 应用 → 再应用 park）留到用户试过这一版之后再决定要不要做。

### 硬规矩（写进 AGENTS.md，别越线）

1. **仓库里只允许 `.lsave`**：不提交 README、`.gitattributes`、日志、回收站。
   二进制标记走 `.git/info/attributes`（本地、不版本化），否则两边各自生成的文件会在 rebase 时撞 add/add。
   **完整包（`full/`）一律不推**（用户拍板）：它在 exclude 里常驻，不是开关。
2. **只 stage 包**：`git add -A`，靠 `.git/info/exclude`（`*` / `!` 开头的目录规则 / `!*.lsave` /
   `/full/` / 回收站）把别的都挡在外面；这份 exclude **每次同步前对一遍内容**（用户手改过也能纠正回来）。
   用户自定义包目录时回收站就落在货架里面（`<货架>/.lsave/bundles-trash`），
   exclude 漏一次它就会被推上去（实测过，测试里也守着）。
   完整包（`/full/`）同理：它不是开关，是常驻规则。
3. **不 `git clean`、不 `git reset --hard`、不 `git push -f`**。
   空仓库首次落地用 `fetch` + `merge FETCH_HEAD`（实测可行），**不需要** `reset --hard`。
4. **不自动 init、不自动改 remote**：写 `.git`、换地址都是用户点按钮的动作。
5. **引擎不 import `git/`**：`bundle/`、`sync/` 里继续没有 obsidian，也没有 git；
   调用方（`main.ts`、`ui/actions.ts`）负责把两边接起来。
6. **成败靠退出码**，别解析中文/本地化文案；需要机器可读的用 `--porcelain` / `-z`。
7. **凭据不落盘**：不写 token、不把带密码的 URL 存进 `data.json`；用系统 git 的 credential helper / SSH。
8. **失败退避**：一次失败后 2 分钟再试，连续失败退到 10 分钟；不要每 30 秒弹一条。
9. **串行**：git 同步期间不导出、不收包；应用进行中（`apply.ts` 的 `applying` 暴露一个 `isApplying()`）
   不 pull（pull 可能在应用读某个包时把它挪走）。

### 运行 git 的参数（经验值，照抄就行）

```
env: GIT_TERMINAL_PROMPT=0, GIT_SSH_COMMAND=ssh -oBatchMode=yes, LC_ALL=C
     （用户自己设过 GIT_SSH_COMMAND 就不覆盖；见 run.ts 的 defaultEnv）
第一次建仓时写进**本仓库** config：core.autocrlf=false / core.filemode=false / core.quotepath=false /
  commit.gpgsign=false / advice.addIgnoredFile=false（见 shelf.ts 的 configureShelf）
超时：本地命令 10 秒；fetch/push 60 秒（超时就杀进程并报"网络或凭据卡住了"）
init：git init -b main（老版本 git 没有 -b 就 init + symbolic-ref HEAD）
兜底：git config user.email 读不到时，在**本仓库**写 user.name=Locally Save / user.email=locally-save@localhost
```

两个必须单独处理的分支：

- **远程还是空仓库**（刚在 GitHub 建的空仓库）：`git fetch origin main` 会报
  `couldn't find remote ref` —— 这不是失败，当成"远程什么都没有"，直接 push；
  「检查环境」用 `git ls-remote --heads origin` 判断远程到底有没有这个分支。
- **本地还没有提交、远程有**：`fetch` + `merge FETCH_HEAD`（空仓库会直接快进落地，实测）。

三条容易踩的坑：

- **"脏"的判据是暂存区有没有料**（先 `add`，再 `git diff --cached --quiet`，退出码 1 ＝ 有），
  **不是 `git status` 非空**：被单包阈值挡下的超大包会一直以 `??` 挂着，按 `status` 判会让节拍
  以为每轮都有活。超阈值的包在**暂存之前**就排除掉（不进 index）。
- **没接上 / 没填地址时，自动那条路一声不吭**：只在状态栏写一句"还没接上 git"，不弹窗
  （每 30 秒弹一次会疯）。
- **提交信息别塞太多**：`包：3 个（第 54 代 → 第 55 代）` 这种就够；包名列表放正文前 10 行。

## 失败对照表（每一句都要指下一步）

| 情况 | 说什么 |
|---|---|
| 找不到 git | 没找到 git：装一个 Git（Windows 上是 Git for Windows），或在这一页填 `git.exe` 的路径 |
| 没填远程地址 | 先填远程地址：在 GitHub / Gitee 建一个**私有**空仓库，把地址贴进来 |
| 认证失败 / 连不上 | 连不上远程：先在终端里对货架跑一次 `git -C "<路径>" pull`，成功后插件就能接着用（凭据是系统 git 记的，插件不存） |
| 文件夹属于别的仓库 | 这个文件夹属于另一个 git 仓库（`<top-level>`）：换一个独立文件夹，别把货架放进库仓库 |
| 推送被拒（重试后仍失败） | 远程刚被另一台机器推过，这轮没推上去；下一次会自动重试 |
| rebase 冲突（理论上没有） | 两边的包撞在一起了（极少见）：货架没动，去终端 `git status` 看看 |
| 单个包太大 | `<name>` 有 812 MB，超过单包上限（50 MB），没推上去：完整包建议走 U 盘；要推就调高上限 |
| 超时 | git 60 秒没响应：网络或凭据卡住了 |
| 货架还没接上 | 还没接上 git：设置 → Git 远程 → 接入这个远程… |

## 已核实的事实（写代码时别重新猜；下面每一条都有测试守着）

- `git add -A` 配合 `.git/info/exclude`（`*` / `!*/` / `!*.lsave` / `/full/` / 回收站）
  只暂存包：回收站里的包、笔记、完整包都进不来；`-A` 也能记录删除（撤下就是一笔 `D`）。
- 两边同时推：后推的一方被拒（`fetch first`）—— 这是正常情况；`syncShelf` 会再拉一遍、再推一次。
- 两边各自 init（无共同祖先）：`rebase FETCH_HEAD` 能直接接上（实测），
  `merge --allow-unrelated-histories` 只是兜底。
- 本地还是空仓库、远程已有提交：`fetch` + `merge FETCH_HEAD` 能直接落地（不需要 `reset --hard`）。
- `git clone` 之后所有文件的 mtime 都变成拉取那一刻（所以列表必须用包里的 `created`）。
- 在子目录里 `rev-parse --show-toplevel` 会返回外层仓库 —— 这是"货架是不是独立仓库"的判据，
  而且**要在 init 之前查**，否则 init 会把外层仓库盖住。
- tracked 文件不受 exclude 影响：手动推上来的完整包照样能收，删它也会同步。
- git 2.55（Windows）下以上行为一致；`init -b` 需要 2.28+，老版本用 `symbolic-ref` 兜底。
