## 0. 用户交互文字规范（硬规矩，测试与评审都看它）

**弹窗、界面、状态栏只显示两类文字：① 提示当前状态；② 要求用户操作。**
其余一律不显示（进日志 / 悬停详情 / 「更新记录」）。

具体到这条线（0.16.14 用户报的"右下角不断显示同步远程、右上角不断显示信息"）：

- **例行的后台动作不演过程**：每 10 / 30 秒的 git 对表同步（`syncGitNow(..., { background: true })`）
  不写状态栏、不弹通知；结果只落在状态栏那句总结里（`已推送 12:31 · 对方：一致`）。
- **自动导出**：没有变化、只是写了更新包 —— 不弹通知（日志 + 状态栏）。**完整备份例外**：
  它不进 git、要用户自己复制，必须说一句。
- **自动接收**：例行写入只在状态栏顶一句（`flash`，8 秒后自己回到上次结果），不弹通知；
  **删了本机文件 / 从基准恢复了本机误改 / 走过强制回退**才弹。
- **git 拉下来的包**不单独报数（真正要说的由接收那条路说）；只有「仅推」例外 ——
  那个方向不看接收文件夹，没人会替你应用，得说一句。
- 要用户动手的照旧说：完整备份要手动应用、起点不一致、包应用失败、设置没填全、确认框。

**为什么**：频繁的"成功"提示会把真正的异常淹掉；用户的原话是"哪些是用户要看的"。
判断标准是"用户需不需要知道 / 需不需要动手"，不是"这件事发生了没有"。

## 1. 接收按「方向」分

`bundle/incoming.ts` 的 `IncomingPolicy` ＋ `ui/actions.ts` 的 `incomingPolicy`；
`main.tick()` 每 30 秒调一次 `checkIncomingBundles()`。**方向是硬边界，不只是提示文案**：

- `upload`（仅推）：**根本不看接收文件夹**（`wantsIncoming` 为 false）—— `autoApplyIncoming`
  只对没开 git 的机器有用；
- `download`（仅拉）：**收到就应用**（完整备份也收）—— `force` ＋ `allowFull` ＋
  `apply: { strictness: 'mirror', alignToPeer: true }`，目标是对面那一点，本机被覆盖 / 删掉的
  东西进回收目录（用户拍板："直接应用，不弹窗"）。这个方向**不导出任何包**
  （`isReceiveOnly()`：启动 / 定时 / 保存后的自动导出、「立即同步」、回传全都不写；
  手动「导出同步包…」仍是用户的明确动作）；
- `both`（双向）：先弹**一句确认**（`confirmIncomingApply`），确认后才应用；取消记
  `dismissed`，同一个包不再问。**用户点了「应用」＝ 看过那份账了**，后面 `isDestructivePlan()`
  保底**不能再拦**（`handleIncoming` 里的 `confirmed`）—— 再拦一次等于让他白点，包还会被记成
  `needs-review` 再也不被挑出来，两边代数就永远差着一截（用户报的"一台 108、一台 109，
  点同步都提示已经最新"）。应用完只有"本地还差一点"（`stateIdCompare !== 'match'`）才回传；
- **`both` + `autoApplyIncomingBoth`（无人值守）的口径变过三次，别再退回前两种**：
  - ≤0.16.11：`mirror + alignToPeer` —— 把仓库整片变成对面那一刻，**正在写的东西被覆盖**
    （用户报的"写完又被回退了"）；
  - 0.16.12：`normal + local-wins` —— 本机这半保住了，但同文件两边都改时**对方那半被静默丢掉**
    （场景 3 实测出来的）；
  - **0.16.13 起：`normal + keep-both`** —— mtime 新的占原名、旧的存成**冲突副本**，
    两份内容都在。**同文件并发编辑只能做到"留两份"**（按文件粒度），行级/块级合并没做，
    别指望它自动合出一份。
  - **0.16.14 补**：这条路上的"本地删除"必须保得住 —— 三方比对的祖先用**我上次交换到的样子**，
    不要被包自带的旧 `base` 顶掉（见 `约定-基准与应用.md` 第 3 节与 `test/local-delete.test.ts`）。
- **差分更新包一律按严格镜像应用**（0.18，`handleIncoming` 里那一段）：合并档会留下本机那一半，
  而新基准清单只收"**真的写成了一致**"的条目 —— 冲突里赢的是本机那一版，那个路径就按**祖先版本**
  记进新基准，令牌既不是旧基准也不是包里报的 `targetBaselineHash`，之后对面按新基准导的包
  这台机器一律判不上、**永远卡住**。镜像档下结果是确定的 ＝ 包里那一点。
  代价：本机被覆盖 / 多出来的文件进回收目录（`.trash/locally-save/`，严格档必然备份）；
  自动接收这条路**不额外 park**（那会在后台凭空写包），要"动手前先存一份"走「打开同步包并应用…」。
  守护：`test/rebaseline.test.ts` 第 5 组末尾那条对照（合并档 vs 接收那条路）。
- **应用成功之后补一份本机的基准完整备份**（0.18.1）：应用差分更新包会变成一份本机没有包文件的基准上
  （`fullFile` 为空）。`checkIncomingBundles` 在应用成功之后跑 `ensureLocalBaselineBundle` ——
  核对校验值对得上才留（版本不涨、`fullHash` 不变），不一致就不留、如实说。
  用户要的是"点一次同步，两边都拿着同一份完整备份，再继续更新"。
- 没开 git：退回 `autoApplyIncoming` 的老边界 —— **只自动应用"不会动到本地已有东西"的更新包**
  （`isDestructivePlan()`），完整备份只提示一句；
- **默认策略一个字没松**：不传 `force` / `allowFull` / `apply` 时行为与 0.14 完全一样
  （`test/incoming-direction.test.ts` 守着）；
- **完整备份**：只有「仅拉」开 `allowFull` 才自动镜像；别的方向 / 没开 git 时只提示一句。

## 2. 按基准收，同一基准按源头分组取最新（`sweepIncoming`）

只挑"起点正好是本机当前使用的**那一份完整备份**"的包（`checkAncestor` 那条硬规矩）。
同一份基准上**按源头分组**（`header.source.copyId`），**每个源头只取终点版本最大的那一份**应用；
同源的那几份旧的记一笔"已被更新的取代"就不再回头 —— 不能"应用一份就换下一个基准"：
更新包**不推进基准**，原地再挑会挑到更旧的那一份，等于把内容往回退一格。
差分更新包会把基准推到它终点那份完整备份上，接着看下一段；不同源头的各自都要应用 ——
那装的是各自那一半改动，漏一份就丢数据。

- 无法应用的（缺那份完整备份）**不记账、不动它**，只提示一句，而且同一个包只提示一次
  （`ui/actions.ts` 的 `waitingNotified`，重启后最多再提示一遍）；
- 默认策略下碰上"要删文件 / 要覆盖本地改动"的那一份停在那儿并报一句（其余照旧搁着）；
- **跳过**：头部读不出、我导出或应用过的（`bundleLog`）、源头就是我这台机器
  （`header.source.copyId === state.copyId`）、`state.incoming` 里记过的 —— **每个包只处理一次**。
  **只有一种例外**：手动的「立即同步」会把记成 `needs-review` / `failed` 的重新挑出来
  （`pickIncoming` 的 `retryBlocked`）—— 用户明确点了同步，就该再试一次；
  不这么做，一个被拦下的包会永远躺着，两边代数差一截而每次同步都说"已经最新"（用户报的 108 / 109）。
  `applied` 与 `dismissed` **不重挑**；
- "已经有了"的判定要把**空文件夹补建**算进去（`report.foldersToCreate`）：只按文件动作判，
  一份"新建空文件夹"的包会被记成 `already`、再也不应用 —— 空目录也是内容；
- 处理结论一律落盘（`state.incoming`，只留最近 `INCOMING_LIMIT` 笔；写之前**重新读一遍状态**，
  别把 apply 刚写的东西盖掉）；记不下只是"下次再提示一遍"，不该让已经成功的应用看起来失败；
- **失败的包自动重试**（`MAX_FAILED_ATTEMPTS = 3` / `RETRY_FAILED_AFTER_MS = 10 分钟`）：
  包失败往往是一时的（还没复制完、正在重写、完整备份临时不在），记成 `failed` 之后不再挑它，
  用户不点两边就永远差一截。手动「立即同步」不受次数限制。

## 3. 一拍里的顺序与"正在打字"

`main.runTick()`：**先 git 推送和拉取**（拉下来的包紧接着就能被看见）→ 再接收 → 最后才考虑导出。

- 刚应用过东西的那一拍**不再导出** —— 那等于立刻生成"回传包"，两边容易来回搬运
  （回传走欠账式那一套）。但那一拍要**立刻把新状态推上去**（`main.runTick` 里应用完再调一次
  `maybeGitSync`；「立即同步」里是应用完再 `syncGitNow` 一次）：peer 文件里记着内容校验值，
  不推的话对面要等下一次节拍（30 秒）才看得到"我已经应用了"。
- **正在打字就不自动动仓库**（0.16.11，用户报的"我刚才打字被强制同步了"）：
  `saveDirtyAt`（`vault.on('modify')` 记的）最近 `EDITING_GRACE_MS = 10 秒` 内有过改动 →
  **只做 git 推送和拉取，接收与自动导出跳过这一拍**。① 接收会**覆盖文件**，正在编辑的笔记被对面那版
  盖掉、光标跳走、未保存的字可能丢；② **不能"逐个文件跳过"** —— 接收是整包严格同步，
  跳过一个文件就等于把包送到的状态改了一半（`stateId` 当场不一致），比晚 30 秒同步糟得多。
  手动同步（命令 / 按钮）不受这条约束。

## 4. git 远程仓库：只搬包

工作区就是同步包文件夹，仓库里只有 `.lsave` 与 `.lsave-peers/*.json`；
**不自动 init、不自动改远程**：那两件事只在「接入」动作里做，别的路径只读不写。
完整备份太大，走 `.git/info/exclude` / 远程仓库自己的 `.gitignore` 排除（`/full/`），不进 git。
拉取到的包不在这里应用 —— 交给 `checkIncomingBundles`，安全边界仍然只有一份。

### 远程仓库可以是「别的仓库里的一个子目录」（0.16）

用户拍板：更新包用 git 同步、放进 `kf-personal-data`，完整备份仍归网盘。
`git/shelf.ts` 的 `readShelfLayout()` 判形态：仓库根＝它自己 → 独立远程仓库；仓库根在它上面 →
`hosted`（子目录形态）。**不在别人的仓库里 init**（那会造出嵌套仓库），也不再因为
"落在别人的仓库里"一律拒绝。子目录形态的纪律（写错一条就是把用户的仓库搅坏）：

- **只碰自己那一段**：`git add -A -- .`、`git commit ... -- .`（cwd 就在远程仓库里），外层仓库里
  用户暂存 / 没管过的文件一个都不碰；`shelfIsDirty` 也只问远程仓库这一段；
- 过滤规则写在**远程仓库自己的 `.gitignore`**（`full/`、`.lsave/` 不进仓库），
  **不动外层的 `.git/info/exclude`** —— 那是仓库级配置，会连别人的文件一起藏起来；
- **拉取只允许"限定范围的对齐"**：外层仓库是用户的，所以 rebase **只在闸门过了之后**才做。
  闸门：
  - **远程仓库之外不许有未提交改动**（`git diff HEAD --name-only -z`，整个仓库；**必须 `-z`**：
    带中文的包名默认会被 git 加引号转义，拿 `startsWith` 比会把远程仓库里的包误判成"远程仓库之外"；
    用户就是这么撞上的）—— rebase 要一棵能动的树，插件不替用户 stash；
  - **已提交**的改动不拦（哪怕动的是远程仓库之外）—— rebase 会接着演下去，冲突就 `--abort`，
    用户的活不会丢（0.16.7 之前把"已提交但不在远程仓库"也算越界，结果两台机器各改各的
    `test-status/<HOST>.json` 就永远同步不过去）；
  - 闸门不过 → 报错并报出**具体的那个路径**，绝不 reset / 合并用户的仓库；过闸就
    `git rebase FETCH_HEAD`，撞上"同一批文件两边都动"就 `--abort` 再报错（指路「刷新包」）。
    外层仓库里有没做完的 rebase / merge 时照旧报错，**绝不 abort**；
- **「刷新包（对齐远程）」比 rebase 更狠**（它是 `reset --hard`，会真的丢掉本地提交），
  所以那道闸门**额外**要求"没推的提交每一笔都只动远程仓库那一段"（`assertOnlyShelfCommits`）；
  动过远程仓库之外的**一律拒绝**。流程：`fetch` → 两道闸 → `reset --hard origin/<分支>` +
  清"本机删过"的记号；导出窗 / 导入窗底部与命令 `refresh-bundles` 都能点到；
- 远程地址照样比对、**绝不悄悄改**；子目录形态下不给别人的仓库加 origin；
- 推的是外层仓库当前**整个分支**（git 只能推分支）：用户自己没推的提交会一起上去，
  界面与 `ShelfStatus.hosted` 上写明这一点。

**删掉的包必须哪儿都不再出现**（0.18.2 改的语义，用户拍板："正确逻辑应该删掉以后远程和其他终端
都不再出现"）。两种删法走同一条路：

- 插件里点的（移到回收站 / 彻底删除 / 被新包取代 / 自动整理）：记过记号（`git/removals.ts`），
  照旧提交并推；
- **在文件夹里手删的**：旧逻辑一律当成"我这份副本丢了"、从 HEAD 恢复回来 ——
  代价是**永远删不掉一份包**（删了 30 秒后又回来，真机 2026-11-04 的 `320 → 650`）。
  现在改成 `salvageDroppedBundles`：先把 HEAD 那一版取回来**移到本机回收站**
  （`bundles-trash/<时间戳>/`，误删能恢复），再记记号把删除提交并推走；
- 对表文件 `.lsave-peers/*.json` 例外，照旧从 HEAD 恢复（它是状态不是包）。
- 想重新拿回远程上的包，走「刷新包（对齐远程）」—— `reset --hard`，用户明确点才做。


## 5. 欠账式回传：应用完不许立刻生成"回传包"

`state.pendingReturn`（`bundle/apply.ts` 写、`bundle/export.ts` 结清）。更新包是累积语义 →
每台只握着改动的一半，收下对方的之后确实得把自己这半发回去；但**一应用就自动导一个包**会
互相套娃：对方收到那份又生成一份、再传回来，两边无限来回（用户报的"无限套娃"）。

所以只**记一笔账**（时间、包名、文件/仓库、改动数/删除数），通知、应用报告、更新记录里
都如实说"你这边还有 N 个改动没发出去"，等用户下次导出更新包（手动，或自动导出）时
**从"应用完变成的那个状态"往外延伸**（起点仍是本机当前使用的这一份完整备份）—— 那一份里只有我这半；
对方仍使用**同一份完整备份**，收下就齐了。任何一次成功导出都把账清掉（`exportBundle` 一处）。

应用报告里的 `report.pendingChanges / pendingDeletes` ＝"我这边对方还没有的改动"，
先摊开给用户看；没有基准时是 `null`，界面上不显示那行 —— 那时他也导不出更新包。

**「收到几个包」只算从远程来的**（`git/sync.ts` 的 `pulledBundles`）：取 `baseHead..HEAD` 里新增的
`.lsave`，`baseHead` 在**提交之后**读。别退回"同步前后各拍一次磁盘快照再相减"：那个口径会把本机在
同步窗口里自己写下的包（导出的包、`full/` 里的完整备份、应用前存下的那一份）算成"从远程收到" ——
界面对着一台仅推的机器说「已从 Git 远程接收 1 个同步包」，而另一台根本没发过东西
（2026-11-23 现场：桌面推走了一份 70 MB 的「应用前先把本机改动存成包」，笔记本一路提示收到）。
`listBundlePaths` 同时跳过回收站与 `.lsave` 目录，本机保管的包不进这份账。

**撤下的包也报数**（`GitSyncReport.deleted`）：远程删掉、这台机器跟着删的包。口径与上面同一套 ——
`baseHead..HEAD` 里被删的 `.lsave`，`baseHead` 在提交之后读，所以**本机自己删的包不算**
（那一笔已经在 `baseHead` 之前进了提交）。两条通道都填：单提交模式由 `adoptTree` 直接给出
（它先把 HEAD 那一份移进回收站再删），普通模式走 `removedBundles`。

- 手动同步那句写 `撤下 N 个包`；后台那趟**只在这一趟真有撤下时**弹一句
  `远程撤下了 N 个同步包。` —— 那是删掉本机已有的文件，按第 0 节就要说话；
- **提示里不写去处**：单提交模式会先把包移进 `<同步包文件夹>/.lsave/bundles-trash/`，
  子目录形态是 git 合流直接删掉（插件没经手、回收站里没有）。写死一处就对另一种形态说了假话；
- 状态文件记 `state.git.deleted`，设置页的连接说明与「各台电脑同步状态」里跟着显示；
- **对表文件不算包**：`.lsave-peers/*.json` 照样取回、照样处理，但「收到 / 撤下 N 个包」两个数都不数它
  （数进去状态栏会凭空多一个包，与只数远程 `.lsave` 的口径冲突）。

**单提交模式还要收拾本机**（`git/sync.ts` 的 `pruneLocal`）：每次同步都会用 `update-ref`
换一个无父提交，旧提交仍挂在 reflog 上，`.git` 照样会变大。所以同步之后（半小时一次）
`git reflog expire --expire=now --all` 再 `git gc --prune=now` —— 远端只有一个提交，本机也不留旧对象。

**写包与同步互斥**（0.18.3）：手动导出（`ExportBundleModal`）也要占 `plugin.bundleBusy` ——
自动导出一直占着，手动这条路过去不占。`writeBundle` 直接写最终路径，不带锁时后台那趟同步可以在
写包途中 `git add -A`，把**写到一半的包**提交上去（对端拉到是坏包，还会一直躺在远程仓库上）。

## 6. 状态栏：一句话，两个来源

`ui/status.ts`（0.15.3 起）：

- **前半句 = git 推送和拉取本身**：`state.git` → `已推送 / 已拉取 / 已完成推送和拉取 / 远程已是最新 / 同步失败`。
  **不要写"已同步"**：推上去只说明远程有我的包，对方没拉、没应用之前内容不一定一样；
- **后半句 = 内容状态**：`.lsave-peers` + `state.stateId`（`git/peers.ts` 的 `peerMatch`）
  → `对方：一致 / 不同步 / 待上报 / 没上报`。`待上报` 是"我这边刚应用/导出，它还没报新状态"，
  不能当成"不同步"。多台逐台计数；
- 没有 git 时才退回 `bundleLog` 的最后一条（`describeLastActivity`）；
- 应用完必须走 `refreshStatusBar`；**别手写 `setSummary` 把"对方：…"盖掉**；
- 悬停显示每台详情；点状态栏 / 命令 `sync-status` 打开「各台电脑同步状态」；
- 启动时 `restoreLastActivity()` 从状态文件读回来 —— 否则一重启就变回"尚未导出"。

**进度**：`SyncProgress` 的 `done / total` ＝ **已经写进包里的文件数 / 总文件数**，从 0 数到总数，
多一个含义都不许有。`writeBundle` 每搬完一个文件回调一次；开跑先报一次 0，并 `await yieldToUi()`
**强制让一帧**（DOM 写进去得等浏览器拿到渲染机会，不然第一帧会被后面的循环挤掉）。
**别把内部步骤编进数字**：算校验值是给接收方做三方合并用的 —— 曾经拆成"算校验值一半、写包一半"
（total ＝ 文件数 × 2）还配上阶段字样，被用户骂画蛇添足。它现在不报进度（慢，数字停在 0，这是老实的）；
纯 CPU 的长循环按**时间**让帧（`utils/async.ts` 的 `yieldIfDue`，不是按项数的 `YIELD_EVERY`）。
状态栏那句动词由 `SyncProgress.label` 给（导出中 / 应用中）。

## 7. UI 上别撞社区的规矩

社区插件评审会照着这些报警告，`npm run lint` 也会：

- 不用已废弃的 API 换一个按钮颜色：`setDestructive()` 要 Obsidian 1.13+，而 `minAppVersion`
  是 1.7.0 —— **不为一个颜色抬最低版本**，用 `ui/modal-layout.ts` 的 `markDestructive()`
  （有就上红样式，没有就当普通按钮），别去调废弃的 `setWarning()`；
- 别在代码里写死 `.obsidian`：配置目录一律走 `Vault#configDir`（`host.configDir()`），
  连设置面板里的**示例文案**也别拿它当例子；
- 定时器用 `window.setTimeout` / `window.clearTimeout`（弹窗窗口里也能对上号）；
- README 顶部必须留一份**英文概览**：评审检查"README 有没有英文说明"，而且要把
  "读写仓库外的文件 / 唯一的 shell 调用（注册表关联）/ 剪贴板只写不读"说清楚。

**界面文案按"正常插件"写**：设置项与对话框里是**一行名字 + 一句话说明**，别把界面当说明书
（用户提过："界面解释太啰嗦，那些描述应该放 README"）。长解释、原理、踩过的坑一律写进
README / `ui/help-modal.ts`；界面只在**真出事**时多说一句（基准不一致、旧版包、要删东西…），
而且要说清"下一步做什么"。报数行保持一行一项（`新增 3 个`、`删除 2 个`），别在括号里塞理由。

## 8. 列表与同步包窗口

- **同步包界面必须同时写「第 N 版」和「状态 xxxx」**（`describeLocalState`，行里是
  `BundleListView.describeGeneration`）：版本号只是节奏号（两台各自 +1 会碰号），
  内容校验值才说明"两边文件一不一样"。导出 / 应用 / 管理三个弹窗都开 `showPosition`，
  行里还要标出「← 本机现在的基准」（跟 `state.bundle.fullFile` 对上号的那个）。
  **列表行里不写包名**（名字一长串挤占大量空间）：只写「第 N 版 · 状态 · 大小 · 时间」，
  完整路径挂在行的 `title` 上，另有「复制路径」按钮。
- **导出对话框导完不关窗**：结果写在窗口里、刚生成的包在列表里选中，用户当场就能
  **文件夹 / 复制路径 / 移到回收站 / 彻底删除**。
- 拖放 / 协议 / 侧栏图标：`ui/drop.ts` 认两种取路径方式（`File.path` / Electron 32 的 `webUtils`），
  文件关联必须调起 URI（`obsidian://locally-save?vault=…&bundle=…`，参数名**不能叫 path**）；
  测试见 `test/drop.test.ts` / `protocol.test.ts`。

## 9. 命令与设置是稳定接口

- **命令 ID 不许改名**（用户快捷键认它）：`sync-now`、`sync-preview`、`upload-to-copy`、
  `download-from-copy`、`export-bundle`、`apply-bundle`、`manage-bundles`、`bundle-log`、
  `toggle-enabled`。后两个"副本"命令现在是**过渡占位**（只弹指路通知），下一版删。
- **设置字段名不许改名**（用户 `data.json` 里存着它），改名前要写迁移。删掉的字段留在旧
  `data.json` 里不读即可，`settingsFrom` 不会把它们带进内存；**`test/settings.test.ts` 会核对
  字段表不多不少**，加 / 删字段必须同时改它。
- 设置分五页：「通用」「同步包」「Git 远程」「自动导出」「高级」。「通用」页装的是插件自身
  那几项（总开关 · 日志级别 · 左侧栏三个图标 · 状态栏）；曾经把后两组拆成「界面与交互」，
  两页各只有一两个开关、看起来像同一件事被劈成两半，已经合回「通用」（别再拆开）。
  「同步包」页分组：包放在哪 · 同步 · 手动导出 · 管理 · 应用同步包 · 用 Obsidian 直接打开。
  「更新包从哪个状态到哪个状态」在「高级」页；那两个下拉**选项是动态的**
  （`ControlSpec.dropdown.options` 允许给函数，`fields/types.ts` 的 `dropdownOptions()`
  在两条渲染路径上都解析它）——"本地有几份完整备份"要到渲染那一刻才知道。
