# 约定 · 导出与包（`.lsave` 这一侧）

> 从 `AGENTS.md` 拆出来的深水区：改 `src/bundle/export.ts` / `format.ts` / `merge.ts` /
> `manage.ts` 之前先读完。基准与应用见 `约定-基准与应用.md`，传输与界面见 `约定-传输与界面.md`。
> 守护用例：`test/bundle.test.ts`（导出 / 容器 / 清理）、`test/chain.test.ts`（合并与串联）、
> `test/generation.test.ts`（发号）、`test/manifest.test.ts`（发布产物）。

## 1. `.lsave` 容器

头部先写、偏移量提前算好（不回写，回写最容易断电写坏）；尾部布局是 `[标记][JSON][长度]`，
读的时候先看文件末尾 4 字节 —— 写读顺序必须一致。读不出的包一律当"不是我们的包 / 传坏了"，
界面里列得出来，自动那条路不碰它（`manage.ts` 的 `readBundleInfo`）。

## 2. 文件名要看懂，也要唯一

`<仓库名>-<完整|更新>-<版本区间>-状态<stateId>-<包ID前6位>.lsave`，例如
`我的笔记-更新-32代到37代-状态3f9a2c1d4e5f6a7b-5f4807.lsave`。
完整备份写它立的版本；更新包写「起点代到终点代」（终点＝接收方应用完到达的版本）；
内容校验值就是**包头部那个**（接收方该变成的状态）。

**不再带时间戳**（用户提的："状态后面那一长串数字没用"）：什么时候导的，列表里每行有
修改时间、更新记录里也写着；**同秒连导两个靠末尾那 6 位包 ID**（随机，不会撞）。

改名不改语义 —— 认包一律读头部；只有**读不出头部**时才按文件名猜类型
（`modeFromName`：`-完整-`/`-更新-` 与老的 `-full-`/`-changes-` **两种都认**，
少认一种，老包或新包就会从它那一组掉进"类型未知"）。

## 3. 导出顺序一处说了算：先完整备份、后更新包

`plannedExportModes()`（`bundle/export.ts`）是唯一出口，导出弹窗与自动导出都走它。
完整备份一写完，它自己就是最新基准 → 更新包按它算**必然是空的**，这时**不写空包**，
只提示一句（"更新包是空的：刚留的完整备份已含全部内容"）。旧顺序（先更新、后完整）演的是：
先按老基准算出更新包（顺手把上一个更新包清掉）、再导完整备份 —— 用户看到的是
"我那个包没了，然后又生出来一个一模一样的"。

## 4. 导出预览与真正导出共用一套挑选逻辑

`prepareBundle` → `planBundleExport`。预览说一套、实际导另一套是明令禁止的。
预览**只算不写**；算不出来（最典型：更新包还没有基准）时**不抛错**，把原因放进 `problem`，
界面照常打开并说明。

## 5. 自动导出只有一条流程

`ui/actions.ts` 的 `exportBundlesNow()` 是所有入口的交汇点（命令 `sync-now`、左侧栏第一个图标、
启动 / 定时 / 保存后三种触发）。锁是插件上的 `plugin.bundleBusy`（`main.tick()` 也看它），
跑完把 `plugin.lastBundleAt` 往后推。三处刻意省：整库**只扫一次**、两个包共用清单、
**自上次导出以来没有任何变化时一个包都不写**（完整备份一写就是整库重写）。

没有变化、没有基准、两个开关都没开，都要**如实说一句**，不能静默（状态栏 / 日志；
自动触发时**不弹通知**，见 `约定-传输与界面.md` 的通知规矩）。

## 6. 更新包只装"自起点那份完整备份以来变过"的

`prepareBundle` 的成员挑选，`anchorFiles` ＝ 起点清单。每个条目的 `base` **一律取起点清单里的
版本**（0.14 起 `ExportOptions.baseFrom` 已删：接收方就以那份完整备份为基准，它手里是这个文件的
哪一版只有那份清单知道）—— 拿"我上次导出的样子"当 base，会把对方正常的旧版本误判成
"它也改过"，满屏冲突副本。

`history` 记**我发出去过的版本**（每个文件最多 `HISTORY_LIMIT = 8`），用来认出
"对方跳过了几个包、手里是我发过的中间版本"（接收方停在"F0 与最新之间某一版"是新模型下的常态）。

**没有基准就拒绝导更新包**（没有起点就算不出来），不要悄悄退化成旧的"相对上次导出"语义。

### 6.1 改名/移动只留「基准 → 现在」这一条（0.17）

`detectMoves(anchorFiles, inventory, …)` 一次配对出**从起点清单直接到当前仓库**的移动：
中间改过几次名（旧 → 中间 → 最终），包里只有「旧 → 最终」一条。

**不再生成"上一份状态 → 现在"的链式移动**（`chainMoves`，0.17 删掉）—— 那是"按顺序演一遍历史"，
应用端得靠影子清单、靠 `previous` 里的中间路径逐跳复现，真机上报过好几次
「包里要把 X 改名成 Y，但本地两个路径都不在」「改名之后旧文件夹又回来了」。
仍使用中间某一跳的接收方，靠**累积删除清单**里点名的中间路径当源（`apply.ts` 的
`aliasSourceForFile` / `aliasSourceForDir`）一步变成最终路径，包里不必再写第二条。

`detectMovesByRecords` 会拿 `previous`（上一份状态）排掉"本来就在那儿"的新路径：
同目录里两个大小/修改时间完全一样的文件（`一.md` 改名、旁边还有同样的 `三.md`）
会让按记录配对歧义，明明改的是名字却被判成"删一个 + 加一个"。配对规则本身一条没松。

### 6.2 删除清单是**累积**的（`state.bundle.ghosts`，0.17）

**`deleted` 也得像 `entries` 一样累积**，这是真机事故「`live/implement` 删了又回来」的根因：

- base 之后新建的路径不在起点清单里，删掉它按"起点 − 现在"永远算不出删除；
  0.16 靠"上一份状态（`previous`）里还有没有它"临时补一笔，**只补一次** ——
  那一份包一导，状态里的 `files` 就没它了，**下一份累积包不再点名**；
- 自动接收按源头**只取最新的那一份**应用 → 没应用中间那一份的机器永远删不掉它，
  下一份包又把它当"本来就在"原样带回去（用户看到的就是"删掉的老文件夹过两天自己回来"）。

写入：状态里记 `ghosts`（路径 ＋ 接收方最后见过的那一版 `size/mtime/hash`），
**每一份更新包都点名**，直到换基准（导出/应用完整备份、应用差分更新包、接上后续基准 ——
新清单本来就不含它）或者这个路径又出现在仓库里（那时它是正常条目）。三条一起守：

- 导出：`prepareBundle` 把 `previous` 里"没了"的路径并进 `ghosts`，再并进 `deleted`；
  **只带着已点过名的幽灵不算"这一轮的新变化"**（否则什么都没改也会每 5 分钟重写一份包），
  预览也用这份口径（`freshDeleted`）；
- 应用：`header.deleted` 里**不在基准清单**的路径记进下一轮的 `ghosts`（`runPlan`）——
  我下次导出还得替你点名，否则第三台机器永远删不掉；
- 接收方本地改过它就不删（`ghostDeleteAllowed` 照旧按 `baseSize/baseMtime/baseHash` 判）。

守护：`test/cumulative-delete.test.ts`（只应用最新那一份也能删干净 / 从没见过该路径的机器也会记 /
换基准清空 / 路径又出现就不算幽灵 / 中间改名合并成一条移动）。

## 7. 起点与号：默认「本机当前使用的这一份完整备份」＋新号从高水位往后发

用户报的现场（0.13）："链条 39 → 54，我应用完整备份回退到 39，之后再导出却发「39 → 40」——
40 历史上早被这条线用过，同一个号底下两份不同内容，还从 39 分出一条岔、搞乱更新顺序。"

- **起点**：`export.ts` 的 `resolveStart()` 三种来路，一处说了算 ——
  ① 合成的起点（`anchorOverride`，"应用前先把本机改动存成包"那一趟）、
  ② 用户在下拉里明确指定（`baseFingerprint`；找不到就**报错**，绝不悄悄换一份，
  包头部记的基准决定接收方怎么比对）、
  ③ **默认：`state.bundle.fullHash` 那一份完整备份**（包文件被移走 / 删了时退回状态里那份清单）。
  0.13 那套"自动接在这条线的最新点后面"（`planAutoStart` / `AutoStartPlan`）**随链条模型一起删了**。
  `ExportStartInfo` 只剩 `{ picked: 'self' | 'explicit' | 'override'; mine }`；起点说明由
  `bundle/log.ts` 的 `describeExportStart` 给，导出窗口 / 导出预览 / 导出结果三处**共用**。
- **号**：见 `约定-基准与应用.md` 第 10 节（高水位只增不减、内容没动就沿用）。
- **回退之后原样没改 → 不写包**：更新包会算成空的，引擎返回 `file: null` 并说一句
  「自第 N 版完整备份以来没有任何变化，不需要导出」。
- **回退环（目标版本号 ≤ 起点号）不许被清理删掉**：它是这条线上唯一一份"往回走"的说明
  （`removeSupersededChanges` 里那道闸）；差分更新包也能造成这种环（「从 54 到 39」）。
- **界面**：导出对话框、导出预览、导出结果都要写清起点是怎么定的；`describeExportRange`
  **两个号都写**（`第 54 版 → 第 55 版`），不再写"→ 最新"。

## 8. 更新包可以指定「从哪个状态到哪个状态」

设置项 `changesFromState` / `changesToState`，引擎是 `ExportOptions.baseFingerprint` / `toFingerprint`；
0.14 起两个端点**只可能是完整备份**。

**值是基准校验值，不是版本号**：版本号是每台机器各数各的节奏号（两边各自 +1 会碰号），
按代选会选错那一份（用户实测：给"32 → 36"的包选了第 32 版当起点，对方回「基准不一致」）。
**本地有几份完整备份就有几个状态**，选项在渲染那一刻扫包目录算出来（`listFullAnchorsSync` +
`loadStateSync`：设置面板是同步渲染的，等不了 await；`readBundleInfoSync` 是唯一那份实现的
同步版，异步那个只是外壳）。链条上的中间点**不再是状态**（`bundle/points.ts` 与
`listPointRefsSync` 一起删了）。

`anchorOptions()` 的键＝校验值（同一份只列一次），标签＝ `第 N 版 · 基准 xxxx`（起点）/
`第 N 版 · 状态 xxxx`（终点）。两条硬规矩：

- **指定的那一份找不到就报错**（`describeAnchorList` 列出现在有哪些），**绝不悄悄换一份** ——
  包头部的 `baseGeneration` / `baselineHash` 决定接收方怎么比对，偷偷换一份等于骗它。
  预览（`planBundleExport`）照旧**不抛错**，把原因塞进 `problem`。
- **起点与终点语义不一样**：起点＝对方手里那一份完整备份，条目与删除项的 `base` 一律取**那份
  清单里的版本**；终点＝送到**那一份完整备份记着的那一刻**，内容**从包里读**
  （`BundleSource.from`，不是当前仓库），字节在它自己的负载里（`payloadOffset + entry.offset`）；
  `emptyDirs` / `stateId` 也用终点的。同一份差分更新包**不重复生成**
  （`findExistingCheckpoint` 翻 `changes/` 比对「起点 ＋ 终点 ＋ 终点内容校验值」）。

## 9. 差分更新包（终点是一份完整备份）

- **导的时候本机什么都不推进**：内容不是你现在的仓库，所以 `state.generation` /
  `state.bundle`（含 `fullFiles`、`history`、`dirs`）/ `state.stateId` 全都不动，
  `pendingReturn` 也不结清（你那半的最新改动它没带上）。日志那一条要标 `checkpoint: true`，
  `stateId` 记的是**终点那一刻**的编号。
- **不重复生成**（同上 `findExistingCheckpoint`）—— 自动导出会一轮接一轮地跑，不挡就是白写。
  换基准提醒（`baselineAdvice`）也不找它：内容由两份完整备份决定，不存在"越攒越大"。
- **要带「目的地那份完整备份的校验值」**（`BundleHeader.targetBaselineHash` →
  `ApplyReport.targetBaseline / targetIsMine`）：接收方据此认出"这个包要送到的地方
  **正好就是我这边的基准**"，那时它其实**什么都不缺**。用户实测过（把"32 → 36"的包发给一台
  已经仍使用 36 的机器），当时只看到一句"基准不一致"，看不出是无需变更 ——
  界面必须把这个结论直接写出来，别只报 mismatch。

## 10. 合并相邻的更新包（`bundle/merge.ts`）

用户要的"防止基准太多、更新太碎"。**0.14 起它的前提换了**：能合的"链"不再是链条模型里
首尾相接的基准，而是**一串更新包串成的链**（`F0→F1→F2`：前一环的目标版本 ＝ 后一环的起点），
合出来的是"从段首那份完整备份到段末那个状态"的一份差分更新包。动机也弱化了 —— 中间点不再是基准，
只剩**少几个包 / 清历史遗留**；功能**保留**。

- **能合的是"直线段"**：每一步只有一条出边的那一串（`planBundleMerges` 自己扫包目录，
  按"谁的目标版本 ＝ 谁的起点"认链，见 `listRings`）。**有分叉就跳过**，
  **按目标版本去重取最长的那段**。走的时候**段首那一环自己也算进去** —— 踩过：只收"后继的那几环"时，
  段首那环被丢掉、区间整体偏一环（用户报的「39 到 54、54 到 55 合不上」有一半是这个）。
- **合并 ＝ 把那几环的负载拼起来**（**不是**重新导一份）：顺着这一串把每份包的条目叠上去
  （**后一环的版本覆盖前一环的**），`base` 取**第一次**提到它时记的那一份，删除项取
  "最后一次提到它时是删"的那些，`history` 把路上那些中间版本一并带上。头部两端照旧：
  起点＝段首那环的起点、目标版本＝段末那环的目标版本，`stateId` / `emptyDirs` 取段末的，
  `viaHashes` ＝ 被吞掉的那几个中间状态（新包里只有它会写 `viaHashes`）。
  **一份完整备份都不需要，也不读仓库**。
- **为什么改成拼装**（用户报的「可能是因为我把 39 代完整备份删了，他就合不上了」）：
  重新导一份要先把段首那份完整备份算出来，用户把它删了就什么都合不了。可合并要的东西
  **全在这几环里**：内容在负载里、版本关系在 `base` 里。
  **别再退回"用 `exportBundle` + `baseFingerprint`/`toFingerprint` 重新导一份"**。
- **段首那一代的号取环自己记的**（头部 `baseGeneration`）：起点那份完整备份不在了，
  文件夹里就没有任何东西报得出它是第几代 —— 而那一环自己知道。
- **先写新的、写成了才移旧的**：那几份小包**移到回收站**（不是真删）。同一段已经有一份时
  直接用那一份（`findRing`），照样把那几份小的移走。动手前复核"这几环现在还是不是首尾相接"：
  包目录刚被动过就报错，什么都不动（先算后做的那份计划可能已经过期）。
- **本机什么都不推进**（不像导出）：版本、基准都不动；只有"本机正好仍使用段末那一份完整备份"时
  把 `bundle.fullFile` 改指合并后的这一份。更新记录里记一条 `checkpoint: true` 的导出，
  note 是「合并了相邻的 N 份更新包（X → Y 代）」。
- 被吞掉的那几个状态的**见证包没了**：所以合并是**用户主动**的一步，不是自动清理。

## 11. `changes/` 里的包默认都留着

只有「同一份起点 ＋ 同一形态 ＋ 同一台机器导的」才被取代（`removeSupersededChanges`，0.14 重写）。
更新包是**自某一份完整备份算出来的累积差量**，删错一份就可能让还以那份完整备份为基准的机器无法应用、
或者丢掉另一台机器那一半改动。逐条：

| 新包 | 旧包 | 处置 |
|---|---|---|
| 完整备份 | 更新包（版本不比它新） | **删**（完整清单取代得了它） |
| 完整备份 | 完整备份 | **一律不碰**（那是你的还原点） |
| 更新包 | 同一份起点 ＋ 同一形态 ＋ **也是我导的** | **删旧的**（新的是累积的，把旧的全说了） |
| 更新包 | 同一份起点，但**别的机器导的**（`source.copyId` 不同 / 认不出） | **留着**（那是对方那一半改动） |
| 更新包 | 同一份起点，但**形态不同**（一份到某份完整备份、一份到最新状态） | **留着**（两种各自有用） |
| 更新包 | **别的起点** | **留着**（还以那份完整备份为基准的机器要用它） |
| 任何 | 回退环（目标版本号 ≤ 起点号） | **留着**（正向导出生不出来） |
| 任何 | **起点已经没人站**（我再也不停在那儿，远程仓库上每台报的 `baselineHash` 也不是它） | **移到回收站**（退休，见 11.1） |
| 任何 | 别的分支 / 读不出头部 / 版本比新包新 | **留着** |

差分更新包还多一条：同一份起点要看**终点是不是同一份完整备份**，送到别处的留着。
「同一台机器导的」认的是头部 `source.copyId`；认不出来也**留着**（宁可多一个包，不丢一半改动）。

删 / 留都要如实报出来（`SupersededReport.kept` → `ExportOutcome.keptChanges` → 弹窗里那句话）：
不是同一分支 / 别的起点 / 别的机器导的 / 版本不比新包小 —— 悄悄留着会被当成"清理开关没生效"，
或者当偶发 bug（用户报过："同一个操作第一遍没清、第二遍清掉了"）。**清理是无条件的**
（0.7.0 把 `pruneSupersededBundles` 开关删了）。时机：**只在写包成功、状态落盘之后**才动手
（旧包是"目前唯一的改动备份"）；别的分支的包、读不出头部的一律不碰；
`keepPaths` 排掉"同一次里刚导出来的那个包"。

### 11.1 「起点没人站」＝ 这份包再也不可能被应用（0.18）

应用一份更新包/差分更新包的**前提**是接收方正好仍使用它起点那份完整备份（`checkAncestor`），
所以起点一旦空出来（我不仍使用那儿、远程仓库每台电脑报的 `baselineHash` 也不是它），
这份包对谁都没用了。三条同时成立才退休，缺一条就留着：

- 远程仓库上**有别的电脑上报过状态**（`peers.length > 0`）—— 单机 / 没开 git 时分不清谁在用；
- **没有任何一台**报着这个起点（某台很久没同步、报的还是旧基准时，它会保护这些包）；
- 旧包**记了校验值**（`baselineHash` 缺失就认不出它基于哪一份）。

跟"被新包取代"那一条的区别是处置方式：**这条走回收站**（`trashBundles`），
因为这里只知道"没人仍使用它的起点"，不能声称它的内容在别处；那一条是删，因为内容被新包完全覆盖。
报告里分两个字段：`SupersededReport.removed` 与 `.retired` → `ExportOutcome.superseded` / `.retired`。
守护：`test/rebaseline.test.ts` 第 8 组（没人站 → 退休且 file 不在；有人站 → 留着）。

## 12. 删除同步包 ＝ 移到回收站

`bundle/manage.ts` 的 `trashBundles`：落脚点是 `bundleTrashRoot()` 算出来的**离包最近的那个
`.lsave` 里的 `bundles-trash/<时间戳>/`** —— 用户在设置里填的包目录是 `<某目录>` 时，
就是 `<某目录>/.lsave/bundles-trash`，**跟 bundles 平级**。不许塞进 `bundles` 里面
（会变成 `.lsave/bundles/.lsave/bundles-trash`，两层 `.lsave` 套着，用户报过）；
老位置仍然会被 `readBundleTrash` / `emptyBundleTrash` 认（`legacyTrashRoot`），
否则用户之前删掉的包会"人间蒸发"。

**真删只有两条路**：「**彻底删除**」（行内按钮，`manage.ts` 的 `deleteBundles` → `removeFile`，
一次一个包，单独确认）与「清空回收站」（`disk.ts` 的 `removeDirRecursive`，rm -rf 语义，
只准传插件自己算出来的回收站路径）；别的删除一律是"移到回收站"。

列表 / 删除 / 回收站都在 `bundle/manage.ts`（不 import obsidian，测试直接跑临时目录），
界面是 `ui/bundle-list.ts` 那一套列表 —— 导出弹窗、导入弹窗、管理弹窗**共用**，
别让"这边能删、那边不能"；行内按钮是**应用… / 文件夹 / 复制路径 / 移到回收站 / 彻底删除**，
两个删除并排（用户提的：只有"移到回收站"时，想真删一个包就得清空整个回收站）；
**回收站那一行三处都要有**，而且放在列表**上面**（放下面会被"最多 40vh 的滚动列表"顶出视野）。

## 13. 更新记录与换基准提醒

- **更新记录（像 git log）**：`state.bundleLog`（`BundleLogEntry`，只留最近
  `BUNDLE_LOG_LIMIT = 100` 条，别把状态文件撑大 —— 它每次读写都要过一遍）＋
  `bundle/log.ts` 的 `appendBundleLog / describeLogEntry / describeBundlePosition /
  describeLastActivity`。`exportBundle` 与 `executeBundlePlan` 在**成功之后、saveState 之前**
  追加一条（方向、类型、版本 base→target、文件数/删除数、包名、来自哪个仓库）；
  `state.bundle.fullFile` 记"我这份基准是哪份包"。界面是 `ui/log-modal.ts`。
- **「更新包变大了就提醒立新完整备份」**（`bundleSizeWarnLimit`，MB，默认 20，`0` ＝ 不提醒）：
  0.11 删过一次（那时每份更新包只装自上一个基准以来的新改动），0.14 又请回来
  （新模型下它是累积的，前提又有了）。判据是**这一份实际要搬的字节数**
  （`header.payloadBytes`），**不是目录总大小**；时机是**包写完之后**；**差分更新包不提醒**。
  目标版本：导出结果对话框、导出预览各说一句，通知与状态栏也带上。
  这是新模型里**唯一要用户配合的维护动作** —— 换了基准，之后每份更新包才重新变小。
  字段名沿用老的，旧 `data.json` 里那个值正好接着生效。

## 14. 换基准之后：按每台电脑各自报的基准导差分更新包（0.18）

完整备份**不进 git**（`/full/` 排除），换基准之后仍在使用旧那台上的电脑，下一次收到的更新包是
"从一份它没有的完整备份算起"的 → 被判「基准不一致」，两边卡死。补法是**差分更新包**
（端点都是完整备份，只装两者之间的差异）：它收下、应用完就换到新基准上，
**手里不需要有新的完整备份**（`landedOnBaseline` 只认清单与校验值）。

- 计划：`bundle/rebaseline.ts` 的 `planRebaselineDiffs`（**只读**）—— 本机当前使用的那份
  （`state.bundle.fullHash`）＋ 远程仓库上每台报的 `baselineHash`（`git/peers.ts`），逐台给结论
  （`ready` / `exists` / `same` / `ahead` / `diverged` / `missing` / `no-baseline` / `too-big` /
  `no-target`）。**不同版本、不同一分支、找不到起点**各有各的话，别压成一句"导不了"。
- 执行：`exportRebaselineDiffs` 只导 `ready` 那几条，两端校验值都钉死
  （`baseFingerprint` ＝ 它那份、`toFingerprint` ＝ 我这份）；本机什么都不推进（`frozen`）。
  同一段不重复生成（`findExistingCheckpoint` 那套口径：起点代 ＋ 终点代 ＋ 终点内容校验值）。
- **超过 80 MB 就不写**（`REBASELINE_MAX_BYTES`）：包一旦落进 `changes/` 就会被 `git add` 收进去，
  超过 GitHub 单文件 100 MB 之后**每一轮同步都带着它失败**，等于把远程仓库搞停。
  那种情况如实说"把完整备份整份复制过去"。
- 入口：命令 `export-rebaseline-diff`「导出换基准的差分更新包…」、管理窗口「换基准之后」那一行、
  以及**导出完整备份之后顺手来一下**（手动导出窗与自动导出都接了）。一台都没上报过就什么都不做。
- 守护：`test/rebaseline.test.ts`（1–4 组）。

## 15. 旧完整备份：只在"确定没人站"时列出来，永远手动清

完整备份是**还原点**，所以 `removeSupersededChanges` 明文不碰它（§11 表格第二行）。
换了两次基准之后它们很占地（一份几百 MB），于是给一个入口 —— 但条件卡死
（`bundle/stale.ts` 的 `planStaleFullBundles`，**只读**）：

1. 不是本机当前使用的这一份（`state.bundle.fullHash`）；
2. 远程仓库上**有别的电脑上报过**，且**没有任何一台**报的 `baselineHash` 等于它；
3. 版本不比我这份新（比我新的那份是"我往回退过"之后的还原点）。

判断不了一律不动并说明原因（没开 git / 还没人上报 / 我还没有基准）。处置是
`trashBundles`（移到回收站）+ `git/removals.ts` 的记号（删除照样推到对面），
界面在「管理同步包」→「清理旧完整备份…」，先摊开再确认。
守护：`test/rebaseline.test.ts` 第 7 组。

## 16. 收下差分更新包之后：本机自己也要有一份这个基准的完整备份（0.18.1）
用户拍板："对面接收后也要导出一个完整备份，保证两边完整备份相同，然后才继续更新，这样最稳。"

应用差分更新包之后基准前进到了另一份完整备份，可手里只有那份更新包 ——
`state.bundle.fullFile` 只能是空的（`apply.ts` 里那段：拿更新包的文件名冒充完整备份，
"恢复本机误改"会去找错东西）。不补的后果：`findBaselineBundle` 按名字找不到它，
「恢复本机误改」/「强制回退到基准再应用」只能报"把那份包放回来"；给第三台机器导差分更新包时，
终点那份完整备份不在本机也做不出来。

写入：`bundle/rebaseline.ts` 的 `planBaselineCopy(state, inventory)`（**只读**）＋
`ui/rebaseline.ts` 的 `ensureLocalBaselineBundle`：

- **该补** ＝ `fullHash` 有值而 `fullFile` 为空；
- **盘上已经有同一份**（`listFullAnchorsSync` 里校验值相等）→ 只把 `fullFile` 记准，不重写几百 MB；
- **先核对校验值**：`listingHashOfFiles(inventory.files)`（＝ `exportBundle` 里 `freshBaseline`
  的同一算法）必须等于 `fullHash`。不等就**不补**并如实说出来 —— 那说明磁盘上这份并不是
  大家当前使用的那个版本（典型：文件系统 mtime 精度不同），补出来的会是**另一个基准**，两边从此不一致；
- 补的时候**什么都不推进**：`moved` 判据是内容编号（内容没动）→ 版本沿用，`fullHash` 不变，
  只是多了一个包文件、`fullFile` 有了名字。

时机：**自动接收那条路每次应用成功之后**（`ui/actions.ts` 的 `checkIncomingBundles`，
所以点一次「立即同步」就全做完）＋ 手动应用对话框收尾（`ApplyBundleModal.afterApply`）。
命令 `copy-baseline-bundle`「给现在的基准留一份完整备份…」是手动补漏的入口。完整备份占几百 MB、
又不进 git，所以照规矩弹一句。守护：`test/rebaseline.test.ts` 第 9 组
（该补 / 校验值不等就不补 / 补出来的校验值与版本 / 补完照样导得出更新包）。

## 17. 更新包的自动管理（0.18.2）

用户拍板：「所有终端都在新的完整备份后，老包到新包的更新包就应该从所有终端和 git 中清掉……
只保留需要的更新包，无意义的更新包自动删，防止仓库繁杂。」

判据只有一条：**还有没有机器用得上它**（应用一份包要求接收方的基准正好是它的起点）。
`bundle/gc.ts` 的 `planBundleGc`（只读）＋ `runBundleGc`：

| 情况 | 判定 |
|---|---|
| 起点是本机的基准，或者远程仓库上还有电脑报着这个起点 | 留着 |
| 起点已经没人用（本机换了基准、别的机器也都跟上去了） | 移到回收站（`base-unused`） |
| 同一份起点 ＋ 同一形态 ＋ 同一台机器导的，还有更新的那一份 | 移到回收站（`superseded-sibling`） |
| 回退环（目标版本号 ≤ 起点号） | 留着：这条线上唯一一份「往回走」的说明 |
| 目标版本比我这一代还新 | 留着：可能装着我还没有的内容 |
| 别的分支 / 读不出头部 | 留着：判不了就不猜 |

**什么时候跑**：`main.runTick` 每一拍在 git 推送和拉取**之前**看一眼 —— 所以「最后一台机器跟上来」
之后最多 30 秒，那份老包从所有地方消失（删除照 `git/removals.ts` 的记号提交并推走）。
没开 git / 远程仓库上没有别的电脑上报 / 正忙 → 整条不跑（分不清谁在用）。
例行清理**不弹通知**：状态栏一句 + 日志（规矩见传输与界面文档第 0 节）。

导出时顺手清（`removeSupersededChanges`）那条路照旧保留：它多一道「内容被新包完全覆盖」的判据；
两条路共用同一套安全闸（回退环、比我新、别的分支、读不出头部都不动；处置一律是回收站）。
界面上还有手动出口「整理更新包…」（`mergeAdjacentBundles`）：**首尾相接的合并 ＋ 兄弟包只留最新** ——
以前那个按钮只做前半件事，兄弟包（`320→862` / `320→863`…）配不成链，点了就像没生效。

守护：`test/rebaseline.test.ts` 第 10 组（没有电脑上报时不动手 / 兄弟包认成多余 / 起点没人用就清 /
只清该清的那一份）、`test/git-flow.test.ts` 第 6 组（手删的包不再被恢复、备份进回收站、远程与另一台一起没掉）。
