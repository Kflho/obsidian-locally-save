# 基准找回与对齐 —— 实施记录（0.16.1）

> 用户原话（2026-10-23，看到 397 同步失败之后）：
> **"对面有 320 代的，112 代只是之前遗留，明显可以同步。"**
> 紧接着补的一句（这条决定了整个做法）：
> **"对面有什么包和基准是什么是两回事，就算对面基准是 112，320 也是后续基准，不应该合并不上。"**

## 1. 现象（两台机器实测）

对面（KahoTAT）在 22:58 用 47 秒做了两件事，把基准从 320 退到 112：

| 提交 | 时间 | generation | stateId | 基准 | pending | lastApply |
|---|---|---|---|---|---|---|
| `0e668b3` | 22:58:01 | 392 | `30085573` | **320 / 12fcdf5c** | 0 | 更新 320→392 |
| `fb8df9f` | 22:58:48 | 392 | `ce9f15a0` | **112 / cece4244** | 108 | **完整-112 代** |

我们 23:52 导出的 `320→397` 头部是 `baseGeneration 320 / baselineHash 12fcdf5c`，
对面 `state.bundle.fullHash` 是 112 的 `cece4244` → `checkAncestor` 直接拒。
而对面的 `full/` 里有 320 那份完整包（526 MB），**信息是全的，只是插件没用它**。

同一份状态还暴露出第二个问题：`state.generation` 停在 **392**，而内容是 112 的。
`apply.ts` 的规则是"编号对不上就取 `Math.max(旧号, 包的目标号)`" ——
镜像没落准时（`stateIdCompare !== 'match'`）号就往回退不了，于是 peer 文件对外宣称
"我在 392"，**这次的排查（包括对面 agent 的结论）就是被这个 392 带偏的**。

## 2. 核心：两件事要分开

| 概念 | 是什么 | 从哪看 |
|---|---|---|
| **我站的基准** | 我这边内容上一次跟对方交换时的那一份（三方比对的**共同祖先**） | `state.bundle.fullHash` / `fullFiles` |
| **对方有什么** | 包里声明的起点完整副本 ＋ 这个包；那份完整包**可能就在本机磁盘上** | `header.baselineHash` ＋ 包目录里的 `full/` |

两件事不是一回事：**包里写的起点比我站的更靠后，就说明"我落后了一段"，
那一段的内容就在那份完整包里** —— 不是"接不上"，是"还没追上"。

## 3. 现在的做法（已实现）

### 3.1 接上后续基准（`resolveAnchor`，`bundle/apply.ts`）

`checkAncestor` 因为基准指纹不等而拒绝、且头部写着 `baseFullBundle` 时，
按指纹在包目录里找**包里声明的那一份完整包**（`findFullBundleByHash`：`bundleDir/full`、
`bundleDir`、当前包旁边的 `full/`、当前包所在目录，认指纹不认文件名）。

找到、且这份包确实"更靠后"（`theirs > mine`、同一分支、不是差量包、不是「仅拉」）→ **三方合并**：

- **祖先 ＝ 我记的那份基准的清单**（`state.bundle.fullFiles`）—— 只有它说得清"我相对它改了什么"；
- **我这边 ＝ 当前扫描**；
- **对方 ＝ 那份完整包的整份内容 ＋ 这个包的条目 − 包里点名的删除**。

实现上就是 `normal` 档：`planSync(local, remote, base)`，`conflictStrategy: 'remote-wins'`、
`propagateDeletions: true`，条目的内容按"包优先、其次从那份完整包里读"（`ApplyAction.write`
多了可选的 `sourceFile` / `sourceInfo`）。应用成功 → 基准接到那份完整包上（`adoptBaseline`）。

于是：本机落后的那一段被补齐，**本机相对自己基准的改动留着**，不需要先镜像一遍 500 MB。

### 3.2 接不上时只给"镜像对齐"（`BaselineResetHint`）

这几种情况不能"接上"，但那份完整包确实在本机，所以**拒收消息不换**（还是原来那两条出路），
只是额外挂一个 `err.baselineReset = { file, hash, generation, reason, mirrorOnly }`：

- 包的起点**不比**本机基准靠后（接上去等于往回走）；
- 老状态文件没有 `fullFiles`（说不清"我相对起点改了什么"）；
- 「仅拉」方向（目标是跟对面严格相等，本机这一半不该留）；
- 差量包（起点到最后一份完整包，让它直接发那份完整副本更直白）；
- 起点完整包不在本机（这条不给提示，照旧拒收指路）。

界面据此多一个按钮 **「按第 N 代镜像对齐再应用」** → `recoverToBaselineAndApply({ baselineOverride })`：
先把仓库镜像到那份完整副本，再应用这个包（本机多出来的进回收目录）。自动收包那条路
（`bundle/incoming.ts`）在「仅拉」策略下同样用它。

### 3.3 代数说真话（`applyDrift`）

- **完整副本镜像一律采纳包的号**（`isFull → generation = targetGeneration`）；
  合并档 / 接上后续基准那趟仍取 `Math.max`（内容里确实留着本机独有的改动）。
- 该变成的没写成（完整副本 / 严格镜像出现 `stateIdCompare !== 'match'`）→
  `state.applyDrift = { expected, actual, generation, at }` 落盘；
  状态栏的悬停、`git/peers.ts` 写出的对表文件（`contentDrift`）都会带一句
  **"内容与第 N 代不一致"**。下一次干净写入自动清掉。

## 4. 验收（`test/baseline-anchor.test.ts`，36 项全绿）

| # | 场景 | 期望 |
|---|---|---|
| ① | 本机停在旧基准（记录 + 内容都是 F1），包从 F2 出发、F2 在本机，本机另有 1 处改动 | 计划里出现 `baselineAnchor`；应用后 F2 新增的文件补上、包的条目落下、**本机改动还在**；基准接 F2；编号 mismatch（那半要回传） |
| ② | 记录脏了、内容其实就在包声明的起点上 | 不合并也不镜像（回收站不新增），应用后编号 match、基准纠正 |
| ③ | 起点完整包不在本机 | 照旧拒收并指路，**没有**"可以对齐"的按钮 |
| ④ | 包起点不比本机基准靠后（往回走） | 给 `baselineReset` 提示；`recoverToBaselineAndApply({ baselineOverride })` 写入成功 |
| ⑤ | 完整包镜像有路径没落成（只读文件） | 代数 = 包的号（不再 max 到旧号）；`applyDrift` 落盘；peer 带着 `contentDrift`；干净写入后清掉 |
| ⑥ | 老状态没有祖先清单 | 给提示 → 镜像兜底写入，基准是包声明的起点 |

回归：`test/bundle.test.ts` 里那两条"基准不是同一份 → 拒收""兄弟包照旧拒收"
已按新规则改写（现在都是"接上后续基准"）；`test/chain.test.ts` 的差量包拒收保持原样。

## 5. 没做的（要用户点头）

**货架分叉的「一键对齐」**：两边都往同一个 hub 推，谁后推谁被拒；插件按设计不 rebase
（外层是用户的仓库），这次是手工 `git pull --rebase` 解的。可做的是**限定范围**的按钮：

1. 本地 `ahead` 的提交**每一笔都只动货架那一段**；
2. 货架段之外的工作区干净、没有半截 rebase/merge；
3. `git rebase FETCH_HEAD` 无冲突（失败就 `--abort`，原样报错）。

报错文案同时带上可复制的命令 —— 这条不改约定，随时可做。
