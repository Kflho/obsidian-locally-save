## 0. 一句话模型

**基准 ＝ 一份完整备份**。更新包只表示"从某份完整备份到某个状态"的差量，不产生新点。
应用包就是"把仓库变成包送到的那个状态"（严格档）或者"把对方那一半合进来"（合并档）。

## 1. 基准：只有完整备份才算点（0.14 起的核心模型）

为什么改、影响面见 `technical_solution_docs/只有完整备份才算基准-实施计划.md`。状态里由
`state.bundle.fullFiles / fullGeneration / fullHash / fullFile` 一起表示"本机当前使用的这一份"。
一句话对照 git：完整备份 ＝ commit，更新包 ＝ "某个 commit → 某个 commit（或工作区）"的 diff。

| 形态 | 起点 | 终点 | 内容取自 |
|---|---|---|---|
| **差分更新包** | 一份完整备份 | **另一份完整备份** | 终点那份包的负载（**不是**现在的仓库） |
| **更新包** | 一份完整备份 | 最新状态（当前仓库） | 当前仓库 |

两者都相对**起点那份完整备份的清单**算差量（自它以来变过的进包、没了的进 `deleted`），
**没有第三种形态**。差分更新包在头部打 `targetFullBundle: true`（`format.ts`），
接收方据此知道"我变成了一份真基准上"（`apply.ts` 的 `landedOnBaseline`）。

### 什么时候推进基准

判定只在 `export.ts` 一处、`apply.ts` 一处，别在别处再写一份：

| 动作 | 基准动不动 |
|---|---|
| 导出完整备份 / 应用完整备份 | **前进** |
| 导出差分更新包 / 应用差分更新包 | 导：不动（内容不是你现在的仓库）；应用：**前进**到终点那份 |
| 导出更新包 / 应用更新包 | **不动**（我还是以那份完整备份为基准）—— 例外见下 |
| 应用前存下的那一份（`parkLocalChangesFor`） | 不动（`frozen`） |

内容记录那一半照旧每次都前进：`bundle.files`（`export.ts` 的 `landedPoint` /
`apply.ts` 的 `nextFullFiles`）、`history`、`dirs`、`generation`、`stateId`
—— **只有"本机当前使用的这一份完整备份"这几样不跟着更新包走**。

### 起点不是本机当前使用的这一份 → 基准接到它上面（`ApplyPlan.adoptBaseline`）

对方立了新基准（87 代）而本机仍使用 54 代那份，它却按新起点导了一份更新包
（「更新包：从哪个状态开始」下拉能选老起点）。内容上本机正好在它的路线上
（`checkAncestor` 的"算一遍目标版本"放行）→ 收下应用完，我该使用的点就是**它那份起点**。
不接的代价：我永远仍使用老点，下次导出变成"从第 54 版算起的整库回声"，包大得离谱。

两道闸（少一道就会记上一个假点）：

1. 头部得写着 `baseFullBundle`：起点**真是一份完整备份**。"应用前先把本机改动存成包"
   那一份的起点是**合成出来的状态**，谁手里都没有它的包文件 —— 接上去就成了谎话；
2. 起点清单是**倒推**出来的（目标版本里包点名的路径换回它带的 `base` 版本、没带 base 的条目＝
   起点里没有它），还要用头部 `baselineHash` 验一遍，验不过就不动。接过之后那份包**不在本机**，
   `fullFile` 留空（界面写"磁盘上没有它的包文件"）。这一步在**计划里**就定下来
   （`report.baselineAdopted`），执行阶段照计划办。

守护：`test/bundle.test.ts` 的 52（对面跟上一代一字不差时不许存"我的改动"包、应用完基准接到那份起点）。

### 为什么回传照样成立

链条时代那条"两个方向的推进必须一起走"是**当时的补丁，不再需要了** —— 现在只有完整备份推进基准：

```
A、B 都仍使用完整备份 F0
  A 改东西 → 导出「F0 → 最新」(P1)     A 的基准仍是 F0，内容 P1
  B 应用它                             B 的基准仍是 F0，内容 P1
  B 改东西 → 导出「F0 → 最新」(P2)     P2 ＝ P1 ＋ B 的改动
  A 应用它：起点 F0 ＝ 本机基准 ✓ → 收下，变成 P2
```

两边**始终以同一份完整备份为基准**，谁都能接着发、接着收，不必先重新导出几百 MB 的完整备份；
累积变大由用户导一份新完整备份整理（`bundleSizeWarnLimit` 提醒），对方仍在使用 F0 时用
**差分更新包**把 F0 → F1 一次带过去。

**别往里再加"两端同步推进"的逻辑**：那是给"点会自己往前走"的模型打的补丁。

### 头部报的三个校验值

- `baselineHash` ＝"我以为你用哪份完整备份上"（导出前那一刻的基准）；
- `targetBaselineHash` ＝"我变成哪儿"。**更新包的目标版本不是基准**（没有包文件、清单没物化过），
  它只是一个状态，给"无需变更 / 算一遍目标版本"两条例外用；
- `viaHashes` **只读不写**：导出不再生成它（0.14 起新包不带），只有 `merge.ts` 合并出来的
  那一份还会带上被吞掉的中间点。

### 三个例外，照旧放行

用户拍板："覆盖对方基准的任意更新包都是可加载的"：

1. 本机没有基准 → 只收完整备份；
2. `header.targetBaselineHash === 本机基准`（这个包要送到的地方正好是本机当前的这个版本 → 无需变更，
   报告里 `targetIsMine`）；
3. **"算一遍目标版本"对得上**：`本机现在的样子（state.bundle.files） ＋ 包里的条目 − 包里点名的删除`，
   它的**清单校验值等于头部报的 `targetBaselineHash`** → 应用完**正好变成对方那一点**
   （跟目标版本不一样的路径全在包里、一样的一条没动），收下是确定的。报告里 `viaMine` 就是这个结论。

第 3 条用的是 `files`（我现在的样子）而**不是** `fullFiles`：我可能刚应用过对方从同一份
完整备份导出的上一份更新包，内容已经往前走了。

光是"来路认点"（`viaHashes`）**不够**：用户实测"39→53，又导了一份完整备份成了 54，
重新导出 39→54，停在 53 的机器被拒" —— 那份完整备份把老的更新包清掉了
（`removeSupersededChanges`），来路断了，但内容上他确实在路线上，所以判定要以"算目标版本"为准
（`viaHashes` 当快路径）。**兄弟包照旧拒收**（两份不同目标版本的包，算出来的目标版本不一致）；
**"删除一万个"那类危险包也拦得住**（包里没覆盖到的差异会让清单校验值不一致）。

### 无法应用就直说，不降级合并

`checkAncestor` 拒绝信息要**指路到具体基准**：报出本机当前使用的这一份（第 N 代 · 基准 xxxx ·
来自哪份包），让对方「从本机这个基准重新导出」，或者导一份**完整备份**；差分更新包能把
"完整备份 → 完整备份"一次带过去。旧包（链条时代发的）照旧收得下。

**别退回"基准不一致也降级合并"**：更新包只有变过的那部分，基准不是同一份时
"基准里有、包里没提到"会被当成"对方删过它"，一大片本机文件要没。

### 旧状态 / 旧包照旧能走

旧状态文件的 `fullHash` 可能还是链条时代的一个中间点 —— 默认起点就是"状态里那一份清单"，
所以**照旧导得出来**；从此以后点只在完整备份上动，下次导 / 应用一份完整备份就自然归位。
`pointConfirmed` 已删（点变成完整备份之后不存在"这个点是我导的还是我应用的"），旧状态里留着不读即可。

## 2. 应用的三条硬规矩

### 2.1 更新包只能往前走，不许拿它往回走（0.16.10）

现场：一篇笔记被更旧的更新包退回了旧版，而且因为"起点对得上"，`checkAncestor` 放行、
看着完全合法。判据在 `planBundleApply`：`header.mode === 'changes'` ＋ **严格档**
（`mirror` / `bundle-wins`）＋ `targetGeneration < state.generation` ＋ 不是 `alignToPeer` → **抛错**，
并说清"要回退请应用完整备份（它本来就是还原点）"。

**不能一刀切**：`normal`（三方合并，`sweepIncoming` 用的就是它）会把"对方那一半"合进来，
包的目标号比本机小是常态（另一个源头导的包）；`alignToPeer`（仅拉）的职责本来就是"变成对面那样"。
守护：`test/baseline-anchor.test.ts` 第 8 组、`test/generation.test.ts`。

### 2.2 完整备份一律"完全镜像"（`mirrorFull`）

包里没有的本地文件移到回收目录、本机改过的被包的版本覆盖 —— 应用完**仓库 == 包**。
理由：合并完整备份会有无穷多种结果（本机改的算谁的、独有的留不留、删除传不传播），
每一种都能配出一个"既不等于包、又不等于本机"的仓库，之后导出的更新包 `base` 就不一致，
两台机器开始互相报"基准不一致"。`APPLY_CHOICES.full` 因此只剩 `mirror` 一项。

### 2.3 更新包必须与本机同一份基准（`checkAncestor`）

不满足**抛错**：本机没有基准 → 只收完整备份；校验值不等 → 拒收并给两条出路。
例外见上面"三个例外"。守护：`test/bundle.test.ts` 的"基准不是同一份 → 拒收""兄弟包照旧拒收"。

### 2.4 档位表只剩引擎意义

`ApplyStrictness`：`normal` / `listed-wins` / `bundle-wins` / `mirror`。界面上的手动应用一律
`mirror`；`APPLY_CHOICES` 两张表各只剩一项（`full` → `mirror`，`changes` → `strict`），
`ui/bundle-modal.ts` **不读它**（`test/bundle.test.ts` 守着这张表 —— 别再把它接回界面）。

- `normal` 走 `planSync` 三方比对（借"仅下载"方向 + `directionDecidesConflict: false`），
  只有 `incoming.ts`（自动接收）与 `chain.ts`（串联）在用；
- **`listed-wins`** 只动包里点名的文件 —— 条目一律用包里的版本（本地改过的那份进回收目录的
  「冲突」文件夹）、`header.deleted` 点名的照删，**包里没提到的一个不动**；
- 强制档不走三方比对（"只有本地改了、包里没改"会被判成"上传"而在包的方向上过滤掉）；
- 严格档**必然先备份**（`keepBackup` 忽略调用方传的值）；
- ~~引擎层保底：把 bundle-wins / mirror 传给更新包会 clamp 成 normal~~ —— **0.11 起不 clamp 了**，
  `strictnessDowngraded` 也一起删了（术语上别叫"回退"：包里那一版**可能比本地还新**）。

## 3. 三方比对的祖先 ＝「我上次交换到的样子」（`seed` / `history`）

`planBundleApply` 里的 `baseline` 是三方比对的共同祖先：

- 平常是 `state.bundle.files`（`contentBefore`，我上次跟对方交换之后两边的样子）；
- **接上后续基准**时是 `state.bundle.fullFiles`（`anchor.baseListing`，我记的那份基准的清单）；
- 包自带的 `baseSize` / `baseMtime` 只在该路径**本机没有记录**、或者它**比记录更新**
  （修改时间超出 2 秒容差）时才覆盖进去。

**为什么不能无条件让包的 `base` 压过本机记录**（0.16.14，用户报的"我删了又被撤回"）：
更新包是**累积**的，包里那个 `base` 取自**起点那份完整备份**，它可能比"我上次交换到的那一版"
更旧（上一份累积包早就把那个文件带到我这儿了）。拿它当祖先，本机删掉的文件会被判成
"两边都改过"→ 走"保导出里那一版"的分支写回来，删除当场被撤回；本机改过的文件也会被算成冲突，
白留一份冲突副本、白记一笔"待回传"。

`history`（包里记着"我发出去过哪几版"，每个文件最多 `HISTORY_LIMIT = 8`）仍然要留着：
**记录本身过期 / 被写坏**时（对方重新立过基准、我中间应用过别的包），靠它认出
"本地仍使用我发过的中间版本，不是本地改动"，别白留冲突副本。
守护：`test/local-delete.test.ts`（本机删除不被累积包撤回 / 本机改动不多留冲突副本）、
`test/bundle.test.ts` 第 47 组（记录过期时靠 history 认）。

## 4. 移动不能当成"删 + 加"

会两边各留一份。识别条件是「新路径确实是新出现的 + 旧路径在基准里 + 对侧那份自基准以来没动过 +
大小与修改时间完全一致」，四条缺一不可（`diff.ts` 的 `detectMoves`）。

- **0.17 起包里只有「基准 → 现在」一条移动**：中间改过几次名由导出端一次配对成「旧 → 最终」，
  **不再带"上一份状态 → 现在"的链式移动**（那是"按顺序演一遍历史"，真机上报过
  「改名之后旧文件夹又回来」）。老包（带链式移动的）照旧要能应用 —— 下面的影子清单逻辑留着。
- **计划阶段的移动要按顺序"演"一遍**（`apply.ts` 的 `plannedFiles` / `movedTo`）：
  老包里的链式移动是两条操作（旧 → 中间 → 新），接收方完全可能仍在使用**基准**上
  （手里只有"旧"，中间那份移动包没应用过）—— 第一条搬完、第二条的源在扫描快照里就不存在了。
  影子清单让"前面那条搬过去的东西"被后面的移动看见；链式那一条的源不在 `contentBefore` 里，
  用包自己带的 `move.size` / `move.mtime` 核对。目录移动同理。
- **停在中间路径上的接收方（0.17）**：包里只有一条「旧 → 最终」，源不在它说的位置上时，
  按**累积删除清单**（`header.deleted`，0.17 起带中间路径）认出"我现在这一份就是那个旧身份" ——
  `aliasSourceForFile`（文件：`size/mtime` 完全对得上、且该路径不在"送到的点"上）与
  `aliasSourceForDir`（目录：整棵子树的相对路径逐条对得上）。**候选必须唯一**，认不出来就报错、
  走强制回退（`recoverToBaselineAndApply`），绝不猜着搬。
  `deliveredFiles` 里已经被幽灵删除划掉的旧路径，搬的时候用 `contentBefore` 那一版把记录接到新路径上
  （`relocatePoint` / 文件移动那一支）—— 不接的话严格镜像会把刚搬过去的东西当"本地多出来的"删掉。
- **"送到的目录"要一路加祖先**（0.17.1 真机）：`deliveredDirs` ＝ `emptyDirs` ＋ 每个文件的**所有上级目录**。
  只加直接父目录会漏掉爷爷目录 —— 真机 2026-10-28：`temp/verify-017/new.md` 是这一趟新建的，
  而 `temp` 在上一份包之后变空了、又在 `state.bundle.dirs` 里，被排进"该删的空文件夹"；
  写完新文件后 `rmdir` 失败 → `effects.ok = false` → 接收层无需变更一次**强制回退**（`recovered: true`）。
  目录是内容：只要它底下（任意深度）有这一趟送到的文件，它自己就得留着。
- **删除信息必须累积**（0.17，`state.bundle.ghosts`，见 `约定-导出与包.md` 6.2）：
  base 之后新建、后来删掉的路径，每份更新包都要点名 —— 只点一次的话，没应用中间那一份、
  直接应用最新包的机器永远删不掉它（真机：`live/implement` 反反复复被重建）。
  "两个路径都不在"因此只剩一种含义：**本机这个路径真没了**（本地删了 / 移走了）——
  错误信息要指路：先把本机恢复到基准（重新应用那份完整备份）再应用，或让对方发完整备份。
  **别自动回滚**：那是覆盖本机内容，得用户自己点（跟"先算后做"一个道理）。
- **移动是幂等的**（更新包是累积的，同一条移动会一直带着）—— 判据不是"目标在不在"，
  而是**"这个源还是不是我记录里的那一份"**（`contentBefore`）：
  - 源没了、目标在 → 早搬过了，跳过；
  - 源在、目标也在：源里的文件一条都不在 `contentBefore` 里 → 这个源是**后来新建的**
    （改名时留下的空壳、用户在旧名字下又建了文件夹 / 笔记），跳过，别拿它去覆盖目标；
  - 源就是我记录里的那一份、目标也真占着 → 严格档以包为准，报告里记 `moveReplacements`，
    合并档仍然拒绝。
- **目标目录已存在时按文件并进去，不再整棵 `replace`**（0.15.6，用户报的「application 里只剩
  一个文件」）：累积包会把同一条移动一直带着，而目标那边多半已经装着上几份包搬过去的东西、
  源这边可能只剩一个空壳 —— 整棵替换会连带扫掉那些"已经在该在"的文件，只补得回
  `header.entries` 里的那几个（移动过去的东西不是条目）。按文件并：目标上没有的搬过去、
  目标上已有的（`sameRecord`）不动、占着别的版本的按严格档进回收目录的「冲突」、
  有同名条目的交给条目写（它才是这一点上的版本）。
- **"跳过"时上的记录也要跟着走**：计划里 `relocated`（`ApplyPlan.relocated`）把状态里的旧路径
  移到新路径，执行阶段 `runPlan` 照它 `freshAnchor` + 划掉旧记录。不搬记录 =
  `state.bundle.files` 停在旧路径，下一份累积包的"目标版本"（`deliveredFiles`）就按旧路径算，
  目标那边的东西又会被当成"本地多出来的"删掉。
- **严格镜像的删除判据是"送到的点上有没有它"（`deliveredFiles`），不是 `baseline`**：
  `baseline` 只是上次记下的样子，本机手工改过名 / 旧版本改名失败时就过时了；照它判会把刚搬过去
  （或手工搬好）的文件整批移到回收目录。删除收尾在**移动算完之后**跑，而且用移动影子清单
  （`plannedFiles`）当快照 —— 移动过的路径不会再被"删一遍"。
- **改名执行失败时不许把记录划掉**（`runPlan` 里 `statFile` 验过才 `delete contentBefore`）：
  划掉之后源还在磁盘上、记录里却没有它，下一份累积包会按"点上没有它"把它删掉。
  被严格镜像删掉的文件同样要从记录里划掉（`delete` 动作收尾再验一次 `statFile`）——
  假记录会让"算一遍目标版本"算错，明明接得上的包被判成"无法应用"。

守护：`test/moves.test.ts` 的「手工改名之后 / 手工改名单个文件 / 改名执行失败 /
目标里已有东西（按文件并）/ 旧路径空壳 / 旧路径新内容 / 真冲突 / 只拉连应用两次」。

## 5. 只拉（`alignToPeer`）的底稿与恢复

- 底稿必须是 `state.bundle.files`，**不能是 `fullFiles`**：更新包是累积的，拿完整备份当底会把
  上几份包带来的东西（尤其是移动过去的、包里只有一个 `move` 不带内容的那些）当成
  "本地多出来 / 本地误改"删掉或恢复回旧路径；连着应用两次就是"旧路径复活、新路径少文件、
  下一轮报目标已存在"。`fullFiles` 只当"恢复本机误改"的原版参考（`restore` 动作）。
- 恢复（`restore`）只在 `alignToPeer && fullFilesBefore` 时生成：本机在"包里没点名"的文件上
  改过 → 从基准完整备份读回原版，误改进回收目录，应用完内容校验值才对得上（`test/download-mirror.test.ts`）。
  缺基准完整备份时**明确报错并指路**，不静默删掉、也不拿别的包顶替。
- 报告里 `pendingChanges` / `pendingDeletes` 在 `alignToPeer` 或 `receiveOnly` 时记 0：
  这个方向没有"我这一半"要回传，记一笔永远发不出去的账只会让人以为漏发了。

## 6. 强制回退到基准再应用（0.15.7，用户拍板）

> "有基准包和对应更新包，信息就是全的，不管本机怎么改过都要能成功。"

- **触发**：计划阶段算不出来（`planBundleApply` 抛错）→ 应用对话框里的
  「强制回退到基准包再应用」按钮；应用完核不一致（`ApplyResult.effects.ok === false` /
  有 `failed` / 「仅拉」时 `stateIdCompare !== 'match'`）→ 自动走 `recoverToBaselineAndApply`
  （`ui/bundle-modal.ts` 与 `bundle/incoming.ts` 各一处；自动接收只在 `policy.force` 那条路上做）；
- **做法**：`findBaselineBundle` 按校验值找回**本机当前使用的那份完整备份** → 完全镜像应用一遍 →
  重新计算并应用这份更新包 → 再核对，结论记在 `ApplyResult.recovered`；
- 本机多出来 / 改过的都进回收目录（严格档必然备份），不会"消失"；
- **基准完整备份不在本机时报错并指路**（放回包目录 / 让对方发一份），绝不悄悄换一份、绝不硬合；
- 核对只看"计划动手的路径"（`collectApplyProblems`：`write`/`restore` 的记录、`rename` 的目标、
  `delete` 的消失、包里记着的空文件夹），**本机多出来的不算问题** —— 那是"我这一半"，
  本来就该由下一次导出带回去；拿整库内容校验值当判据会把每台双向机器都判成"不一致"。

守护：`test/alignment.test.ts`（完整备份 = 严格对齐 / 更新包 = 严格对齐 / 同一份包再应用幂等 /
手工搬过 / 少一个被移动的文件 → 拒绝计划 → 回退再更新成功 / 基准包不在 → 指路）。

## 7. 接上后续基准（0.16.1，用户拍板）

> "对面有什么包和基准是什么是两回事，就算对面基准是 112，320 也是后续基准，不应该合并不上。"

现场：对面记的基准是第 112 版（老遗留），我们导的包从第 320 版出发，而 320 那份完整备份
就躺在它的 `full/` 里 —— 旧逻辑只丢一句"无法应用，不合并"，逼人先镜像 500 MB。
规则在 `apply.ts` 的 `resolveAnchor`：

- **触发**：`checkAncestor` 因基准校验值不等而拒绝，且头部 `baseFullBundle === true`
  （合成起点不算）→ `findFullBundleByHash` 按校验值在包目录里找**包里声明的那份完整备份**
  （认校验值不认文件名；`bundleDir/full`、`bundleDir`、当前包旁边的 `full/`、当前包所在目录）；
- **能接上**（`theirs > mine`、同一分支、不是差分更新包、不是「仅拉」）→ **三方合并**：
  祖先 ＝ **我记的那份基准的清单**（`state.bundle.fullFiles`，**不能**拿包声明的起点当祖先）、
  我这边 ＝ 当前扫描、对方 ＝ **那份完整备份的整份内容 ＋ 包的条目 − 包里点名的删除**
  （`normal` 档 + `remote-wins` + 传播删除；写入的来源可以是那份完整备份，见
  `ApplyAction.write` 的 `sourceFile` / `sourceInfo`）。应用成功 → 基准接到那份包上
  （`adoptBaseline`）。**本机相对自己基准的改动因此留着**，不需要先镜像；
  报告里 `baselineAnchor` 写明接的是哪一份、留了几处本机改动；
- **无法应用就只给镜像保底**：包起点不比本机基准靠后（往回走）／老状态没有 `fullFiles`／
  「仅拉」／差分更新包 → 拒收消息不变，额外挂 `err.baselineReset`（`BaselineResetHint`：
  `file / hash / generation / reason / mirrorOnly`），界面出「按第 N 代镜像对齐再应用」→
  `recoverToBaselineAndApply({ baselineOverride })`；起点包不在本机时**不给提示**，照旧拒收指路；
- **代数要说真话**：完整备份镜像一律采纳包的号（`isFull → targetGeneration`），
  合并档 / 接上后续基准仍取 `Math.max`；该变成的没写成（完整备份 / 严格镜像
  `stateIdCompare !== 'match'`）→ `state.applyDrift = { expected, actual, generation, at }`，
  状态栏悬停与 `git/peers.ts` 的对表文件（`contentDrift`）都写"内容与第 N 代不一致"。
  **别再退回"镜像没落准也报旧号"**：上次就是它让对面报"我在第 392 版"而内容停在 112。

守护：`test/baseline-anchor.test.ts`。

## 8. 目录（含空文件夹）要建，也要删

包里的目录集 = `header.emptyDirs` ＋ 条目的上级目录（`dirsInBundle`）。
**严格镜像下目录也是内容**（0.11 用户拍板："空目录也是内容的一部分"）。

- **只装着被排除文件的目录不算内容**（`sync/disk.ts` 的 `scanTree`，0.15.4）：
  里面一个可见的文件 / 子目录都没有（`desktop.ini`、`*.lsave`、`.git`…）、但条目数 > 0 →
  **不进 `dirs`**。它搬不过去、`rmdir` 也删不掉，算进内容校验值只会让它永远不一致
  （用户报过"应用 100 代完整备份后编号一直差一点、列表却标着「← 本机现在的基准」"）。
  **真·空目录（一个条目都没有）照旧算内容**。
- 计划里先算一份 `deliveredDirs` ＝ **这一趟送到的那一点上有哪些目录**：包里的空文件夹
  ＋ 条目的上级 ＋ **那一点上还留着的文件的上级** − 点名删除的上级。计划的删除清单与
  执行收尾**都照它**，别各算一份；
- 执行收尾 `pruneEmptyDirs(..., keep = plan.deliveredDirs)`：删文件之后收拾空壳时
  **不许碰这一趟该有的目录**。踩过：对面把一个文件夹里的文件删光、文件夹留着，
  这边删完文件顺手把空壳收掉 → **内容校验值当场不一致**（"跟对方导出时的 xxxx 还差一点"
  而文件一个不差）；旧写法对更新包只删 `state.bundle.dirs` 记过的，会**漏掉本机新建的空文件夹**。
- `normal` / `bundle-wins` 仍按记录判（保守）。应用 / 导出后 `state.bundle.dirs` 只记
  **两边都见过**的目录。目录位置杵着同名文件时**报失败不硬来**。
- **删除清单必须"深的排前面"**（`byDepthDesc`）：父子都要删时先删父目录会被"非空"挡住，
  用户看到的就是"应用一次删不干净、每次多删几个"。
- **目录的删除只能走 `removeEmptyDir`（`rmdir`）**：非空必然失败，清单漏看了文件也只会"没删掉"。
- **计划里的空目录还要按磁盘复核**（`pickRemovableEmptyDirs`）：扫描清单看不见被排除规则挡住
  的东西（`*.lsave`、`desktop.ini`…），`rmdir` 却会失败；复核时**从深到浅累计**。
  复核不掉的**如实报出来**（`ApplyReport.foldersKept`，通知里也写一句原因），并把它记进目录基准 ——
  否则下一轮会把它当"新目录"重新建到对面去。
- 已经要写文件的目录会被 `ensureDir` 顺带建出来，所以 `folders` 要跳过这些
  （`receivingSide()` + `implied`），否则界面上会重复报数。
- **「删父目录」与「建新子目录」不许同时发生**（`removableDirs`）：一个目录能删，除
  「基准里有 ＋ 底下没文件」之外，还得**底下的每个子目录也都能删**（按深的在前递归）。
  否则「删 A」和「把 A/B 建过去」打架，用户看到「第一次删了又建了一部分、第二次才彻底同步成功」。
- 报告里**文件与文件夹都要报**（包里几个、本地几个、一致几个、要建几个、要删几个、留着几个）。
- **目录 / 文件冲突**（本地同路径是文件夹、包里是文件）：`normal` 档报成明确失败、
  **不动那个文件夹**；强制两档才把它移到回收目录腾位置。

## 9. 落盘：记录"两边都见过、这次真的写成了一致"的路径

- **上一次应用的结果必须落盘**：`state.bundle.files` 只记**两边都见过、且这次真的写成了一致**
  的路径 —— 绝不能写成"当前仓库的完整清单"（那会把我独有的文件也记进基准，
  下次应用就被当成"对方删过它"删掉，这是报过的 bug）。
- **应用完整备份时，新基准只能从「这个包自己的清单」里建**（`freshAnchor`）：
  **绝不能拿"我原来的基准"当底** —— 我独有的、包里根本没有的文件会漏进基准，
  之后我一导更新包，它们就被当成"我删掉了它们"发给对方（用户报过：对方那台机器的仓库比
  它的状态旧，于是凭空要求删掉本地还在的两个 schedule 文件）。
- **没落准就不换基准**（`landedOnBaseline`，0.15.4）：完整备份 / 差分更新包只有在 `result.failed`
  与 `plan.foldersKept` 都为空时才把 `fullFiles/fullGeneration/fullHash/fullFile` 换成这一份；
  有文件没写成、有文件夹删不掉时**退回上一次确认过的那个点**，日志与界面都要说"没写成这份基准"。
  判据**不是**内容校验值一致 —— 仍使用点的机器允许有本地改动；但只要写入 / 删除有失败，
  就不能声称站上了这个点。列表里那个「←」也**必须**同时比对基准校验值（`baselineOfBundle`）。
- **计划里那份"应用前的快照"必须被采用**（`ApplyPlan.contentBefore`）：`runPlan` 算新的内容清单
  用的是**计划时**那份 `state.bundle.files`，**不许现读状态**。踩过：park 会在"算计划"与"执行"
  之间把状态往前推，照它算出来的结果就**不等于包送到的那一份**，两边从此不一致。
- **冲突输的那一份必须移到回收目录的「冲突」文件夹**（`disk.ts` 的 `CONFLICT_TRASH_DIR`，
  本地侧 `.trash/locally-save/冲突/时间戳/`），**不要留在原地** —— 留在仓库里的冲突副本会跟着
  下一个包传到对面去，两边各滚一份、越滚越多。
- **应用有模块级串行锁**（`bundle/apply.ts` 里的 `applying`）：两个对话框一起点会互相踩着写同一批文件。

## 10. 版本号与内容校验值

### 版本号 ＝ 内容在这个分支里的"版本号"（0.10.1）

**同一份内容，在任何机器、走任何路径，报出来的版本号都必须相同**。三条写入规则：

1. **应用任何包 → 采纳包说的那一代**（`state.generation = header.targetGeneration`，
   **不再有 `Math.max`**）。**往回走是允许的、也是对的**：应用一份更老的完整备份之后，
   内容就是那一刻的，版本号跟着回去才叫"内容的版本号"。旧定义（"见过这条分支的哪一段"）
   靠 `Math.max` 硬压住回退，代价是两台内容相同的机器报出不同版本数 —— 那个定义已经废掉，
   **别再请回来**。（安全性：更新包只在"基准版本 ≤ 本机版本"时收得下。）
2. **导完整备份时，"内容没动过"就沿用当前版本**；有真改动才 `+1`。判"动没动"看内容编号
   （`state.stateId`），不看"大小 + 修改时间"：用户原话"导出完整备份本身根本不改变内容，
   不应该增加版本"；网盘同步 / 编辑器重写 / `touch` 碰一下时记录会变、内容一个字没变。
   `moved` ＝ `这次算出来的内容校验值 !== state.stateId.id`（旧状态文件没编号时退回按记录判）。
3. **导更新包 → `+1`，但"内容自上次导出以来没动过"就不加**。用户现场：起点钉在第 39 版，
   每次自动导出都重新导出同一份内容，而旧代码无条件 `+1` → 39→48 / 39→49 / 39→50 三份包
   内容校验值一模一样、版本号一路涨。**并且状态里那个号被撑大过就照手里的包改回来**
   （`smallestGenerationOf`：取同一目标版本报过的**最小**号）。判别用 `hasLocalChanges(state, inventory)`。
   **差分更新包 → 用终点那份完整备份的版本**。
- 配套：`removeSupersededChanges` 判"旧包是不是比我新"用的是**新包写入后本机所在的版本**
  （`state.generation`），不是新包头部的 `targetGeneration`。
- **导出起点默认＝「本机当前使用的这一份完整备份」＋ 新号从高水位往后发**：`state.maxGeneration`（高水位）
  ＋ `state.generation` ＋ **这次起点那一代**，三者取最大再 +1；"内容自上次导出以来没动就沿用
  当前号"。高水位**只增不减**（`raiseGeneration`，apply / export 两处调）——
  "回退之后再导出也不会撞历史上用过的号"就靠它。**别把包目录里的最大号塞进高水位**：
  外部包会把本机的号顶高，让"比我新的包不删"那道闸门失效（测试 37 守着）。
- **回退之后原样没改 → 不写包**：更新包会算成空的，引擎返回 `file: null` 并说一句
  「自第 N 代完整备份以来没有任何变化，不需要导出」；自动导出本来也走"没有变化一个包都不写"。
- **回退环（目标版本号 ≤ 起点号）不许被清理删掉**：它是这条线上唯一一份"往回走"的说明
  （`removeSupersededChanges` 里那道闸）。差分更新包也能造成这种环（「从 54 到 39」）。

### 内容校验值 ＝ "两边到底一不一样"的唯一判据

`sha256(排序后的「f\0路径\0内容校验值」+「d\0目录」)[:16]`。版本号回答不了这件事
（只是节奏号，两台各自 +1 会碰号），基准校验值只说明"祖先是同一份"。

导出时把**导出完那一刻**的编号写进包头部（`BundleHeader.stateId`），接收方应用完重扫一遍仓库、
算一个自己的跟它比（`compareStateId`）→ `match` ＝ 两边文件内容一致；`mismatch` ＝ 还差那笔
"欠回传"；旧包没记 → `unknown`。编号同时落进 `state.stateId` 与每条更新记录。

几条不能忘的：**编号里不掺 mtime**、**目录也算进去**、读不到校验值的文件如实计数（`unverified`，
那一行按大小+时间顶上）；**行里的校验值要截断成 `HASH_KEEP`（16 位）**再喂进哈希 ——
缓存里存 16 位、现算 64 位，不统一就会"同一个仓库算两次得到两个编号"（踩过）。
这一步**不报进度**（进度只认"打进包里几个文件"），但它会读盘，所以按时间让帧。

## 11. 应用只剩一种语义：严格同步（0.11 用户拍板）

- **界面上没有"应用方式"可选**：完整备份与更新包都走 `mirror` —— 包里点名的文件一律用包里的
  版本（本地那份先进回收目录）、`header.deleted` 点名的照删、**本地多出来的文件也移到回收目录**。
  应用完**仓库 == 包送到的状态**，内容校验值当场一致。
- **为什么更新包也敢镜像**：起点必须与本机当前使用的基准**完全相等**（`checkAncestor` 拦在前面），
  所以"送到的状态"是确定的 ＝ **我这边内容的样子**（`state.bundle.files`）＋ 条目 − 点名删除
  （**不是**"本机当前使用的那份完整备份"：更新包不推进基准，它比我的内容旧）。
- **应用前先把本机的东西存成一个包，起点就是"这份包送到的那一点"**
  （`ui/bundle-modal.ts` 的 `parkLocalChanges` → `export.ts` 的 `parkLocalChangesFor`）——
  严格档会覆盖 / 移走本地东西，先落一个包才不丢；**存不下就不动手**。

  ```
    park 那一环：  新点 N ──► N ＋ 我的东西        ← 这一环谁都能用
  ```

  三条硬规矩（都是踩出来的）：
  - **起点必须是合成的那个点**（`landedAnchorOf`：`plan.contentBefore` ＋ 包条目 − 点名删除；
    完整备份就是它自己的清单），不是"本机当前的这个版本" —— 按我自己的点算，会把"我这一点上有、
    对方那份里没有"的文件算成"没改过"，存出来是个**空包**，而镜像照样把它换走。
  - **对方那份包已经处理的路径不进这一环**（`skipPaths` ＝ 它的条目 ＋ 点名删除）：
    那些路径上我手里那份只是"比对方旧"，不是"我改过"。
  - **内容校验值照目标版本算**（`stateIdHashes`：被覆盖的路径用它包里的 `entry.hash`）。
